# CLAUDE.md

Working conventions for this repo (`PXL-Digital-Application-Samples/pxl-classroom`).

## Git
- **No pull requests.** Commit and push directly to `main`. Never open a PR, never branch "to be safe."
- End commit messages with the standard `Co-Authored-By` trailer.

## Working style
- Be terse and concrete. Do things rather than explain them; give exact values/clicks when the user must act.
- Don't ask for command approval - permissions are set to bypass in `.claude/settings.local.json`.

## Canonical documentation
- **`ARCHITECTURE.md`** - full technical specification (topology, trust model, data model, workflows, actions, flows, constraints). This is the single source of truth for *what the system is*.
- **`RUNBOOK.md`** - operational procedures (setup, onboarding, monitoring, edge cases, recovery).
- **`README.md`** - short orientation + links.
- *Authoritative AI Memory Rule:* when architecture or operational procedure changes, update `ARCHITECTURE.md`, `RUNBOOK.md`, and this file in the same commit. Do not introduce new top-level planning/progress/review documents - the project no longer uses them.

## Project facts (load-bearing - read ARCHITECTURE.md for detail)
- Target platform: **GitHub Team for Education. Never GitHub Enterprise.**
- **Hub-and-spoke:** all workflows live in the central public `pxl-classroom` hub. Per-org control repos hold data only and contain no workflow files.
- **Minimal-minutes (Wave 8):** synchronous provisioning (no queue), one nightly `daily-activity.yml` cron that disables itself when no assignment is active, event-driven dashboard regen. The system bills zero minutes when idle.
- **Admin Panel is the source of truth for lecturer actions** - assignment YAML and override JSON are generated and committed via the SPA + Contents API. The public Page assignments index is stored in the control repo as `assignments.json` keyed by assignment ID (object format), gathered dynamically by the hub build pipeline using `scripts/fetch-pages-data.mjs` to form the global Page data index. `regenerate-dashboard.yml` runs the interim report generator script (`generate-interim-reports.mjs`) to update `reports/dashboard.json` for active assignments in real-time. Roster CSV imports map schema validation (AJV) errors from mechanical formats (e.g. `/students/3/email`) to friendly, line-and-student-specific warnings using `formatRosterValidationError`.
- **`pxl-classroom` CLI is the parallel lecturer surface** (in `cli/`) - same App, same device-flow auth, same schemas as the SPA. Owns the workflows that scale poorly through clicks: CSV roster import, install audits, feedback-PR orchestration, bulk submission download (merging `_manifest.json` conforming to `download-manifest.schema.json` with fields `{login, archive_sha, archive_branch, archive_branch_url, downloaded_at}` by student login instead of overwriting, resetting remote origin to a tokenless URL). The SPA links to it via "Copy CLI command" affordances. For **autograding**, the system supports two paths: lecturer-local (via CLI) or student-side (`github_actions`, synced via SPA).
- **Central GitHub App** is created via the App Manifest form at the SPA's `/setup` route. Frontend deploys automatically via `deploy-frontend.yml` (which aggregates public JSONs from orgs). The manifest includes organization-level `organization_administration: read` for Enhanced Billing (distinct from repository `administration`); only account Starring remains manual. Setup verification and System Health validate permission metadata and probe the live billing endpoint. `setup-org.yml` performs the same preflight before creating organization state.
- **VITE_CORS_PROXY_URL**: If overridden, must explicitly end with `?url=` or `?` (which is auto-rewritten) for the device-flow proxy.
- **Scripting Note:** do not use inline `node -e` scripts in workflow YAML. Extract to `scripts/`.
- **One source of truth per cross-surface concern.** `lib/audit.mjs` exports `EXPECTED_APP_PERMISSIONS` and `MANIFEST_APP_PERMISSIONS` consumed by both CLI and `SetupView.vue`; `lib/gittree.mjs` is HTTP-stack-agnostic and shared by CLI, scripts, and SPA; `lib/control-layout.mjs` exports `CONTROL_SCAFFOLD_DIRS` (the ARCHITECTURE.md §5.1 control-repo layout), consumed by `lib/audit.mjs`'s scaffold check, `scripts/scaffold-control-repo.mjs` (called by `setup-org.yml`), and `control-repo-template/`. Don't fork these. `control-layout.mjs` must stay dependency-free - `setup-org.yml` runs the scaffold script without `npm ci`. `tests/scaffold.test.mjs` fails if any consumer drifts.
- **Preservation pushes a complete object graph.** `preserve/preserve.mjs` must fetch the submission SHA with full history before pushing it to `pxl-classroom-archive`. A shallow fetch (`--depth=1`) grafts away the commit's ancestors and the archive rejects the pack with `remote unpack failed: index-pack failed` - invisible while a student repo is one template commit, fatal once they have history. `tests/preserve-archive-push.test.mjs` reproduces it over `file://`.
- **Finalize is complete only when submissions are archived.** The idempotency key is not "a `lockdown-record.json` exists" - `find-finalizable.mjs` re-queues a past-deadline assignment while any student with a `snapshot_sha` lacks a verified `observations/<id>/<login>/preservation.json` (ARCHITECTURE.md §6.2.1). Three invariants keep that safe and must not be broken independently: `lockdown.mjs` **freezes** prior `snapshot_sha`/`lockdown_at` on a retry (re-reading `HEAD` would swap an on-time submission for a late commit - `tests/lockdown-retry.test.mjs`); retries are capped by `finalize_attempts` vs `MAX_FINALIZE_ATTEMPTS`; and `Commit + push` is `if: always()` so the record and counter survive a failed leg. `check-idle` must not disable the workflow when a finalize leg failed, or the retry can never run.
- **An empty population is not a failure.** Zero repository records for an assignment (nobody accepted yet) must never fail `collect`/`lockdown` - it turned every nightly finalize red and buried real failures in sibling matrix legs. `lockdown` still writes an empty `lockdown-record.json` so `preserve` reports "no students to preserve" instead of `fail:no-lockdowns`. Likewise a 403/404 on the billing usage endpoint skips that org instead of failing sibling matrix legs - and because requesting an ungranted permission is a **422 at token-mint time**, `weekly-usage-report.yml` re-mints without the billing scope and warns rather than failing the leg before the script's skip can run. System Health and onboarding must surface the missing `organization_administration: read` approval or Enhanced Billing access. That permission lives on the **App**, not the installation: an App created before the manifest declared it cannot have it approved by any org (RUNBOOK §6.7) - `gh api apps/pxl-classroom-provisioner --jq .permissions` is the check.
- **No attacker-controlled text may reach a shell on a broker.** A broker is public, holds `PXL_APP_PRIVATE_KEY` as a repo secret, and has issues enabled - so any GitHub account can fire its workflow. `BODY="${{ github.event.issue.body }}"` in a `run:` block there was arbitrary code execution against the App key, reachable by anyone, against every participating org (ARCHITECTURE §4.3.1). `${{ }}` is substituted into script *text*; `env:` is not. `tests/broker-injection.test.mjs` enforces three things: no workflow interpolates `github.event.*`/`client_payload` into any `run:` or `github-script` body (repo-wide, not just the broker); the broker never reads the issue *body* (it forwards the issue number, and `scripts/read-team-payload.mjs` validates it in the hub via `lib/team-payload.mjs`, with no `client_payload` fallback left in `acceptance/action.yml`); and the broker reads the issue *title* only through `env:`, only to match `^team:<slug>$`, and only as `client_payload.team_hint` - a **concurrency key**, never an authoritative value. The hint cannot be dropped: the concurrency group is evaluated at dispatch time, before the body can be read, and per-team serialization is what guards team capacity without a distributed lock.
- **Signed invitations are what stop outsiders triggering work.** Acceptance fires on a public event on a public repo, so anyone can ring the doorbell - star, fork, issue, comment, wiki edit are all open to any account, and none prove authorization. The roster gate authorizes, but only *after* the broker minted an App token and the hub cloned the private control repo. `lib/invite-token.mjs` (Node) + `lib/invite-token-format.mjs` (isomorphic, crypto-free, bundled by the SPA) move the first check to the edge: the broker checks out the public hub, verifies an Ed25519 signature against `acceptance/invite-keys.json`, and only then mints. **Asymmetric because the verifier is public** - an HMAC would put the minting secret on every broker; encryption is wrong too, since the broker cannot hold a decryption key and ciphertext replays fine on a public channel. The token rides in the issue **title** (122 chars, budget 256) so the broker never reads the body. `vars.INVITE_ENABLED` and the `pxl-accept:` prefix are job-level `if` checks, evaluated before a runner is allocated. `tests/invite-token.test.mjs` pins that no step before verification references a secret, plus canonical encoding (26 and 64 bytes do not divide into 6-bit groups, so the last char of each part carries discardable bits - without the check one link had several spellings). The token is **not** secret against sharing: that risk is accepted and bounded by `max_acceptances` (ARCHITECTURE §15). It must never reach Pages output. Republish reuses the nonce so live links survive a repair; `regenerate_invite: true` rotates it and retires them. `INVITE_KID` rotates keys. See ARCHITECTURE §4.3.2, RUNBOOK §1.3.1.
- **A closed issue on a public repo hides nothing.** The acceptance issue's TITLE carries the signed invitation, so the first student to accept used to publish the assignment's token to anyone who looked at the broker's issue list or searched GitHub for `pxl-accept:` - defeating §4.3.2 outright and, because the acceptance card is named `sha256(invite_token)`, making the card and its teams file public too. Three steps close it and none is optional: the **broker redacts the title** on *both* the accepted and the rejected path (`gh issue edit --title`, `issues: write` only, so no extra credential on a public repo - the reject path matters because `wrong-assignment` means a *live* token for another assignment landed there); the **hub deletes the issue** in `acceptance-handler.yml` (`deleteIssue` is GraphQL-only and needs **admin**, i.e. the App's `administration: write`, which `github.token` can never have) - it must run **after** `read-team-payload.mjs`, because deleting on the broker races the hub's read of the body and breaks every group join; and **System Health Tier 4 sweeps** the broker for surviving `pxl-accept:` titles, which is what catches a missing permission, an `INVITE_ENABLED=false` that skips cleanup, or a dead run. The sweep runs even when the assignment's own `invite_token` is absent or malformed. Where deletion fails, redaction alone is *not* sufficient - the rename stays in the issue timeline - so the message tells the lecturer to regenerate. `tests/invite-exposure.test.mjs` pins all three.
- **Public Pages artifacts disclose only what the student portal needs.** The acceptance card lives at `data/<org>/i/<sha256(invite_token)>.json` (teams beside it as `<sha256>.teams.json`), so finding it requires the link, a leaked filename is not a working token, and the teams file stops being a public cohort list of member logins. `assignments.json` survives reduced to id/title/organization/opens_at/deadline_at/timezone/repository_name_pattern/assignment_type/state, for one reason: the `/` portal matches a student's own repos against assignments and **students cannot read the control repo**. Broker repo, roster mode, cap, accepted count, description and group config are on the card only. `pages/scan.mjs` fails the publish on anything matching the token wire shape; `tests/public-data-contract.test.mjs` pins both halves. `index.html` sets `referrer: no-referrer` because the token is in the URL path. Residual, accepted: titles and deadlines stay enumerable - after §4.3.2 that grants nothing. In e2e fixtures `inviteToken()` must stay **pure** - a `Date.now()`-derived expiry is encoded at minute granularity, so the spec and the route mock straddling a minute boundary mint different tokens and 404 the card (flaked ~1 run in 4).
- **Hub credentials only run from `main`.** `workflow_dispatch` runs the workflow file from whatever ref it is given, and `participating-orgs` has deliberately lighter protection (ARCHITECTURE §5.5) - together a way to run hub code at a chosen ref with the App key in scope. Every job referencing `PXL_APP_PRIVATE_KEY` or `PXL_INVITE_SIGNING_KEY` therefore declares `environment: provisioning`, whose deployment branch policy is `main` only; a job naming an environment does not start when the ref is outside the policy, so this holds regardless of where the secret lives. `setup-org.yml`, `retry-acceptance.yml` and `publish-assignment.yml` additionally reject a `workflow_dispatch` from a `[bot]` actor as their FIRST step - lecturers dispatch as themselves, a stolen broker credential arrives as `<slug>[bot]`. Never put these secrets in workflow-level or job-level `env:`. Both keys are **environment** secrets with no repository-level copy, so a job that omits `environment: provisioning` cannot read them at all; `PXL_APP_CLIENT_ID` stays a repo secret because a client id is public by design. `tests/workflow-hardening.test.mjs` enforces all three. See ARCHITECTURE §4.3.4.
- **A rejection is an outcome, not a failure.** `accept.mjs` splits `reject()` (exit **0**, `rejected:*`) from `fail()` (exit **1**, `fail:*`). A student who is not on the roster, or arrives after the deadline, is the system working - painting the hub's Actions tab red for that teaches people to ignore red runs and buries real failures beside them. The outcome string still gates every downstream step, and `acceptance-handler.yml` routes rejections to the org's instructor tracking issue via `./notify` (`event-type: acceptance-rejected`, deduped per assignment+login+reason) - previously a rejection wrote nothing anywhere and the lecturer of that org had no way to see it. `tests/accept.test.mjs` pins both exit codes.
- **A restricted GitHub account fails invisibly.** GitHub returns HTTP 201 for an issue opened by an account it has flagged, then removes the content seconds later; no webhook fires, so the broker never runs. Observed live. `AssignmentView` records the acceptance issue number and, when polling gives up, re-reads it: gone means `blocked-account` ("GitHub is blocking your request"), not `timeout` ("GitHub is under load"). Check at timeout, never right after creation - the removal is not immediate.
- **System Health must check the invitation chain, not just the broker.** Four things have to agree before a student can accept, and every mismatch fails silently: the assignment holds an `invite_token`, the hub publishes the `kid` it was signed with (`acceptance/invite-keys.json`), the broker's `INVITE_NONCE` matches the token's, and `INVITE_ENABLED` is not `false`. Tier 4 checks all four; Tier 5 checks the acceptance card at `public/i/<sha256(token)>.json` - it previously only checked that the id was in `assignments.json`, which stayed true while the student's page 404'd. The checks stay silent for an unsaved Admin Panel form (`formDoc`), which never carries a token. `tests/diagnostics-invitations.test.mjs` proves each one FAILS when it should.
- **The Admin Panel rebuilds the whole assignment on save.** `buildDoc` constructs the YAML field by field, so anything it does not carry through is deleted - and the document still validates, because the invite fields are optional. Editing a published assignment therefore used to wipe its `invite_token` and silently retire every student's link. `buildDoc` and the edit-load path must both carry `invite_token`, `invite_nonce` and `invite_expires_at`; `tests/admin-lifecycle-ui.test.mjs` pins both halves.
- **One reader for the invitation, and it is the writer's.** `INVITE_FIELDS`, `readInviteField`, `parseInviteFields` and `quoteInviteValue` live in `lib/invite-token-format.mjs` beside the wire format, and are used by `scripts/set-assignment-invite.mjs` (writer), `AdminView.verifyLiveInfrastructure` and `AssignmentDetailView.loadInviteToken` (readers). The module stays **dependency-free** - `lib/invite-token.mjs` imports it and the broker runs that with no `npm ci` - so the parse is line-based regex, not a YAML round trip. Three consequences that are load-bearing: **`getRepoContent` resolves to decoded FILE TEXT, not a `{ok, data}` envelope** (both invitation read paths asked a string for `.ok`, so neither ever ran - and the test written to catch it grepped for the error message, which passed *because* the code always took the error branch); **`invite_nonce` is written quoted**, because ~1 nonce in 600 is all-digits-with-a-leading-zero and round-trips through a YAML parser as an integer, failing the hub's `^[0-9a-f]{8}$` check and silently retiring every live link on the next republish; and **`verifyLiveInfrastructure` re-reads unconditionally**, never gated on the form lacking a token, or a regenerated invitation never reaches the panel. `startPublishWatch` must call it on **both** terminal branches (`ready` and `timeout`) - the token is minted while the watcher polls, so without that the success banner says "verified live" over an empty link box. `tests/invitation-link-surface.test.mjs` runs the real round trip and flags any `getRepoContent` binding used as a response.
- **Dry-run is sacred.** Every CLI `--dry-run` must have zero side effects - no API writes, no PRs, no commits. (`feedback open --dry-run` creating real PRs was a P0; fixed in e967035.)
- **Live Status / Refresh invariants (AssignmentDetailView):** a post-deadline commit never downgrades a student who has an on-time submission on record (it sets `first_late_sha`, not a `late` status - nightly semantics), a partial refresh is never persisted (all students refreshed, or nothing is committed to the control repo), and grading sync results with 0 check-runs are logged under failed with reason `"no CI run at preserved SHA"`. Sync checks abort on API rate limits/errors. CSV export is generated client-side from the on-screen report, never fetched from the control repo. Live status checks classify based on the current local observation time (`new Date()`) instead of the student-forgeable `committer.date`. Status updates are frozen for students who already have `lock_down_at` set. Grading sync uses a 6-worker pool for concurrency and prevents overwriting pre-existing grades if the graded list is empty. The action button is labeled "Refresh".
- **Student Tooltip & Identity Resolution:** Hovering over student logins in the table/cards resolves identity across 4 tiers: (1) institutional roster (`students/roster.yml`), (2) Git commit author email/name (prioritizing real email, suppressing dummy `@users.noreply.github.com` and bot names `[bot]`/`provisioner`/`web-flow`), (3) GitHub public user profile (`GET /users/{login}`, batched in background with concurrency 6), and (4) clean fallback (`null`). Search filters across all resolved fields (name, email, student number, group, company).
- **Backend Observation & Report Invariants:** `collect/collect.mjs` queries `/repos/<org>/<repo>/commits?sha=<branch>&per_page=1` to record `commit_count`, `commit_date`, `author_name`, and `author_email` in snapshot observations, falling back to `GET /users/{login}` when commits are automated/missing. `report/report.mjs` propagates `commit_count`, `author_name`, and `author_email` to `reports/<id>.json` and CSV exports.
- **System Health Modal & Diagnostic Engine:** Unified diagnostic engine (`lib/diagnostics.mjs` and `lib/audit.mjs`) provides 5-tier ordered dependency checks (Auth -> Org Foundation -> Control Repo -> Template & `is_template: true` -> Acceptance Broker -> Pages Edge) and 1-click self-healing repairs. Tier 1 checks the **App's own declaration** (`GET /apps/pxl-classroom-provisioner`, needs no auth) before installation drift: an org owner cannot approve a permission the App does not declare, so undeclared permissions are reported against the App owner (`upstream: true` on the drift entry, "Blocked upstream" in the message) rather than as org-level drift - this misattribution is what made the 2026-08-21 onboarding failure take hours. Tier 1 also fails on `repository_selection !== "all"`, exempting the hub's own deliberately scoped installation. Both degrade to info/skip when `/apps` is unreadable - never a false alarm. `missingManifestPermissions` in `lib/audit.mjs` is the single comparison, shared by the audit engine, the diagnostic engine and `scripts/check-app-declaration.mjs`, which `weekly-usage-report.yml`'s `app-declaration` job runs on the Sunday cron so manifest-vs-App drift is caught on a cadence instead of by the next lecturer onboarding an org. Rendered inside `SystemHealthModal.vue` triggered on `DashboardView` by the `activity` pulse button (organization-wide health) and on `AdminView` via the "Troubleshoot" header button and interactive live status banners (per-assignment pre-flight troubleshoot & auto-fix). The organization dropdown renders styled visual status lights for org access and persists the last selected organization in `localStorage`. The top banner provides a direct `+ Assignment` shortcut navigating immediately to the new assignment editor.
- **Embedded Resource Usage Panel:** Embedded underneath assignments on `DashboardView`, presenting organization-wide KPI cards (Actions Linux compute minutes, storage GB-hours, organization GitHub API rate limit quota available vs total with reset countdown, and org limits status), 7-day early-warning threshold indicators, and a compact searchable line-item table.
- **Dispatch-and-watch.** SPA workflow triggers are never fire-and-forget: publish polls Pages assignments JSON with a cache buster and 8-minute timeout; daily-activity watches `reports/<id>.json`; usage sends a unique `request_id`, polls the exact Actions run every 5 s, then reloads `usage-latest.json` once after completion; retry-acceptance polls Actions status/conclusion with a 4-minute timeout and prompts before `bypass_window: "true"`. A completed usage run with unchanged `generated_at` is an error, not a reason to keep polling stale JSON.
- **Lecturer validations & Student gating.** Lecturer actions (granting extensions, retrying acceptances) validate student logins beforehand (checking roster, records, reports, and GitHub user API, returning specific error warnings for typo check vs. not on roster). Extension operations are append-only to preserve overrides history and success toasts clarify that status updates on the next nightly run or live refresh. The student acceptance card is gated client-side on `state === 'published'`, `deadline_at` not passed, and `accepted_count < max_acceptances` (showing closed/cap-reached early/closed status messages instead of Accept button, keeping provisioned repo access if already accepted). Acceptance timeout displays specific causes (cap reached, roster, or GitHub load - the roster cause is hidden under `roster_mode: open`). The central acceptance handler (`accept.mjs`) verifies that the student is registered in `students/roster.yml` (failing with `rejected:not-on-roster` or `rejected:no-roster` if missing) before recording acceptance or provisioning.
- **`roster_mode` is per-assignment and fails closed.** `enforced` (default) requires the login in `students/roster.yml`; `open` skips the roster gate entirely for assignments whose cohort isn't known up front (exams), leaving the `opens_at..deadline_at` window and `max_acceptances` as the only guardrails. **`open` therefore requires `max_acceptances`** - enforced in the schema (`allOf`/`if`/`then`), in `AdminView.fieldErrors` (so Save disables), and in `accept.mjs` (`fail:config`) for hand-edited YAML. Absent or unrecognised values - including `"Open"` - are treated as `enforced` in **both** `accept.mjs` and `pages/generate.mjs`; never loosen that to a truthy check. The flag is published to the public assignments JSON (the privacy scanner matches field *names* like `full_name`, not the substring "roster", so it does not trip). Under `open`, `AdminView.validateStudentLogin` treats any real GitHub account as valid for retries/extensions, since there is no roster to be absent from.
- **Theming is token-only.** The SPA is dual-theme (dark default / light / system). Every colour is declared **once** in `frontend/src/style.css`'s `:root` as `light-dark(<light>, <dark>)`; the toggle flips `color-scheme` via `data-theme` on `<html>` and every token re-resolves. **`:root` is the only place in the codebase a colour literal may appear** - no hex, `rgb()`/`rgba()` or named colours in component `<style>` blocks or inline `style=`, and no `var(--token, #fallback)` fallbacks (a fallback silently pins one theme). `light-dark()` returns a `<color>`, so it cannot wrap a whole `box-shadow` - only `--shadow-color-*` is themed, geometry is shared. Undefined custom properties fail **silently** (`border-color` -> `currentColor`, `background` -> `transparent`, `box-shadow` -> `none`), which is how `--border-color`, `--accent-amber`, `--color-border`, `--shadow-glow`, `--bg-hover`, `--bg-active` and `--accent-primary` all shipped broken. `tests/theme-tokens.test.mjs` enforces all four rules; see `DESIGN.md` §2 and §5. The runtime is `lib/theme.js` (`themeMode`, `resolvedTheme`, `setThemeMode`, `toggleTheme`). **The toggle is two-state**: `system` is only the implicit state of a visitor who has never used it, and the first press leaves it permanently - following the OS after someone has stated a preference would override them. `THEME_MODES` is what the toggle emits (`dark`/`light`); `STORABLE_MODES` adds `system` for stored values and `?theme=`, stored in `localStorage` under `pxl_theme` behind `try`/`catch`; a plain visit never writes a preference, only an explicit choice or a `?theme=dark|light|system` override does. **The default follows the OS** (`:root { color-scheme: light dark }`) - a first-time visitor gets whichever theme their machine is set to, and that is also the no-JS behaviour since an absent `data-theme` resolves from `prefers-color-scheme`. An explicit `light`/`dark` pins it regardless of the OS. Every toggle persists (`setThemeMode` -> `persistMode`); a plain visit never writes a preference, or `system` could never follow a later OS change. The inline boot script in `index.html` duplicates the storage key and mode list deliberately (it must run before the module graph or light-mode users flash dark) and sits *after* the SPA shim so a `404.html`-redirected deep link has its `?theme=` back before it reads it; the test asserts the copies stay in sync.
- **One app bar, one sign-in surface.** Every route renders exactly one `AppHeader.vue` (brand or breadcrumb variant) whose right rail always carries `ThemeToggle` plus `UserBadge` when a `user` prop is passed; `AuthCard.vue` is the only sign-in surface and owns the entire device flow, emitting `authenticated(user)` so the view only says what to load next. **`AppHeader.vue` must never gain a `<style scoped>` block** - slot content compiles in the *parent's* scope, so scoped rules cannot reach the breadcrumbs/actions views pass in; the `.app-header-*` vocabulary lives in `style.css`. This is the same trap that shipped four times: `.center-card` (used by 7 views, defined in 5), `.dashboard-header` (used by 3, defined in 1), `.sandbox-header` (used, defined nowhere) and `.auth-error` (used by HomeView, defined in 7 others) all rendered **unstyled** with no build error - `/usage` and `/dashboard/:org/usage` had full-bleed left-aligned sign-in cards and headers with no background or sticky positioning. **If more than one component uses a class, it belongs in `style.css`** - `tests/scoped-style-leakage.test.mjs` enforces this and the 86-instance backlog behind it is cleared, so it can no longer regrow. Use `.btn-link`, never `.link-btn` (a scoped re-implementation of the DESIGN.md §3 text button, removed). Where owners had diverged on a class, the global rule is the shared base and each owner keeps its scoped override, which still wins on `[data-v-*]` specificity. See `DESIGN.md` §7. `HomeView`'s signed-out hero is a deliberate exception - it is a landing hero, not a card. See `DESIGN.md` §6.
- **Lecturer onboarding is in-app, not in the RUNBOOK.** `Connect an organization` sits permanently in the org switcher (and on the empty dashboard) and links to GitHub's own installation picker (`APP_INSTALL_URL` in `lib/audit.mjs`) - the SPA never enumerates organizations itself, because a lecturer may belong to dozens and GitHub's page already filters to the ones they can install on. Installing happens in another tab, so `DashboardView` refetches installations on `visibilitychange`. When an org is installed but has no control repo, the dashboard shows `.setup-required-card` (distinct from `.onboarding-readiness-card`, which means "ready, now create an assignment"), branching on a probe of `permissions.push` on the hub repo: a lecturer without hub write is told a hub admin must run Setup Organization rather than handed a button that 403s. `getInstallations` paginates - the default `per_page` is 30 and orgs past it vanish from the switcher silently.
- **SPA UX & Design System conventions:** The SPA strictly follows the GitHub Primer design system (`DESIGN.md` is canonical): surface layering (`--bg-canvas` / `--bg-surface` / `--bg-surface-elevated`, inverted ramp in light so cards stay raised above canvas in both themes), a strict 1-primary-button rule per view (`.btn-primary`), status dot indicators (`.status-indicator` + `.status-dot` with `.dot-success`, `.dot-warning`, `.dot-danger`, `.dot-neutral`), and Primer underline tabs (`.primer-tabs` / `.primer-tab`). Root portal (`/`) is role-adaptive (unauthenticated landing with sign-in and direct link lookup; authenticated student "My Assignments" querying accepted repos only; authenticated lecturer dashboard routing); unaccepted assignments are unlisted by default (distributed via direct link `/:org/a/:id` without public browsing); assignment-scoped dates go through `formatDate(iso, assignment.timezone)` (`dashboard.json` entries carry `timezone` for this); editors with unsaved state guard both route-leave and `beforeunload` (incl. the roster tab's pending import - RosterTab exposes `isDirty()`); auth failures render inside the auth card, never the page-level error state, on **every** view; every authenticated view (incl. Admin Panel and assignment detail deep links) shows a sign-in card when no session exists - never a data-shaped empty state; assignment detail header includes an Edit shortcut button to edit the current assignment, an **Export ▾** dropdown menu (CSV, Manifest JSON with count/disabled state, and CLI commands), and a **··· More ▾** dropdown for secondary/maintenance actions; error toasts stay 15 s with hover-pause and a dismiss button (`role="alert"`), displaying text content safely and linking via an optional link property; CSV downloads carry a UTF-8 BOM for Excel; RUNBOOK citations are links to the GitHub blob; per-route document titles live in `router/index.js` `afterEach`; Inter loads non-blocking from `index.html` (no CSS `@import`); router `scrollBehavior` resets page scroll to the top on page navigations.
- **Publish never strands state.** "Save & publish" reverts the assignment YAML to `draft` when the `publish-assignment.yml` dispatch fails, so `state: published` never coexists with a missing broker. Cross-field rules the schema can't express (deadline > opens_at, `max_acceptances` ≥ 1) are enforced in `AdminView.validate()`.
- **New/Edit Assignment Form Invariants (AdminView):** The template repository selector is an autocomplete combobox calling `listOrgTemplates` (GitHub search `is:template` with REST API client-side `is_template` fallback on error/rate-limit) with WAI-ARIA combobox accessibility tags, collapsing on outside click. Editing the repository name pattern sets a manual lock preventing auto-overwrite from title/slug syncs. The default `max_acceptances` cap is `150`. Dynamic field-level validations display red warning messages underneath touched/dirty fields in real-time.
- **CLI destructive ops confirm.** `roster import` prompts before committing removals (TTY) or requires `--force` (non-TTY); `feedback open` separates newly created vs adopted pre-existing PR counts and exits non-zero on partial failure; `--concurrency` parses to positive integers only. Local host runner (`grade --runner host`) prompts for interactive confirmation on TTYs, requiring the `--force-host` bypass flag, or exits non-zero on non-TTY.
- **Group Assignments (M:1 Student-to-Repository mapping):** Polymorphic assignments (`assignment_type: "individual" | "group"`). Configured via `group_config` (`formation_mode: "self-service" | "pre-assigned"`, `max_team_size`, `min_team_size`, `allow_team_creation`). Teams are stored as manifests in `teams/<id>/<team-slug>.json` conforming to `team.schema.json`. Group repos use `{team_slug}` in `repository_name_pattern`. Sequential concurrency on `accept-${org}-${id}-${team_slug || login}` serializes joins and guarantees capacity limits without distributed locks. The first member provisions the repo from the template; subsequent members receive `PUT /collaborators/{login}` with admin access. Team switching revokes old repo collaborator access (`DELETE /collaborators/{login}`) and adds to new, marking 0-member teams `vacant: true`. Lecturer dashboard provides segmented Teams View and Students View, under-capacity warnings, and interactive team creation/member management modals. Lockdown demotes all team members to `pull`; preservation archives to `refs/heads/preserved/<id>/<team-slug>`; reporting aggregates top-level `teams` array and maps `team_slug`/`team_name` across CSV exports and student tables.
- **Carrying groups forward (team seeding).** Group membership is per assignment, so assignment 2 would make students re-form assignment 1's teams. `lib/seed-teams.mjs` is the single pure planner (no fs, no fetch, no Node builtins - the SPA imports it) shared by `SeedTeamsModal.vue` and `pxl-classroom teams seed`; it materialises `teams/<target>/<slug>.json` from a previous assignment's manifests or the roster's `team_slug`/`team_name` columns. **The roster is never written** - copy-forward from the *latest* grouping is drift-free, while a roster record would go stale the moment a student switches teams, and a roster CSV re-import replaces the file wholesale (`RosterTab` commits the parsed CSV, `CSV_COLUMNS` has no `teams` key) and would silently wipe it. Two invariants the planner exists to protect: **a login appears in at most one team file per assignment** (`accept.mjs` takes the first directory match, so a duplicate makes membership random) and **a target team that already has members is never overwritten**. It refuses - never truncates - on over-capacity teams, and refuses when target and source share a `repository_name_pattern`, because provisioning is idempotent on repo *existence* and would hand students the previous assignment's locked-down repository. Writes go through `lib/gittree.mjs` in **one** commit (33 teams via the Contents API would be 33 commits against a ~80 writes/min secondary limit; `utf8Base64` is `Buffer`-or-`TextEncoder` so the module is isomorphic) and **must** be followed by a `regenerate-dashboard.yml` dispatch - students read the generated public teams file, never the control repo, which is why lecturer-created teams used to be invisible until the next nightly run. Seeding is not enrolment: no repo exists until a member accepts, so `TeamsTable` dims members without an acceptance record - but only on a published assignment, since acceptance is impossible on a draft and flagging every member there is noise (`hasAccepted` is the fact, `isPending` is the display question; the undo depends on the first, the dimming on the second). **A bulk write needs a bulk undo:** `planUnseed` (shared by `TeamsTable`'s `Undo seed (N)` and `pxl-classroom teams unseed`, so the rule cannot fork) deletes - in one multi-file gittree commit, `content: null` per path - only teams carrying `seeded_from` with no repo and no accepted member; per-team deletion was the only route and `deleteVacantTeam` refuses teams with members. `planSeed` also returns `unplaced` (roster-relative, omitted under `roster_mode: open`) and names the students a kept target team strands, because after a carry-forward that list is the entire remaining manual task. `group_config.unassigned_fallback` (`block` default | `self-service`) is what stops a pre-assigned assignment from dead-ending late enrollers, and `accept.mjs` now enforces pre-assignment server-side (`rejected:team-not-assigned`) instead of honouring any team the payload names.
- **`lib/gittree.mjs` retries GitHub's *secondary* rate limit.** It answers 403 **or** 429 and does not necessarily zero `x-ratelimit-remaining`, so the old `403 && remaining === "0"` test made a large multi-file commit (a hundred blobs in a burst, e.g. seeding a big cohort's teams) fail outright instead of backing off. `rateLimitDelayMs` honours `retry-after`, falls back to a 60 s minimum for a secondary limit per GitHub's guidance, and still fails fast on a permission 403, which carries neither the header nor the wording.
- **DESIGN.md §1.2 is enforced on the group views too.** `tests/e2e/22-design-conformity.spec.mjs` used to visit only the dashboard/admin/usage routes, so the assignment detail page shipped with two competing primaries and the student page rendered one per team row - the exact case §1.2 names. The Teams tab's `Create Team`, the join-list rows and the manage modal's `Add` are secondary; the manage modal's `Save Changes` and the student's `Create & Join Team` are the single primary of their view (neither is `.btn-success`, which is not a §3 variant). The suite now covers `/dashboard/:org/:id`, both team modals, the seed modal and both student group states.
