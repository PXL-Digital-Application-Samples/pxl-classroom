# CLAUDE.md

Working conventions for this repo (`PXL-Digital-Application-Samples/pxl-classroom`).

## Git
- **No pull requests.** Commit and push directly to `main`. Never open a PR, never branch "to be safe."
- End commit messages with the standard `Co-Authored-By` trailer.

## Working style
- Be terse and concrete. Do things rather than explain them; give exact values/clicks when the user must act.
- Don't ask for command approval - permissions are set to bypass in `.claude/settings.local.json`.
- **No backticks in a double-quoted `git commit -m`.** The shell runs them as command substitution *before* git sees the string, so the quoted code fragment vanishes silently and the commit lands with a hole in it - `437dda0` lost three of them from one paragraph and `main` blocks force-push (RUNBOOK §1.5), so it cannot be amended. Use single quotes for any `-m` containing backticks, `$`, or `!`. Same family as the heredoc rule below: the shell processes the text before the tool does.
- **NEVER edit a file through a shell heredoc.** No `python3 - <<'EOF'`, no `cat > file <<'EOF'`, no `node -e`. Use the **Edit** tool for targeted replacements and **Write** for whole files. The shell and the interpreter both process escapes before the code runs, so regexes and string literals are silently mangled - `[^\n]*` becomes a literal newline, `\.` loses its backslash, `\s` and `\$` raise SyntaxWarnings. It has produced broken code in this repo many times over. If a scripted transform is genuinely unavoidable (a repo-wide sweep), **Write** the script to a real file, run it, then delete it. Bash remains correct for reading, searching, git, and running tests.

## Linting
- **`npm run lint` is the only lint command, and CI runs exactly it.** It was `eslint .` while CI's `test` job ran `eslint . --max-warnings 0` and CI's `lint` job ran `actionlint` + `scripts/workflow-lint.mjs` with no local equivalent - so a change could be linted clean locally, repeatedly, while CI had been red since `48ed831` over a shellcheck finding no local command could produce. Nine commits shipped on top of it. `scripts/lint.mjs` now owns all three checks; `ci.yml` calls `npm run lint` and nothing else. **actionlint and shellcheck are both pinned** - actionlint by version into gitignored `.tools/` (fetched on demand), shellcheck as a devDependency and passed explicitly with `-shellcheck`, because taking it from the runner image means a different version reports different findings. A tool that cannot be obtained **fails** the run; there is deliberately no skip flag, since a check that quietly does not run is the whole bug. `tests/lint-parity.test.mjs` fails if CI grows a lint route of its own or the entry point drops a check.
- actionlint runs shellcheck over every workflow `run:` block. A genuine false positive gets `# shellcheck disable=SC<code>` with a comment saying why - e.g. a GraphQL `$id` in single quotes is deliberately unexpanded (SC2016).

## Canonical documentation
- **`ARCHITECTURE.md`** - full technical specification (topology, trust model, data model, workflows, actions, flows, constraints). This is the single source of truth for *what the system is*.
- **`RUNBOOK.md`** - operational procedures (setup, onboarding, monitoring, edge cases, recovery).
- **`README.md`** - short orientation + links.
- *Authoritative AI Memory Rule:* when architecture or operational procedure changes, update `ARCHITECTURE.md`, `RUNBOOK.md`, and this file in the same commit. Do not introduce new top-level planning/progress/review documents - the project no longer uses them.

## Project facts (load-bearing - read ARCHITECTURE.md for detail)
- Target platform: **GitHub Team for Education. Never GitHub Enterprise.**
- **Hub-and-spoke:** all workflows live in the central public `pxl-classroom` hub. Per-org control repos hold data only and contain no workflow files.
- **Minimal-minutes (Wave 8):** synchronous provisioning (no queue), one nightly `daily-activity.yml` cron that disables itself when no assignment is active, event-driven dashboard regen. The system bills zero minutes when idle.
- **Admin Panel is the source of truth for lecturer actions** - assignment YAML and override JSON are generated and committed via the SPA + Contents API. Roster CSV imports map schema validation (AJV) errors from mechanical formats (e.g. `/students/3/email`) to friendly, line-and-student-specific warnings using `formatRosterValidationError`.
- **`pxl-classroom` CLI is the parallel lecturer surface** (in `cli/`) - same App, same device-flow auth, same schemas as the SPA. Owns the workflows that scale poorly through clicks: CSV roster import, install audits, feedback-PR orchestration, bulk submission download (merging `_manifest.json` conforming to `download-manifest.schema.json` with fields `{login, archive_sha, archive_branch, archive_branch_url, downloaded_at}` by student login instead of overwriting, resetting remote origin to a tokenless URL). The SPA links to it via "Copy CLI command" affordances. For **autograding**, the system supports two paths: lecturer-local (via CLI) or student-side (`github_actions`, synced via SPA).
- **Central GitHub App** is created via the App Manifest form at the SPA's `/setup` route. Frontend deploys automatically via `deploy-frontend.yml` (which aggregates public JSONs from orgs). The manifest includes organization-level `organization_administration: read` for Enhanced Billing (distinct from repository `administration`); only account Starring remains manual. Setup verification and System Health validate permission metadata and probe the live billing endpoint. `setup-org.yml` performs the same preflight before creating organization state.

- **Preservation pushes a complete object graph, and never with `--force`.** An org is entitled to forbid force-push with a ruleset (the same thing that made `ec896c8` stop force-pushing the broker), and a rejected push here fails preservation for every student - the safety net the whole deadline flow rests on. Nothing is lost: `refs/heads/preserved/<id>/<login|team-slug>` is fresh per student and `lockdown.mjs` freezes `snapshot_sha` across retries, so a retry pushes the same SHA to the same ref and git reports it already up to date. A genuine non-fast-forward means the archive holds something the system did not put there, which is not a thing to overwrite silently. `preserve/preserve.mjs` must fetch the submission SHA with full history before pushing it to `pxl-classroom-archive`. A shallow fetch (`--depth=1`) grafts away the commit's ancestors and the archive rejects the pack with `remote unpack failed: index-pack failed` - invisible while a student repo is one template commit, fatal once they have history. `tests/preserve-archive-push.test.mjs` reproduces it over `file://`.
- **Finalize is complete only when submissions are archived.** The idempotency key is not "a `lockdown-record.json` exists" - `find-finalizable.mjs` re-queues a past-deadline assignment while any student with a `snapshot_sha` lacks a verified `observations/<id>/<login>/preservation.json` (ARCHITECTURE.md §6.2.1). Three invariants keep that safe and must not be broken independently: `lockdown.mjs` **freezes** prior `snapshot_sha`/`lockdown_at` on a retry (re-reading `HEAD` would swap an on-time submission for a late commit - `tests/lockdown-retry.test.mjs`); retries are capped by `finalize_attempts` vs `MAX_FINALIZE_ATTEMPTS`; and `Commit + push` is `if: always()` so the record and counter survive a failed leg. `check-idle` must not disable the workflow when a finalize leg failed, or the retry can never run.
- **`late_policy` and `lock_down_enabled` are two decisions, and both used to be dead.** `late_policy: block` said "refuse late pushes" and no code read the field; `lock_down_enabled` said "demote admin -> pull at the deadline" and no code read that either - lockdown demoted everyone on every assignment regardless. Both shipped as form defaults, which is UX_PLAN's C4: *the UI must not describe behaviour the system does not have.* Now `block` stops the ref with a **repository ruleset** (`lib/submission-lock.mjs`: `update` + `non_fast_forward` + `deletion`, App in `bypass_actors` as `actor_type: "Integration"`) and `lock_down_enabled` is the separate Phase 4 demotion - because "cannot push" and "cannot re-run a workflow" have different costs, and demoting takes Actions, secrets, environments and runners on a course whose subject *is* those things. Confirmed live before shipping: the App pushes straight through an `active` ruleset (`remote: Bypassed rule violations`) while an **org owner** gets `current_user_can_bypass: "never"` and `GH013` - a student is repo admin, strictly weaker. Non-negotiables: **`lock_down_enabled` defaults to `true` when the field is absent** (every pre-existing assignment was demoted at the deadline; inferring "no lock" from a missing field would silently stop freezing live cohorts), **a ruleset is never created without a resolvable App id** (the system would be locked out with no way back), and **a failed ruleset degrades to a demotion, never to no lock**. `emptyForm()` defaults to `report`: `block` discards work, so a lecturer opts in. `tests/submission-lock.test.mjs`, `tests/lockdown-late-policy.test.mjs`, `tests/e2e/29-late-policy-control.spec.mjs`. ARCHITECTURE §11.2.1.
- **The sentinel's precision was invisible in the record it exists to improve.** It writes no `lockdown-record.json` on purpose, so the nightly hours later had no prior to read and stamped `lockdown_at` with **its own clock** - for a 20:00 deadline the record said the cohort froze at 00:00 and `uncertainty_seconds` reported four hours where the sentinel had achieved seconds. Nothing was lost (nobody could push after the stop, so the SHA is right), but that number is the evidence a lecturer cites in a dispute and it understated the system against them. `lockdown.mjs` now reads the `sentinel-<key>.json` timeline sitting beside the record and credits a **fired** one - `gave-up:runtime` is not credited, because there the nightly really is what stopped the cohort and claiming otherwise invents precision. Credited **per target, not per cohort**: a student whose extension was still running when the sentinel fired was deferred then and is only being stopped now, so their own effective deadline is the discriminator - it is later than the instant precisely when they were deferred past it. `tests/lockdown-phases.test.mjs` pins all three, and the deferred case was written first with the dead flat `deadline_at` override shape, which reads as *no extension at all* - the fixture trap this file already records, hit again.
- **The sentinel waits for the instant and stops nothing itself.** `deadline-sentinel.yml` (4-hourly cron, 4.5 h arm window, keyed on **(org, deadline instant)** so assignments sharing a deadline share a job) closes the gap between the deadline and the nightly. Load-bearing details: it **polls rather than sleeps**, and the poll is `GET /orgs/{org}/repos?sort=pushed&direction=desc&per_page=100` — one call for a hundred repos, where per-repo polling would be 7,200 requests against a 5,000/hr limit; `pushed_at` is GitHub's own timestamp, so the resulting timeline (`lockdowns/<id>/sentinel-<key>.json`) is the only thing that can answer "at 21:55 your last push was 21:12", which the committer-date fallback cannot. The stop goes through `applySubmissionLock` via `STOP_ONLY=1`, so there is one implementation of "stop writes" — and **`STOP_ONLY` must never write a lockdown record**, because `find-finalizable.mjs` reads that record's existence as evidence a finalize happened and one with empty `results` strands the assignment forever. Every failure degrades to the nightly (`fired=false` triggers no stop), which is why it is safe; it **ships disabled** and `publish-assignment.yml` enables it beside `daily-activity.yml`. `tests/deadline-sentinel.test.mjs`, `tests/lockdown-phases.test.mjs`. ARCHITECTURE §11.2.3.
- **The `until` fallback is honest, not tamper-proof.** Phase 1 fires on the nightly, not at the deadline, so under `block` phase 2 rebuilds the submission with `commits?until=<effective deadline>` and takes `[0].sha` - `null` (a `no_submission`, not an error) when nothing was committed in time. Confirmed live: **`until` filters on the committer date alone** - authored-before/committed-after is excluded, authored-after/committed-before is returned, matching `git log --until` - and `GIT_COMMITTER_DATE` is client-supplied, so this must never be described as proof; the form's own copy says so. It only runs when `pushed_at` (already in hand from the repo object) is after the deadline, so the ordinary case costs no extra call, and the window is the student's *effective* deadline. Under `report` it must not run at all: a late commit **is** the submission there. `preserve.mjs` gained a third bucket for `no_submission` - one slacker used to turn the whole cohort's nightly amber. ARCHITECTURE §11.2.2.
- **Lockdown stops the whole cohort first, then records it.** `lockdown.mjs` is four phases (plan / stop / record / demote), not one loop per student. The old loop read a student's `HEAD` and then demoted them, so in a 200-student cohort student 1 froze at T+0s and student 200 minutes later - the demotion is a write against an ~80/min secondary limit - which both gave the end of the list extra time and made the snapshot a smear rather than a cut. `applySubmissionLock({ targets, method })` is the only thing that knows *how* writes stop (`demotion` today, one ruleset flip later); `recordCohortState` reads `pushed_at` off the repo object it already fetches, which is GitHub's own server-side timestamp and the only field in the record a student cannot set. The record carries `locked_at`, `lock_method` and per-student `pushed_at`. Two invariants the tests pin (`tests/lockdown-phases.test.mjs`): **every** stop precedes **any** read, and a phase-2 failure leaves the cohort stopped and is safely re-runnable - a repo that cannot be read still produces no result row, because `preserve` iterates results and a permanently unpreservable row turns every later night amber. Freeze-on-retry stays, but as belt and braces rather than the thing holding the design up.
- **One deadline per student, and `lib/effective-deadline.mjs` is where it is decided.** Every comparison against "the deadline" must be the deadline *for that student*, or the system acts against work a lecturer allowed. `report.mjs` had the only copy and it read `override.deadline_at` - a field the Admin Panel stopped writing on 2026-06-17 in favour of the append-only `overrides[]` array that `override.schema.json` requires - while `lockdown.mjs` and `find-finalizable.mjs` never opened `overrides/` at all. So extensions worked nowhere: the student was demoted to `pull` at the assignment's own deadline and then reported as on-time and extended. The test covering it built its fixture in the same dead shape, which is exactly the failure mode this file warns about. Both shapes are read now (old control repos hold the flat one), the array wins, and an extension only ever **extends** - a value before the assignment deadline is ignored rather than shortening it. A group shares one repo, so the most generous member extension governs the team. **The SPA imports the same module** (`frontend/src/lib/deadline.js` re-exports it, as `lib/invite.js` does for the token format) because the rule had forked three ways: the backend and the two lecturer views took the **last** entry of the append-only history, while `AssignmentView` and `GroupAcceptanceCard` took the **first** - so a student granted a second extension was shown, and counted down to, a deadline that had already been superseded. `AssignmentView` also replaced the deadline unconditionally, so an earlier value would have *shortened* it on screen. `tests/effective-deadline.test.mjs` fails if any file outside the module picks the extension in force itself. **Two more things that must stay true:** a student who already has a **frozen snapshot is never deferred**, whatever their overrides say - deferring rewrites their result row with `snapshot_sha: null` and loses the recorded submission (RUNBOOK §6.2a covers the after-the-fact grant); and a **malformed extension locks rather than defers**, because a student left deferred on an unparseable date would never be finalized at all. Four more consequences that must stay true together: `lockdown.mjs` **defers** such a student before its first read (no repo fetch, no observation, no permission touched) and records `deferred_until`/`deferred_count`; `preserve.mjs` does not count a deferral as an error, but a missing `snapshot_sha` *without* `deferred_until` still is; `find-finalizable.mjs` re-queues the assignment when a `deferred_until` passes, outside `MAX_FINALIZE_ATTEMPTS` because it is new work, not a retry; and the assignment stays counted in `activeCount`, or `daily-activity.yml` disables itself mid-extension and never comes back. `tests/effective-deadline.test.mjs`, `tests/lockdown-extension.test.mjs`, `tests/preserve-deferred.test.mjs`, `tests/find-finalizable.test.mjs`. ARCHITECTURE §6.2.2, RUNBOOK §6.2.
- **An empty population is not a failure.** Zero repository records for an assignment (nobody accepted yet) must never fail `collect`/`lockdown` - it turned every nightly finalize red and buried real failures in sibling matrix legs. `lockdown` still writes an empty `lockdown-record.json` so `preserve` reports "no students to preserve" instead of `fail:no-lockdowns`. Likewise a 403/404 on the billing usage endpoint skips that org instead of failing sibling matrix legs - and because requesting an ungranted permission is a **422 at token-mint time**, `weekly-usage-report.yml` re-mints without the billing scope and warns rather than failing the leg before the script's skip can run. System Health and onboarding must surface the missing `organization_administration: read` approval or Enhanced Billing access. That permission lives on the **App**, not the installation: an App created before the manifest declared it cannot have it approved by any org (RUNBOOK §6.7) - `gh api apps/pxl-classroom-provisioner --jq .permissions` is the check.
- **`roster_mode: org_member` turns a list of EMAIL ADDRESSES into a gate, by letting GitHub do the binding.** A lecturer holds student emails, not GitHub usernames, and email can never be matched directly: an installation token cannot read a user's email addresses (`GET /user/emails` is user-to-server), and anything the SPA sends is a claim, not a credential (§4.3). So the lecturer invites the addresses to the org, GitHub connects each invitation to whichever account accepts it, and `accept.mjs` asks for the result. Load-bearing details, all measured live 2026-08-25: the gate is **`GET /orgs/{org}/memberships/{login}`, never `/members/`** - an invited-but-unaccepted account reports `state: "pending"` on the former and **404 on the latter**, identical to never-invited, and that difference is the entire student-facing message (the waiting-screen rule again: a page may not guess why it is stuck); `active` accepts, `pending` is `rejected:membership-pending`, 404 is `rejected:not-org-member`, and **403/5xx is `fail:*`, never a rejection** - a missing `members: read` approval must not silently admit or silently reject a whole cohort; and anything that is not exactly `active` rejects, so an unrecognised state fails closed. **The residual is unfixable in code and must stay in the copy:** an invitation to an address no GitHub account has *verified* leaves `login: null` and creates no membership record, so the student is indistinguishable from an outsider - the 404 message names **both** causes rather than asserting one. A cap is optional here (membership is itself a limit), unlike `open` where it is mandatory. `tests/org-member-gate.test.mjs` drives the real `accept.mjs` against a real local HTTP server via `GITHUB_API_URL` - and uses **`spawn`, not `spawnSync`**, because the mock server lives in the test process and a synchronous spawn blocks the event loop that would answer the child, hanging the suite. `tests/e2e/42-org-member-mode.spec.mjs`, ARCHITECTURE §15, RUNBOOK §12.4.
- **One reader for `roster_mode`: `lib/roster-mode.mjs`.** The rule was written by hand in five places as `roster_mode === "open" ? "open" : "enforced"`, a spelling that normalises and **silently collapses anything it does not recognise** into `enforced`. That is right for garbage - the gate must fail closed - and wrong for a value the system has since learned about: `AdminView.loadAssignmentIntoForm` used exactly that ternary, so opening an `org_member` assignment rewrote it to `enforced` on load and `buildDoc` saved the rewrite back, silently converting a membership-gated cohort into one gated on an empty roster. Same shape as `buildDoc` deleting invitation tokens. `normalizeRosterMode` is now shared by `accept.mjs`, `pages/generate.mjs`, `AdminView`, `AssignmentView`, `StudentDiagnosticsModal`, `lib/seed-teams.mjs` and `lib/promote-roster.mjs`, and **every `!== "open"` guard became `=== "enforced"`** - those guards all meant "the roster is the gate", which is true of exactly one mode; leaving them would have told an `org_member` student they were not on a roster that does not govern them, and warned a lecturer that seeded students "will be rejected" when they will not. The fail-closed test now asserts the **behaviour** (junk in, `enforced` out) rather than grepping `accept.mjs` for the literal ternary, which pinned a spelling and went red the moment the rule was shared.
- **An org's base repository permission is a floor under lockdown, and nothing was watching it.** `default_repository_permission` is what every **org member** gets on every repository, private ones included. It grants students nothing today - `provision.mjs` adds them as repository **collaborators**, not members - which is exactly why nobody looks at it: six of seven readable PXL orgs are `none` and `PXL-CSMobile` sat on `read` from its 2024 creation, a year before this system existed. Two things arm it the moment membership is used for enrolment: GitHub grants the **highest** applicable permission, so a base of `write` sits beneath `lockdown.mjs`'s demotion to `pull` as a floor the freeze cannot go below - the demotion reports success and the student keeps pushing; and it applies to **private** repos, so at `read` every member can read `pxl-classroom-control` - the roster's names, student numbers and institutional emails, plus every report. `baseRepositoryPermissionFinding` in `lib/audit.mjs` is the single judgement (`read` -> warn, `write`/`admin` -> fail), surfaced as diagnostics Tier 1. The load-bearing rule is the **absent** case: the field is returned to org admins only, so a value the caller cannot see yields **no check at all** rather than a green one - the same "unreadable is not evidence" rule Tier 1 already applies to `/apps/{slug}`. `tests/org-base-permission.test.mjs`, RUNBOOK §11.
- **A git worktree is a full second checkout, and the repo-wide scanners walked into it.** `.claude/worktrees/` holds them, so every "nothing re-implements this rule" guard found the worktree's copy of the module and reported it as a fork, and `eslint .` linted every file twice under the wrong config (the per-directory overrides are anchored at the repo root, so `acceptance/accept.mjs` came back as `'process' is not defined`). CI never has a worktree, so this is a purely local red - which is worse, not better: `npm run lint` is the command CLAUDE.md tells you to trust, and a suite that goes red because a sibling checkout exists trains people to ignore red. `.claude` is now in `eslint.config.mjs`'s `ignores` and in the skip list of all six directory scanners (`deadline-countdown`, `effective-deadline`, `check-run-score`, `scripts-inventory`, `vue-route-safety`, `workflow-dispatch-contract`) - six copies of that list, which is its own small fork waiting to happen.
- **Declaring a permission is not being granted it, and nothing could tell you which orgs had granted it.** Widening the App leaves every existing installation on the **old** set until that org's owner clicks *Review request*, so `check-app-declaration.mjs` passes, `GET /apps/{slug}` shows the new permission, and the feature is dead on the orgs nobody chased - with nothing red anywhere. `GET /orgs/{org}/installations` answers only for an owner **of that org**, so verification by hand stalls exactly where it matters: on the 2026-08-25 `members` + `organization_administration: write` rollout, 7 of 11 orgs could be confirmed and **4 could not be seen at all**. `scripts/check-installation-approvals.mjs` walks `GET /app/installations` - every org in one call, App JWT only, hence `environment: provisioning` on the `installation-approvals` job in `weekly-usage-report.yml`. Load-bearing details: it compares against the **App's own live declaration** (`GET /app`, read as the App so no slug can name a different one) rather than `MANIFEST_APP_PERMISSIONS`, because the question is "has this org accepted what the App asks for *today*" and a constant bumped first would paint every org amber for a permission nobody had been asked to approve yet; the comparison is `permissionMeetsRequirement`, not equality, or a **downgrade** (`read` where `write` is declared - the actual 2026-08-25 case) reads as approved; it **walks past page 1**, because "every org has approved" off the first 100 installations is a confident all-clear from a truncated read; and a missing credential, an unreadable API or a non-array body prints **`DID NOT RUN`** and exits 0 rather than a false all-clear - a check that quietly does not run looks exactly like a passing one. `lib/app-jwt.mjs` holds the one JWT minter, extracted from `scripts/fetch-pages-data.mjs` the moment a second caller needed it: two copies of a signing routine drift into an intermittently invalid credential rather than a visible error. **Not every installation is ours.** The App is publicly *listed* - hub-and-spoke requires it, because each course org is a separate organization and a private App installs only on the account that owns it, so making it private would uninstall it everywhere - which means any GitHub account can install it, and an unrelated org did on 2026-08-22. The check therefore sorts installations three ways against `participating-orgs.yml`: a participating org that has not approved **fails**, a participating org with **no installation** fails (nothing else in the system notices, and RUNBOOK §11 carried it as a manual checklist item), and a third-party installation is **named as a notice but never fails** - a permanent false positive beside the real ones is how a weekly check stops being read. Two distinctions it must keep: an **empty** `orgs:` list is an answer, not an unreadable file (the branch really does start `orgs: []`, and conflating them makes every installation third-party and silences every real gap), and an **unreadable** list treats everything as participating - over-reporting, never silencing. Matching is case-insensitive but reporting uses the file's own spelling, or a lecturer is sent looking for an org that as spelled does not exist. `tests/installation-approvals.test.mjs`, RUNBOOK §10.6.
- **No value is composed into a script, anywhere.** `${{ }}` is substituted into the script *text* before bash or the JS parser sees it, so the rule is not "is this value attacker-reachable" but "is this a literal I wrote". Everything else goes through `env:`. The old guard named only `github.event.*` and `client_payload`, and sixteen sites survived it - `gh api users/${{ inputs.github_login }}` in `retry-acceptance.yml` (a job holding the App key that provisions for an arbitrary login with the deadline bypassed) and `setup-org.yml` putting an **installation token and a dispatch input into the same line**, with the org validated in the *next* step. `tests/broker-injection.test.mjs`'s `isConstant` now allowlists only run-scoped facts GitHub sets itself (`github.repository`, `github.run_id`, `runner.*`, `env.*`, literals) and covers composite `action.yml` files too. `retry-acceptance.yml` and `setup-org.yml` validate their inputs as their first use, and `setup-org.yml` passes credentials via `http.https://github.com/.extraheader` rather than embedding them in a remote URL.
- **The team hint is a lock, not a label.** The acceptance concurrency group is keyed on `client_payload.team_hint`, derived from the issue *title*, because that is all the hub has before it can read the body - and per-team serialization is the only thing guarding `max_team_size` (§5.8). Nothing compared the two, so a title saying `team:decoy` with a body saying `team_slug: popular-team` serialized against one team and wrote to another; two in parallel both read the target at n-1 and both appended. `lib/team-payload.mjs`'s `teamHintMatches` refuses a mismatch, `acceptance-handler.yml` passes `TEAM_HINT`, and both-empty is the individual case.
- **Nonce revocation fails closed.** `verifyInviteToken` used `if (nonce && ...)`, so a broker with no `INVITE_NONCE` variable accepted **every token ever issued** for that assignment, including ones a `regenerate_invite` had just retired - and a publish that died between creating the repo and setting its variables produced exactly that. An absent nonce is now `reason: "no-nonce"`, and `scripts/verify-invite-token.mjs` names it as a deployment fault distinct from a forged token. The value is also **trimmed**: it comes from a repository variable a human can edit, and a trailing newline superseded every live link behind a deliberately generic student-facing message. `tests/invite-nonce-revocation.test.mjs`.
- **No attacker-controlled text may reach a shell on a broker.** A broker is public, holds `PXL_APP_PRIVATE_KEY` as a repo secret, and has issues enabled - so any GitHub account can fire its workflow. `BODY="${{ github.event.issue.body }}"` in a `run:` block there was arbitrary code execution against the App key, reachable by anyone, against every participating org (ARCHITECTURE §4.3.1). `${{ }}` is substituted into script *text*; `env:` is not. `tests/broker-injection.test.mjs` enforces three things: no workflow interpolates `github.event.*`/`client_payload` into any `run:` or `github-script` body (repo-wide, not just the broker); the broker never reads the issue *body* (it forwards the issue number, and `scripts/read-team-payload.mjs` validates it in the hub via `lib/team-payload.mjs`, with no `client_payload` fallback left in `acceptance/action.yml`); and the broker reads the issue *title* only through `env:`, only to match `^team:<slug>$`, and only as `client_payload.team_hint` - a **concurrency key**, never an authoritative value. The hint cannot be dropped: the concurrency group is evaluated at dispatch time, before the body can be read, and per-team serialization is what guards team capacity without a distributed lock.
- **Signed invitations are what stop outsiders triggering work.** Acceptance fires on a public event on a public repo, so anyone can ring the doorbell - star, fork, issue, comment, wiki edit are all open to any account, and none prove authorization. The roster gate authorizes, but only *after* the broker minted an App token and the hub cloned the private control repo. `lib/invite-token.mjs` (Node) + `lib/invite-token-format.mjs` (isomorphic, crypto-free, bundled by the SPA) move the first check to the edge: the broker checks out the public hub, verifies an Ed25519 signature against `acceptance/invite-keys.json`, and only then mints. **Asymmetric because the verifier is public** - an HMAC would put the minting secret on every broker; encryption is wrong too, since the broker cannot hold a decryption key and ciphertext replays fine on a public channel. The token rides in the issue **title** (122 chars, budget 256) so the broker never reads the body. `vars.INVITE_ENABLED` and the `pxl-accept:` prefix are job-level `if` checks, evaluated before a runner is allocated. `tests/invite-token.test.mjs` pins that no step before verification references a secret, plus canonical encoding (26 and 64 bytes do not divide into 6-bit groups, so the last char of each part carries discardable bits - without the check one link had several spellings). The token is **not** secret against sharing: that risk is accepted and bounded by `max_acceptances` (ARCHITECTURE §15). It must never reach Pages output. Republish reuses the nonce so live links survive a repair; `regenerate_invite: true` rotates it and retires them. `INVITE_KID` rotates keys. See ARCHITECTURE §4.3.2, RUNBOOK §1.3.1.
- **A closed issue on a public repo hides nothing.** The acceptance issue's TITLE carries the signed invitation, so the first student to accept used to publish the assignment's token to anyone who looked at the broker's issue list or searched GitHub for `pxl-accept:` - defeating §4.3.2 outright and, because the acceptance card is named `sha256(invite_token)`, making the card and its teams file public too. Three steps close it and none is optional: the **broker redacts the title** on *both* the accepted and the rejected path (`gh issue edit --title`, `issues: write` only, so no extra credential on a public repo - the reject path matters because `wrong-assignment` means a *live* token for another assignment landed there); and **System Health Tier 4 sweeps** the broker for surviving `pxl-accept:` titles, which is what catches an `INVITE_ENABLED=false` that skips cleanup or a dead run. The sweep runs even when the assignment's own `invite_token` is absent or malformed. **The third step - the hub deleting the issue - was removed: an installation token cannot delete an issue at all, see the bullet below.** `tests/invite-exposure.test.mjs` pins what remains.
- **Redaction, deletion and a sweep are all AFTER the fact - the fix was to stop publishing a credential.** The three steps above hide the browsable copy of the title; they cannot touch the `opened` event, which GitHub emits before any of them run and GH Archive mirrors permanently. Measured 2026-08-25: `curl -s https://api.github.com/repos/<org>/<broker>/events`, unauthenticated, returned a full still-valid `pxl-accept:` token on an issue that had **already been deleted**, for a live `roster_mode: open` assignment. Hiding it is not available - every student-initiated trigger on a public repo emits a public event and there is no private transport without self-hosting - so the title had to stop being *sufficient*. The link now carries a **P-256 private key** (`invite_key`, 184 base64url chars, `lib/acceptance-signature.mjs`), the browser signs an assertion naming the student's own account, and both the broker and the hub compare the signed `github_id` to the issue's author. **P-256, not Ed25519**: Ed25519 only reached WebCrypto in Chrome in May 2026, so one student in five could not have signed at all. Load-bearing consequences: **`linkSecretFrom` is the single answer to "which field is the link"** (`invite_key` migrated, `invite_token` not) and is consumed by `pages/generate.mjs`, `AdminView`, `InvitationShare`, `lib/diagnostics.mjs` and the e2e fixture - three independent readers is the shape that forked `diffRosters`; the broker takes the signed path only when it has **both** a title and `INVITE_PUBKEY`, so republishing a broker before a keypair exists cannot reject a whole cohort; and **`PUBLIC_TEXT_RULES` gained a second rule**, because the first is keyed on the token's `<35>.<86>` shape and could not see a key at all - it anchors on the PKCS#8 P-256 header (36 chars, identical in every key ever minted, so a partial paste is caught too) and deliberately does **not** match the public half, which lives on a public broker by design and would be a permanent false positive beside the real findings. `tests/acceptance-signature.test.mjs`, `tests/public-text-token-shape.test.mjs`, ARCHITECTURE §4.3.2.
- **The team hint is appended AFTER signing, so the verifier has to cut it off - and for months it did not.** `verifyAcceptanceTitle` split `github.event.issue.title` on `.`, which handed the signature back as `<signature> team:alpha` - not base64url - so **every group acceptance on the signed path was rejected as `malformed`**, on every group assignment, while individual acceptance worked perfectly. Nothing caught it: not one test had ever verified a title carrying a hint, and the e2e fixture's mocked broker returned 201 for any string at all. The fix is `split(/\s/)[0]`, the same cut the broker's own bash regex makes; trailing content is **ignored rather than refused**, because the hint is a concurrency key and never an authoritative value (§5.8). The lasting change is the fixture: **the mocked broker now runs the real verifier**, so any spec that accepts proves the SPA→broker seam, and `tests/e2e/44-signed-acceptance.spec.mjs` asserts on the verdicts. A mocked dependency that accepts everything tests nothing.
- **The acceptance payload is binary because the JSON one did not fit.** It carried the assignment id verbatim plus a full ISO-8601 `issuedAt`, and a real id - `2526-automation-scripting-practicum-exam-2` - produced a **253-character** title before any team hint was appended, so a group acceptance threw at the accept button for a reason the lecturer chose months earlier when naming the assignment. It is now 19 bytes (version, 8 bytes of `sha256(id)`, a 48-bit account id, a 4-byte nonce) = 26 base64url chars, giving 127/143/197-character titles measured live. **`issuedAt` is deleted**, not shortened: `verifyAcceptanceTitle` documented it as never enforced, so it was 32 characters of dead data. Hashing the subject is what makes the title's length independent of the id, and it keeps `wrong-assignment` meaningful - a broker holding the wrong `INVITE_PUBKEY` is a real deployment fault (RUNBOOK §1.3.2) and must not read as `bad-signature`. **The budget is 256 and it is OURS**: measured 2026-08-26, GitHub accepts a 1024-character title and refuses 1025, while its own 422 says "maximum is 256" - building on the enforced number would mean building on what GitHub's validator calls invalid. Titles round-trip byte-identically (whitespace and tabs included), which had to be measured, because verification compares bytes.
- **Who accepted is ONE field: `github.event.issue.user`.** The broker verified the signature against `issue.user.id`, validated `github.actor` and `github.event.sender.id`, and dispatched *those* to the hub - so the account we checked and the account we provision for were two different readings of the same event. They agree for a freshly opened issue, which is exactly what makes the split dangerous; an issue opened through an App on a user's behalf reports the App as `sender` and the user as `issue.user`. The verified id was also computed as a step output and thrown away. One field now decides who signed, who is validated, who is dispatched and how the run is serialised. Related: **the hub does NOT re-check the signer and cannot** - the dispatch carries a login and an id, never the title - and a comment claiming it did was worse than the gap, because it invites the broker's check to be relaxed on the strength of a second one that does not exist. `tests/acceptance-identity.test.mjs`.
- **`injectAuth` stored a session shape GitHub cannot produce.** It wrote `{login, name, email}` while `auth.js` persists `{login, id, name, email}`, and `getUser()` reads the stored object rather than re-fetching - so **every e2e acceptance signed with `githubId: undefined`**. The old payload turned that into `"g": null` and the mocked broker took it, so the suite stayed green over a title production would refuse. Personas now carry distinct ids (the anti-replay property is "is this the account that signed", which a shared id makes untestable) and `personaId(login)` fills one in for the many specs that build a user inline - `'id' in user` rather than `??`, so a spec can still test the absent case deliberately. The SPA now refuses to sign without an id and says *"your GitHub account id is missing from this session"* rather than letting the crypto's "not base64url" reach a student as if their link were broken.
- **A leftover `pxl-accept:` title means two different things, and the advice differs.** Tier 4's exposure sweep said "still carry this assignment's invitation token... the link is effectively public... regenerate the invitation" for *any* leftover. On a **migrated** assignment that is false and the advice is actively harmful: the title is a signature naming one account, useless to anyone else, and regenerating retires every student's link to fix nothing. It is a `warn` there, pointing at the acceptance-handler run for the actual reason and saying explicitly **not** to regenerate; it stays a `fail` on the old format, where the title *is* the credential. Same rule as everywhere else here - do not describe a risk the system does not have.
- **The hub CANNOT delete the trigger issue, and never could - the step is gone.** `deleteIssue` refuses an App installation token outright: measured live 2026-08-26, twice, in two organizations, `{"type":"FORBIDDEN","path":["deleteIssue"],"message":"Viewer not authorized to delete"}`. **It is not a permission.** Both orgs grant the App `administration: write`; the same installation token had read that very issue two steps earlier; and in the publish run that created the broker the same token created the repository and wrote its secrets and variables, all admin-level. A **user** token with repository admin deletes it immediately. GitHub documents this nowhere - the mutation's schema description is "Deletes an Issue object.", and neither the permissions reference nor the GraphQL limitations page mentions it - but its community answer for the identical error on `GITHUB_TOKEN` (also an installation token) is "use a personal access token". The system holds no PAT by design, and adding a long-lived user credential to the hub to tidy a public issue trades §4.3.4 away for housekeeping. So the step had **never once succeeded** while warning on every acceptance that an org should grant a permission it already had - which is worse than the gap, because it is a control the docs claimed and the system did not have (C4). Redaction on the broker is the mitigation, and after §4.3.2 the title is a signature naming one account rather than a credential. Tier 4's sweep is unaffected: it fires on titles that were never **redacted**, which is the signal that means something. `tests/invite-exposure.test.mjs` now fails if anything calls `deleteIssue` again.
- **The failed-deletion warning asserted a cause and threw the evidence away.** `acceptance-handler.yml` ran `deleteIssue` with `2>/dev/null` and, on failure, printed "deleteIssue needs Administration: write on the organization". Measured live 2026-08-26 during a full end-to-end run: **that is false**. `PXLAutomation` grants the App `administration: write` (9 of the 12 participating orgs do, and 3 are unreadable to a non-owner), the same installation token had just read the issue body two steps earlier, and the mutation succeeds against `deleteIssue` with a user token holding repository admin. So the real cause is still unknown - and was unknowable, because the one line anybody reads was a guess and the error was discarded. It now captures GitHub's own message (truncated to 300 chars; Actions masks registered secrets in annotations) and stops diagnosing. The same wording had propagated into ARCHITECTURE §4.3.2, RUNBOOK §1.3.1 and the Tier 4 sweep, sending a lecturer to approve a permission they already had.
- **A secondary lookup may not take the assignment page down.** `checkExistingState` and `checkRosterStatus` ran inside the acceptance card's own `try`, so one rejected request - an aborted `/user/repository_invitations` is enough - replaced a perfectly well-loaded assignment with *"Couldn't load the assignment data. Check your connection"*, about data already in hand. They are isolated now and swallowed, because the honest fallback **is** the default view: not knowing whether a student already has a repository shows them Accept, and accepting again is idempotent. Same rule as the tracking page never replacing itself with an empty state. Two more from the same hook: `checkExistingState` was called **twice** on every page load (once by `loadAssignment`, once by `onMounted`), measurably doubling both of a student's lookups for no new information; and the interval driving the deadline countdown sat *after* two unguarded awaits, so any rejection froze it and left an unhandled error in a console nobody reads - it starts first now, and nothing above it can stop it.
- **A pre-migration link must NOT be signed, and nothing was stopping it.** `signedAcceptanceIssueTitle` signed whatever secret the URL carried. A link handed out before the change carries a 122-character bearer token, `fromBase64Url` rejects its `.` separator, and the accept button renders **"not base64url"** to the student - so the deploy that shipped signing would have broken acceptance for **every live assignment at once**, since none had a keypair yet. Found by running the thing, not by reading it. Those assignments' brokers still verify the old way, so the old title is the **correct** output there, not a fallback: `signedAcceptanceIssueTitle` branches on the wire shape (`TOKEN_PATTERN`), and `acceptanceIssueTitle` stays until no live assignment is on the old form. The team hint has to survive that branch - it is the acceptance concurrency key, and dropping it lets two joins read the same count (§5.8).
- **Rotation retires a link too, and only migration was covered.** `regenerate_invite` mints a fresh keypair - the answer to a leaked link, and the *recurring* case, where migration happens once. The old key is gone from the document, so the "a secret the document still carries" rule below cannot see it, and the prune deleted its card: a rotated-away link landed on the not-found page, whose only honest wording is a guess between three causes. The fix needs **no record of retired secrets** (a list of them on the assignment is one more field `buildDoc` could silently drop): the orphaned card **names its own assignment**, so `pruneStalePublicFiles` converts it into a marker rather than deleting it, whenever that assignment is still being published. Three rules it must keep: a `.teams.json` at a retired digest is **pruned, never retired**, or a superseded link could still fetch the cohort list; a marker is **pruned once its assignment is gone**, or every rotation leaves a file behind for ever; and retiring is **idempotent**, because `regenerate-dashboard` runs on every acceptance and a marker rewritten or dropped on the second pass is a link that worked once. `tests/superseded-invitation.test.mjs`.
- **A retired link resolves to a page that says so, and the two diagnostics for it are different checks.** Migration and rotation both take working links out of students' hands. `pages/generate.mjs` therefore writes a second card at the digest of **a secret the document still carries that is no longer the link** - phrased that way rather than as "has both fields", so it tracks `linkSecretFrom` instead of restating it: on an **unmigrated** assignment the token *is* the link, and a both-fields test would replace that cohort's only working card with a tombstone. The marker carries `{superseded, assignment_id, title, organization}` and deliberately **no `assignment` key**, so a browser on a cached build falls through to its own not-found state rather than rendering half an assignment with an Accept button; it must also be registered in `expectedInviteFiles` or the prune deletes it on the same run that writes it. Without it the student lands on the not-found page, whose only honest wording is a guess between three causes - **a page may not guess why it is stuck**, the same rule as the provisioning wait screen. The lecturer's half is the Admin Panel warning on the one republish that cannot preserve links, because two pieces of copy promise the opposite (C4). And **System Health Tier 4 had to be split**: `linkSecretFrom` was swapped in without teaching the parse the new shape, so `parseToken` saw a 184-char key, returned null, and the engine reported "invite_token is malformed, republish to mint a valid one" over a working link *and then returned*, taking the nonce, the switch and the exposure sweep with it. A migrated assignment is checked on `invite_key`'s shape and on the broker's **`INVITE_PUBKEY` matching the assignment's own public half** - the one agreement the signed path actually rests on, previously checked nowhere, and a republished broker sends no legacy token so a missing key does not degrade, it rejects everyone in silence. Its `INVITE_NONCE` is **not** judged: the signed path never reads it, and reporting a failure the system does not have is how a health panel stops being read. `tests/superseded-invitation.test.mjs`, `tests/diagnostics-invitations.test.mjs`, `tests/e2e/43-superseded-link.spec.mjs`, RUNBOOK §1.3.2.
- **Public Pages artifacts disclose only what the student portal needs.** The acceptance card lives at `data/<org>/i/<sha256(invite_token)>.json` (teams beside it as `<sha256>.teams.json`), so finding it requires the link, a leaked filename is not a working token, and the teams file stops being a public cohort list of member logins. `assignments.json` survives reduced to id/title/organization/opens_at/deadline_at/timezone/repository_name_pattern/assignment_type/state, for one reason: the `/` portal matches a student's own repos against assignments and **students cannot read the control repo**. Broker repo, roster mode, cap, accepted count, description and group config are on the card only. `pages/scan.mjs` fails the publish on anything matching the token wire shape; `tests/public-data-contract.test.mjs` pins both halves. `index.html` sets `referrer: no-referrer` because the token is in the URL path. Residual, accepted: titles and deadlines stay enumerable - after §4.3.2 that grants nothing. In e2e fixtures `inviteToken()` must stay **pure** - a `Date.now()`-derived expiry is encoded at minute granularity, so the spec and the route mock straddling a minute boundary mint different tokens and 404 the card (flaked ~1 run in 4).
- **Hub credentials only run from `main`.** `workflow_dispatch` runs the workflow file from whatever ref it is given, and `participating-orgs` has deliberately lighter protection (ARCHITECTURE §5.5) - together a way to run hub code at a chosen ref with the App key in scope. Every job referencing `PXL_APP_PRIVATE_KEY` or `PXL_INVITE_SIGNING_KEY` therefore declares `environment: provisioning`, whose deployment branch policy is `main` only; a job naming an environment does not start when the ref is outside the policy, so this holds regardless of where the secret lives. `setup-org.yml`, `retry-acceptance.yml` and `publish-assignment.yml` additionally reject a `workflow_dispatch` from a `[bot]` actor as their FIRST step - lecturers dispatch as themselves, a stolen broker credential arrives as `<slug>[bot]`. Never put these secrets in workflow-level or job-level `env:`. Both keys are **environment** secrets with no repository-level copy, so a job that omits `environment: provisioning` cannot read them at all; `PXL_APP_CLIENT_ID` stays a repo secret because a client id is public by design. `tests/workflow-hardening.test.mjs` enforces all three. See ARCHITECTURE §4.3.4.
- **A rejection is an outcome, not a failure.** `accept.mjs` splits `reject()` (exit **0**, `rejected:*`) from `fail()` (exit **1**, `fail:*`). A student who is not on the roster, or arrives after the deadline, is the system working - painting the hub's Actions tab red for that teaches people to ignore red runs and buries real failures beside them. The outcome string still gates every downstream step, and `acceptance-handler.yml` routes rejections to the org's instructor tracking issue via `./notify` (`event-type: acceptance-rejected`, deduped per assignment+login+reason) - previously a rejection wrote nothing anywhere and the lecturer of that org had no way to see it. `tests/accept.test.mjs` pins both exit codes.
- **A restricted GitHub account fails invisibly.** GitHub returns HTTP 201 for an issue opened by an account it has flagged, then removes the content seconds later; no webhook fires, so the broker never runs. Observed live. `AssignmentView` records the acceptance issue number and, when polling gives up, re-reads it: gone means `blocked-account` ("GitHub is blocking your request"), not `timeout` ("GitHub is under load"). Check at timeout, never right after creation - the removal is not immediate.
- **System Health must check the invitation chain, not just the broker.** Four things have to agree before a student can accept, and every mismatch fails silently: the assignment holds an `invite_token`, the hub publishes the `kid` it was signed with (`acceptance/invite-keys.json`), the broker's `INVITE_NONCE` matches the token's, and `INVITE_ENABLED` is not `false`. Tier 4 checks all four; Tier 5 checks the acceptance card at `public/i/<sha256(token)>.json` - it previously only checked that the id was in `assignments.json`, which stayed true while the student's page 404'd. The checks stay silent for an unsaved Admin Panel form (`formDoc`), which never carries a token. `tests/diagnostics-invitations.test.mjs` proves each one FAILS when it should.
- **The Admin Panel rebuilds the whole assignment on save.** `buildDoc` constructs the YAML field by field, so anything it does not carry through is deleted - and the document still validates, because the invite fields are optional. Editing a published assignment therefore used to wipe its `invite_token` and silently retire every student's link. `buildDoc` and the edit-load path must both carry `invite_token`, `invite_nonce` and `invite_expires_at`; `tests/admin-lifecycle-ui.test.mjs` pins both halves.
- **One reader for the invitation, and it is the writer's.** `INVITE_FIELDS`, `readInviteField`, `parseInviteFields` and `quoteInviteValue` live in `lib/invite-token-format.mjs` beside the wire format, and are used by `scripts/set-assignment-invite.mjs` (writer), `AdminView.verifyLiveInfrastructure` and `AssignmentDetailView.loadInviteToken` (readers). The module stays **dependency-free** - `lib/invite-token.mjs` imports it and the broker runs that with no `npm ci` - so the parse is line-based regex, not a YAML round trip. Three consequences that are load-bearing: **`getRepoContent` resolves to decoded FILE TEXT, not a `{ok, data}` envelope** (both invitation read paths asked a string for `.ok`, so neither ever ran - and the test written to catch it grepped for the error message, which passed *because* the code always took the error branch); **`invite_nonce` is written quoted**, because ~1 nonce in 600 is all-digits-with-a-leading-zero and round-trips through a YAML parser as an integer, failing the hub's `^[0-9a-f]{8}$` check and silently retiring every live link on the next republish; and **`verifyLiveInfrastructure` re-reads unconditionally**, never gated on the form lacking a token, or a regenerated invitation never reaches the panel. `startPublishWatch` must call it on **both** terminal branches (`ready` and `timeout`) - the token is minted while the watcher polls, so without that the success banner says "verified live" over an empty link box. `tests/invitation-link-surface.test.mjs` runs the real round trip and flags any `getRepoContent` binding used as a response.
- **A `python` autograde test is its `script`, on every runner.** `provision.mjs` emitted `command: t.command || "pytest"` and never read `script`, while `runner-host.mjs` and `runner-docker.mjs` both write `script` to `t.py` and run it and ignore `command` - and the Admin Panel only ever writes `script`. So one test definition ran the lecturer's code locally and the *student repository's own* pytest suite on Actions, with no error on either side. The generated workflow now writes the script to `.pxl-autograde/<test-id>.py` and runs `python3` over it, the schema **requires `script` when `type: python`** (`allOf`/`if`/`then`, as `roster_mode: open` requires a cap) so there is no second field left to disagree about, and `setup_command` - read here, never a schema field under `additionalProperties: false` - is gone. The script reaches the file through **`env:`**, never composed into the `run:` text: that is the string-concatenation bug below, one layer down. `AdminView.fieldErrors` refuses a scriptless python test at authoring time *and renders the message* - an error that only blocks Save is a disabled button with no explanation. `tests/sweep-correctness.test.mjs` pins that the generator and both CLI runners agree on the authoritative field; its slice of the generator is bounded at the next `} else {`, because the command-grader branch below it satisfies the same assertion.
- **Automated checks are a task, not a config language.** The assignment form showed an *Enable autograding* checkbox that opened a type dropdown and four unlabelled textareas whose meaning changed with it - no headers, no totals, no validation until the schema refused the save three commits later, and a visibility control named after its mechanism (*"Private (Hidden via reusable workflow)"*) rather than after the decision. The form is one summary line now (`Off` / `3 checks · run on your machine` / `2 checks · run in student repos, hidden`); `AutogradeModal.vue` owns the rest. **`autograde_enabled` is no longer a checkbox - the configuration's existence is the flag**, which is why `loadAssignmentIntoForm` loads `enabled: true` with zero checks *as off*: `tests.minItems: 1` makes that document unsaveable, and preserving it would trap a lecturer behind an error with no control to fix it. `frontend/src/lib/autograde.js` is the pure shared half (presets, per-row problems, `cleanChecks`, the summary line) so `tests/autograde-modal.test.mjs` can run the real presets through the real schema instead of asserting that a template contains a string. Load-bearing: **a preset arrives pre-filled and valid** (a row plus a type dropdown is the config language this replaced); **duplicate ids are refused**, because two checks with one id collide as workflow step ids; and **zero checks cannot be saved** - *Turn off automated checks* is the other button. `provision.mjs`'s `visibility: public` + zero-tests path no longer emits a hardcoded `npm test`: guessing a student's toolchain and reporting the result as this assignment's grade is worse than a red run that says why. - **One page is not the list.** A GitHub list endpoint answers with a page; reading it and then making a statement about the whole collection is a confident claim off a truncated read - the call *succeeds*, so no error path fires and no fallback runs. The merge that did work carried the **whole template tree** (making the file selection decorative) and grafted the template's entire history in. `tests/sync-starter.test.mjs` missed all of it by building its students with `git clone` of the template - shared history, which real provisioning never produces. `lib/starter-sync.mjs` is the pure planner (no fetch, no fs) shared by `scripts/sync-starter.mjs`, `cli/src/commands/sync-starter.mjs` and `StarterSyncModal.vue`'s pre-flight, so the modal's preview and the workflow's behaviour cannot drift. It compares **blob SHAs** across three trees - template at the commit, template at its parent, student's `main`, each one `GET /git/trees/{ref}?recursive=1` - because a git blob SHA is a content address and is identical in every repository holding the same bytes: matching `head` is done, matching `base` means untouched, anything else is the student's. Load-bearing: the split is **per file**, not per student (hence the `merged-and-pr` outcome - one edited file must not hold back three other corrections), the PR branch is cut from the **student's own** `main` so no foreign SHA is involved, writes go through `lib/gittree.mjs` in one commit, and **`selected_files` is now applied** - it used to be recorded in the sync record and pasted into the PR body while the merge carried the entire template HEAD regardless, so the modal said "Files to Synchronize (1/1)" over an operation syncing everything (C4). A truncated tree listing **fails** rather than reading as "the student deleted everything", and a commit touching >300 files says so rather than silently offering GitHub's first 300. **Re-running adopts rather than duplicates**: each sync PR carries `<!-- pxl-starter-sync: <templateSha> -->` and a later run of the same sync reuses it - without that, a live rehearsal's second run opened a *second* PR (`#1` then `#3`) in the same repo, and re-running is exactly what a lecturer does when a sync looks like it did nothing. The open-PR list is walked in full, because a missed marker is a duplicate rather than a visible error. The unit is **one template commit** because the use case is "I need to correct a mistake in the assignment" - which also means a lecturer who solved the exercises in the template will sync their solution; RUNBOOK §12.10 says so.
- **The autograding score is in the check run's ANNOTATIONS.** `AssignmentDetailView.vue` and `cli/src/commands/grade.mjs` each held a byte-identical private parser searching `output.title/summary/text` for `Points X/Y`. Verified live 2026-08-25 against `classroom-resources/autograding-grading-reporter@v1`: an Actions-created check run has `output.title === null`, `output.summary === null` and `annotations_count: 4`; the reporter calls `core.notice()`, so `Points 0/170` and `{"totalPoints":0,"maxPoints":170}` are **annotations**, from `GET /repos/{o}/{r}/check-runs/{id}/annotations`, which nothing fetched. So every parse fell through to "green means full marks, anything else means zero" - a 15/20 recorded as **0**, and nobody noticed because a fully-green or fully-red run happens to come out right. `lib/check-run-score.mjs` is the one parser (`parseCheckRunScore(run, annotations, fallbackTotal)` - annotations is **required and type-checked**, so a stale positional call fails loudly rather than grading a cohort against `[]`) plus `pickAutogradeCheckRun`; `lib/check-run-annotations.mjs` walks the pages (default page size 30, and a grader emitting a notice per exercise scrolls the score off page one) and returns `complete: false` rather than a short answer dressed up as a whole one. `tests/check-run-score.test.mjs` pins the live shapes and fails if any file outside the module parses a points string.
- **`gh` writes API errors to STDOUT, so a captured value is non-empty on failure.** Measured 2026-08-26: `gh api users/does-not-exist --jq .id` exits 1, puts `{"message":"Not Found",…,"status":"404"}` on **stdout** and only `gh: Not Found (HTTP 404)` on stderr. So `VAR=$(gh …)` followed by `[ -z "$VAR" ]` is not a check, it is a guard that can never fire - `retry-acceptance.yml` had exactly that, and only Actions' default `bash -e` stopped a JSON error blob being written into `$GITHUB_OUTPUT` as a student's account id; what it did cost was the message, so a lecturer who misspelled a login got `gh: Not Found` instead of being told which login. The rule is **guard on the exit code** (`if ! VAR=$(gh …)`, or `|| …`) and then **validate the shape** - `--jq` prints the string `null` for a field GitHub omits, which is non-empty too. `tests/workflow-hardening.test.mjs` fails on any capture that assumes success from the text. This cost three false readings in one session, including reporting five healthy migrations as mismatched and repeating a workflow's own guess back as a diagnosis, so it is worth knowing before writing the next one-off `gh` check.
- **The CI grading sync could never have worked: the App does not declare `checks`.** Reported live 2026-08-26 by a lecturer on `python-hacking-intro` - *"CI results sync failed for 1 student(s) due to API errors. Nothing was saved; try again later."* - with **4,995 of 5,000** API calls still available, which is what ruled out the rate limit the wording implied. Both endpoints the sync uses, `GET /repos/{o}/{r}/commits/{ref}/check-runs` and `GET /repos/{o}/{r}/check-runs/{id}/annotations`, are gated by the **Checks** repository permission (GitHub's "Permissions required for GitHub Apps" reference; the endpoints' own pages document only the classic `repo` scope, which is why this was missable). The Admin Panel authenticates with a **user-to-server** token from the App, and that is capped by what the App declares - so it 403s for every student, in every org, always. `checks: read` is now in `MANIFEST_APP_PERMISSIONS`, which makes `check-app-declaration.mjs` fail until the App owner adds it and each org approves (RUNBOOK §6.7a) - the drift is real and the check is meant to see it. Two rules the fix carries: a **403/401 gets its own sentence** naming the permission, because "try again later" is advice that can never come true and a lecturer will retry for ever; and a student with **no commit on record** is no longer counted as an API failure - `targetSha` was undefined, the URL was built with `undefined` in it, and GitHub's 404 was reported as an API error rather than as "nothing to grade yet".

- **Feedback PR Web & CLI Orchestration:** `AssignmentDetailView.vue` provides 1-click bulk Feedback PR creation for assignments with `feedback_pr: true`, backed by `scripts/open-feedback-prs.mjs` and `open-feedback-prs.yml`, lazily opening draft PRs (`main` -> `pxl-baseline`) once students push commits. **The script had never run** (same two faults as the starter sync - see the bullet above) and running it live on 2026-08-25 turned up four more, all now pinned by `tests/open-feedback-prs.test.mjs`: the adopt path listed `state=all` and took `[0]`, so it leant on GitHub's default sort to avoid recording a **closed** PR as the feedback thread - "already exists" can only be an open one, since a closed PR does not block a new one; a `listPrs` that failed or came back empty **fell through recording nothing at all** - not opened, not failed, no record - leaving a student with a feedback PR the control repo never knew about; `created` and `adopted` were one counter called `opened`, while the CLI has always reported them apart ("12 opened" reads very differently when eleven were already there); and a partial failure **exited 0**, so a run that missed four students out of forty showed a green tick. It exits non-zero now, which is exactly why the workflow's commit step is `if: always()` - the records for the PRs that *did* open are already on disk, and abandoning them makes the next run rediscover every one through the adopt path. **And the SPA does not dispatch that workflow - it opens the PRs client-side**, so it was a third implementation and the worst of the three: **no adopt path at all** (a `422 already exists` was counted as a plain failure, so a student whose record had lost its PR number was reported broken on every run and never recorded), **one `commitFile()` per student** (200 commits on a 200-student cohort against a ~80 writes/min secondary limit - the arithmetic that made team seeding use `gittree`; it is one `commitFiles()` now), and a **failed record write swallowed into `console.warn`** while the toast said "Successfully opened N", leaving the PRs on GitHub and the dashboard permanently disagreeing. `lib/feedback-pr.mjs` now owns the 422 classification (`isAlreadyExists` / `isNoCommitsBetween` - the same status carries "already exists", "No commits between" and "drafts not supported", so the message is the only thing that tells them apart) plus the title and body, and all three import it. `tests/open-feedback-prs.test.mjs` fails if any of them re-implements the test; every assertion in it was checked against the pre-fix sources to confirm it fires.
