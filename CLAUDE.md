# CLAUDE.md

Working conventions for this repo (`PXL-Digital-Application-Samples/pxl-classroom`).

## Git
- **No pull requests.** Commit and push directly to `main`. Never open a PR, never branch "to be safe."
- End commit messages with the standard `Co-Authored-By` trailer.

## Working style
- Be terse and concrete. Do things rather than explain them; give exact values/clicks when the user must act.
- Don't ask for command approval - permissions are set to bypass in `.claude/settings.local.json`.
- **No backticks in a double-quoted `git commit -m`.** The shell runs them as command substitution *before* git sees the string, so the quoted code fragment vanishes silently and the commit lands with a hole in it - `437dda0` lost three of them from one paragraph and `main` blocks force-push (RUNBOOK §1.5), so it cannot be amended. Use single quotes for any `-m` containing backticks, `$`, or `!`. Same family as the heredoc rule below: the shell processes the text before the tool does.
- **NEVER edit a file through a shell heredoc.** No `python3 - <<'EOF'`, no `cat > file <<'EOF'`, no `node -e`. Use the **Edit** tool for targeted replacements and **Write** for whole files. The shell and the interpreter both process escapes before the code runs, so regexes and string literals are silently mangled - `[^\n]*` becomes a literal newline, `\.` loses its backslash, `\s` and `\$` raise SyntaxWarnings. It has produced broken code in this repo many times over. If a scripted transform is genuinely unavoidable (a repo-wide sweep), **Write** the script to a real file, run it, then delete it. Bash remains correct for reading, searching, git, and running tests.

## Linting
- **`npm run lint` is the only lint command, and CI runs exactly it.** It was `eslint .` while CI's `test` job ran `eslint . --max-warnings 0` and CI's `lint` job ran `actionlint` + `scripts/workflow-lint.mjs` with no local equivalent - so a change could be linted clean locally, repeatedly, while CI had been red since `48ed831` over a shellcheck finding no local command could produce. Nine commits shipped on top of it. `scripts/lint.mjs` now owns all three checks; `ci.yml` calls `npm run lint` and nothing else. **actionlint and shellcheck are both pinned, fetched the same way** - a versioned release asset downloaded into gitignored `.tools/` on demand, verified against a SHA-256 in `scripts/lint.mjs`, and shellcheck passed explicitly with `-shellcheck`; taking either from the runner image means a different version reports different findings. Neither comes from npm any more (see the `decompress` bullet) and neither is fetched by piping a script from a branch into bash, which is how actionlint used to arrive. A platform with no pinned digest **fails** rather than downloading unverified. A tool that cannot be obtained **fails** the run; there is deliberately no skip flag, since a check that quietly does not run is the whole bug. `tests/lint-parity.test.mjs` fails if CI grows a lint route of its own or the entry point drops a check.
- actionlint runs shellcheck over every workflow `run:` block. A genuine false positive gets `# shellcheck disable=SC<code>` with a comment saying why - e.g. a GraphQL `$id` in single quotes is deliberately unexpanded (SC2016).
- **A `run:` block over 4 KB hangs the linter on Windows, and CI stays green while it does.** actionlint copies each script to shellcheck's **stdin**; a Windows anonymous pipe holds **4096 bytes**, so once the script exceeds that the copy blocks on a full pipe and `Wait()` never returns - no output, no exit, for ever. Linux pipes hold 64 KB, which is why `lint: success` on every CI run throughout. Measured 2026-08-26: `publish-assignment.yml`'s single 92-line *Publish broker* step reached **4106 bytes** and deadlocked; every other block in the repo was under 3 KB, which puts the cliff at 4096 exactly rather than near it. Bumping actionlint does not help (1.7.1 and 1.7.12 both hang). It went unnoticed because a hang looks like work in progress: `91114af` added **seven lines** to that step and shipped with *"local actionlint could not be run to completion"* in its commit message instead of a lint result, and the next session lost an hour to it. Three things now hold: the step is **split in two** (1707 + 2438 bytes) - splitting is platform-neutral, and a Windows-only workaround would reintroduce the exact local-vs-CI drift `scripts/lint.mjs` exists to end; `scripts/lint.mjs` gives every step a **120 s timeout** that names this cause, because a two-minute failure is a diagnosis where an infinite hang is not; and `tests/workflow-hardening.test.mjs` caps every `run:` block at **3500 bytes** in milliseconds, on every platform, covering composite `action.yml` files too. The timeout is the diagnosis, the test is the guard - do not rely on the timeout, and do not raise the cap to fit a block that has outgrown it.

## Canonical documentation
- **`ARCHITECTURE.md`** - full technical specification (topology, trust model, data model, workflows, actions, flows, constraints). This is the single source of truth for *what the system is*.
- **`RUNBOOK.md`** - operational procedures (setup, onboarding, monitoring, edge cases, recovery).
- **`README.md`** - short orientation + links.
- **`LESSONS.md`** - why each rule below exists: what broke, how it was found, what was measured. **Not** a fourth opinion on how the system works - every entry is the story behind one rule in this file, and the rule is the authority. It exists because this file had reached 216 KB, three quarters of it narrative, and was loaded whole into every session: the rules that must be followed were competing for attention with 156 anecdotes. Splitting it keeps every word and makes the rules readable. **ARCHITECTURE.md and RUNBOOK.md describe the system as it IS** - a past incident belongs in LESSONS.md, not in them.
- *Authoritative AI Memory Rule:* when architecture or operational procedure changes, update `ARCHITECTURE.md`, `RUNBOOK.md`, and this file in the same commit. A new rule here gets its story in `LESSONS.md` and a `[Why]` link, in that same commit - a rule whose reason is lost gets argued away by the next person who finds it inconvenient. Do not introduce new top-level planning/progress/review documents - the project no longer uses them, and `LESSONS.md` is not one: it is this file's other half.

## Project facts (load-bearing - read ARCHITECTURE.md for detail)

Each rule below is the whole rule - you can act on it without opening anything else.

### Shape of the system

- **Hub-and-spoke:** all workflows live in the central public `pxl-classroom` hub. Per-org control repos hold data only and contain no workflow files.
- **Minimal-minutes (Wave 8):** synchronous provisioning (no queue), one nightly `daily-activity.yml` cron that disables itself when no assignment is active, event-driven dashboard regen. The system bills zero minutes when idle.
- **Admin Panel is the source of truth for lecturer actions** - assignment YAML and override JSON are generated and committed via the SPA + Contents API. The public Page assignments index is stored in the control repo as `assignments.json` keyed by assignment ID (object format), gathered dynamically by the hub build pipeline using `scripts/fetch-pages-data.mjs` to form the global Page data index. [Why](LESSONS.md#admin-panel-is-the-source-of-truth-for-lecturer-actions)
- **`pxl-classroom` CLI is the parallel lecturer surface** (in `cli/`) - same App, same device-flow auth, same schemas as the SPA. Owns the workflows that scale poorly through clicks: CSV roster import, install audits, feedback-PR orchestration, bulk submission download (merging `_manifest.json` conforming to `download-manifest.schema.json` with fields `{login, archive_sha, archive_branch, archive_branch_url, downloaded_at}` by student login instead of overwriting, resetting remote origin to a tokenless URL). [Why](LESSONS.md#pxl-classroom-cli-is-the-parallel-lecturer-surface)
- **Central GitHub App** is created via the App Manifest form at the SPA's `/setup` route. Frontend deploys automatically via `deploy-frontend.yml` (which aggregates public JSONs from orgs). The manifest includes organization-level `organization_administration` for Enhanced Billing - **`read` is what the code needs, `write` is what it declares**, held deliberately for org-scoped lockdown (see the permission-drift bullet). [Why](LESSONS.md#central-github-app)
- **Scripting Note:** do not use inline `node -e` scripts in workflow YAML. Extract to `scripts/`.
- **Everything specific to one institution is in `deployment.yml`, and it is DATA.** Claim domains, timezone, hub owner/repo, App slug, control-repo name, archive prefix - a fork edits that file and nothing else; the product name *PXL Classroom* is the software, not the deployment, and stays. [Why](LESSONS.md#everything-specific-to-one-institution-is-in-deployment-yml-)
- **One source of truth per cross-surface concern.** `lib/audit.mjs` exports `EXPECTED_APP_PERMISSIONS` and `MANIFEST_APP_PERMISSIONS` consumed by both CLI and `SetupView.vue`; `lib/gittree.mjs` is HTTP-stack-agnostic and shared by CLI, scripts, and SPA; `lib/control-layout.mjs` exports `CONTROL_SCAFFOLD_DIRS` (the ARCHITECTURE.md §5.1 control-repo layout), consumed by `lib/audit.mjs`'s scaffold check, `scripts/scaffold-control-repo.mjs` (called by `setup-org.yml`), and `control-repo-template/`. [Why](LESSONS.md#one-source-of-truth-per-cross-surface-concern)

### Credentials, secrets and workflow safety

- **Sign-in rests on a CORS proxy, and there is no substitute to switch to.** `github.com/login/device/code` and `/login/oauth/access_token` send **no** CORS headers - measured 2026-08-28, a **200** carries zero `access-control-*`, and GitHub's docs say "CORS pre-flight requests (OPTIONS) are not supported at this time" - so a browser can never call them directly and the proxy is structural. [Why](LESSONS.md#sign-in-rests-on-a-cors-proxy-and-there-is-no-substitute-to-)
- **Two entry points run with NO `npm ci`, and a bare import in either graph is a total outage.** `acceptance/broker-workflow.yml` runs `scripts/verify-invite-token.mjs` on a **public** repository holding `PXL_APP_PRIVATE_KEY` - installing dependencies there is supply-chain surface on a credential-bearing public repo, which is why it does not - and `setup-org.yml` runs `scripts/scaffold-control-repo.mjs` before any dependency exists (the reason `lib/control-layout.mjs` is dependency-free). [Why](LESSONS.md#two-entry-points-run-with-no-npm-ci-and-a-bare-import-in-eit)
- **`git add <dir>/` is FATAL when the directory is absent, and CONTROL_SCAFFOLD_DIRS keeps growing.** It exits **128** and stages **nothing** - not even the pathspecs that did match - so under `set -e` the step dies and everything the job already wrote to the checkout is discarded, with a script that succeeded and a red step nobody reads as data loss. [Why](LESSONS.md#git-add-dir-is-fatal-when-the-directory-is-absent-and-contro)
- **A single-org dispatch disabled the nightly for EVERY org, and left nothing red behind.** The minimal-minutes design lets `daily-activity.yml` switch **itself** off when no assignment is active, and only a publish switches it back on - which makes `gh workflow disable` a statement about the whole hub, so only a run that looked at the whole hub may reach it. [Why](LESSONS.md#a-single-org-dispatch-disabled-the-nightly-for-every-org-and)
- **The sentinel's `Finalize now` had never run, and 403'd the first time a deadline reached it.** It dispatches `daily-activity.yml` with the job's own `GITHUB_TOKEN`, and the `watch` job declared no `permissions:` - so it inherited the workflow's `contents: read` and could not dispatch anything (`Resource not accessible by integration`, `x-accepted-github-permissions: actions=write`, run 33013299689). [Why](LESSONS.md#the-sentinel-s-finalize-now-had-never-run-and-403-d-the-firs)
- **Declaring a permission is not being granted it, and nothing could tell you which orgs had granted it.** Widening the App leaves every existing installation on the **old** set until that org's owner clicks *Review request*, so `check-app-declaration.mjs` passes, `GET /apps/{slug}` shows the new permission, and the feature is dead on the orgs nobody chased - with nothing red anywhere. [Why](LESSONS.md#declaring-a-permission-is-not-being-granted-it-and-nothing-c)
- **No value is composed into a script, anywhere.** `${{ }}` is substituted into the script *text* before bash or the JS parser sees it, so the rule is not "is this value attacker-reachable" but "is this a literal I wrote". Everything else goes through `env:`. [Why](LESSONS.md#no-value-is-composed-into-a-script-anywhere)
- **A concurrency group serializes only against the SAME STRING, so two workflows that touch one thing must build it identically.** `acceptance-handler.yml` keys on `team_hint || github_login` and `retry-acceptance.yml` keyed on `github_login` alone. Those coincide for an individual assignment and diverge for a **group** one - so a lecturer's retry and a student's join on the same team ran under different groups, neither waited for the other, and both could read the manifest at n-1 members and `members.push()` past `max_team_size`. [Why](LESSONS.md#a-concurrency-group-serializes-only-against-the-same-string-)
- **The master App key was on ELEVEN PUBLIC REPOSITORIES, and scoping the token never touched it.** `publish-assignment.yml` wrote `PXL_APP_PRIVATE_KEY` as a repo secret onto every `broker-<id>`, and brokers are created `--public` - counted live 2026-08-31, **11 across 8 orgs**. What that key mints, read straight from `GET /apps/pxl-classroom-provisioner`: `administration: write`, `organization_administration: write`, `members: write`, `secrets: write`, `workflows: write`, `contents: write`, on **every org the App is installed on**. [Why](LESSONS.md#the-master-app-key-was-on-eleven-public-repositories-and-sco)
- **A fallback that is never reached protects nobody, and the CORS proxy pair was in the wrong order.** The PXL-owned Worker shipped as `VITE_CORS_PROXY_FALLBACK_URL` with corsproxy.io primary - and a fallback only fires when the primary *fails*, so once corsproxy.io was working again on a paid key the third party was back on the path of every sign-in. [Why](LESSONS.md#a-fallback-that-is-never-reached-protects-nobody-and-the-cor)
- **The App-permission drift check only ever looked one way.** `missingManifestPermissions` walks `MANIFEST_APP_PERMISSIONS` and reports what the App **lacks** - a feature that cannot work. Nothing walked the other direction, so a permission the App holds and no code needs was invisible for as long as it existed. [Why](LESSONS.md#the-app-permission-drift-check-only-ever-looked-one-way)
- **The privacy scanner never ran at the moment of publication.** `pages/scan.mjs` is a good gate and it was invoked from exactly one place - `pages/action.yml`, which runs when an ORG's control repo regenerates its own `public/`. `deploy-frontend.yml`, the workflow that actually puts bytes on a world-readable site, had **zero** references to it, while `scripts/fetch-pages-data.mjs` copies `public/i/*.json` and `public/teams/*.json` **verbatim** out of twelve control repos into the bundle. [Why](LESSONS.md#the-privacy-scanner-never-ran-at-the-moment-of-publication)
- **A guard written as a LIST of files covers what somebody remembered.** `tests/workflow-hardening.test.mjs` named three workflows by hand as needing the `[bot]` dispatch guard, and the list was wrong four times over: `sync-starter-code.yml`, `open-feedback-prs.yml`, `reconcile-registry.yml` and `weekly-usage-report.yml` all hold `PXL_APP_PRIVATE_KEY`, all reach `workflow_dispatch`, and none had it - the first two also mint a token for an **arbitrary org taken from their own input**. [Why](LESSONS.md#a-guard-written-as-a-list-of-files-covers-what-somebody-reme)
- **`shellcheck` came from npm, and every version of that package unpacks with unfixed-critical `decompress`.** Zip Slip, arbitrary file write and hardlink creation on extraction, advisory range `*`, package unmaintained - there is no patched version to move to, and the only npm escape is `shellcheck@1.1.0`, which unpins the binary to whatever "stable" meant at publish time and trades a supply-chain hole for exactly the version drift `scripts/lint.mjs` exists to prevent. [Why](LESSONS.md#shellcheck-came-from-npm-and-every-version-of-that-package-u)
- **GitHub's secret scanning cannot see the credentials this system mints itself.** Push protection is on and blocks `ghp_`, which is why `.env.test` is a smaller problem than it looks - but the invitation link's PKCS#8 P-256 key and the claim key have no provider prefix and nothing for GitHub to key on. [Why](LESSONS.md#github-s-secret-scanning-cannot-see-the-credentials-this-sys)
- **Hub credentials only run from `main`.** `workflow_dispatch` runs the workflow file from whatever ref it is given, and `participating-orgs` has deliberately lighter protection (ARCHITECTURE §5.5) - together a way to run hub code at a chosen ref with the App key in scope. [Why](LESSONS.md#hub-credentials-only-run-from-main)
- **A per-org cap is not a global cap, and the sentinel's was the only unbounded matrix.** `find-armable.mjs`'s `MAX_SENTINELS` (8) reads like a budget for one cron firing - its own comment cites the Team plan's 60 concurrent jobs - but the `arm` job is a **matrix over orgs**, so it bounds one org's list and `aggregate-armable` then flattens all of them into a single `watch` matrix. [Why](LESSONS.md#a-per-org-cap-is-not-a-global-cap-and-the-sentinel-s-was-the)
- **Credentials never appear in a git command line.** `preserve/preserve.mjs` logs every command it runs, on the **public** hub, and built `https://x-access-token:<token>@github.com/...` into it; Actions masked it only because `create-github-app-token` registers the value. [Why](LESSONS.md#credentials-never-appear-in-a-git-command-line)
- **Two workflows never ran once, and no cron was there to go red.** `sync-starter-code.yml` and `open-feedback-prs.yml` were the only two on the floating `actions/create-github-app-token@v1`; **v1 has no `client-id` input** - it takes `app-id` - so the *first* step of both failed with `Input required and not supplied: app-id` and neither workflow ever reached its script. [Why](LESSONS.md#two-workflows-never-ran-once-and-no-cron-was-there-to-go-red)
- **`gh` writes API errors to STDOUT, so a captured value is non-empty on failure.** Measured 2026-08-26: `gh api users/does-not-exist --jq .id` exits 1, puts `{"message":"Not Found",…,"status":"404"}` on **stdout** and only `gh: Not Found (HTTP 404)` on stderr. So `VAR=$(gh …)` followed by `[ -z "$VAR" ]` is not a check, it is a guard that can never fire - `retry-acceptance.yml` had exactly that, and only Actions' default `bash -e` stopped a JSON error blob being written into `$GITHUB_OUTPUT` as a student's account id; what it did cost was the message, so a lecturer who misspelled a login got `gh: Not Found` instead of being told which login. [Why](LESSONS.md#gh-writes-api-errors-to-stdout-so-a-captured-value-is-non-em)
- **The CI grading sync could never have worked: the App does not declare `checks`.** Reported live 2026-08-26 by a lecturer on `python-hacking-intro` - *"CI results sync failed for 1 student(s) due to API errors. Nothing was saved; try again later."* - with **4,995 of 5,000** API calls still available, which is what ruled out the rate limit the wording implied. [Why](LESSONS.md#the-ci-grading-sync-could-never-have-worked-the-app-does-not)
- **Git Push Rule:** Always use `$env:GITHUB_TOKEN=""; git push origin main` (PowerShell) when pushing to this repository to avoid authentication failures caused by dummy tokens in the environment.

### Invitations and acceptance

- **`rejected:cap-reached` promised a queue that Wave 8 deleted.** The message ended *"Acceptance queued for lecturer review."* and **nothing queues a rejected acceptance, nothing retries one** - the minimal-minutes redesign replaced the queue with synchronous provisioning, and no code anywhere reads a cap-reached rejection afterwards. [Why](LESSONS.md#rejected-cap-reached-promised-a-queue-that-wave-8-deleted)
- **The invitation status line could never say "Cap reached".** `InvitationShare`'s status is the **student-facing truth**, gated on the same conditions `AssignmentView` uses to decide whether to show an Accept button - a lecturer must not read *"Live"* over the page telling students *"Registration cap reached"*. [Why](LESSONS.md#the-invitation-status-line-could-never-say-cap-reached)
- **A green retry run is not a repository, and the panel announced one anyway.** `accept.mjs` exits **0** for every `rejected:*` outcome on purpose (a student who is not on the roster is the system working, and painting the hub red for it teaches people to ignore red) - so `retry-acceptance.yml` concludes `success` when it **refused**, and none of its follow-up steps fire either, leaving a green run that says nothing. [Why](LESSONS.md#a-green-retry-run-is-not-a-repository-and-the-panel-announce)
- **Two wire formats share one vocabulary at two sizes, and merging them is the trap.** `lib/acceptance-signature.mjs` and `lib/invite-token-format.mjs` sit side by side and each declare `SUBJECT_BYTES`, each define `subjectsMatch`, each carry an `encodePayload`/`decodePayload` pair - identical names, **8 bytes against 16**. [Why](LESSONS.md#two-wire-formats-share-one-vocabulary-at-two-sizes-and-mergi)
- **The team hint is a lock, not a label.** The acceptance concurrency group is keyed on `client_payload.team_hint`, derived from the issue *title*, because that is all the hub has before it can read the body - and per-team serialization is the only thing guarding `max_team_size` (§5.8). [Why](LESSONS.md#the-team-hint-is-a-lock-not-a-label)
- **Nonce revocation fails closed.** `verifyInviteToken` used `if (nonce && ...)`, so a broker with no `INVITE_NONCE` variable accepted **every token ever issued** for that assignment, including ones a `regenerate_invite` had just retired - and a publish that died between creating the repo and setting its variables produced exactly that. [Why](LESSONS.md#nonce-revocation-fails-closed)
- **A public broker accumulates whatever anyone writes into it, and nothing was looking.** Issues are the trigger mechanism, so a broker is a public repository anyone can open an issue on - that is not a flaw. What had no owner is everything that lands there and is **not** an acceptance: the job-level `if` skips those before a runner is allocated (deliberately), so nothing redacts, closes or notices them. [Why](LESSONS.md#a-public-broker-accumulates-whatever-anyone-writes-into-it-a)
- **No attacker-controlled text may reach a shell on a broker.** A broker is public, holds the broker App's private key as a repo secret, and has issues enabled - so any GitHub account can fire its workflow. `BODY="${{ github.event.issue.body }}"` in a `run:` block there was arbitrary code execution against the App key, reachable by anyone, against every participating org (ARCHITECTURE §4.3.1). [Why](LESSONS.md#no-attacker-controlled-text-may-reach-a-shell-on-a-broker)
- **Signed invitations are what stop outsiders triggering work.** Acceptance fires on a public event on a public repo, so anyone can ring the doorbell - star, fork, issue, comment, wiki edit are all open to any account, and none prove authorization. The roster gate authorizes, but only *after* the broker minted an App token and the hub cloned the private control repo. [Why](LESSONS.md#signed-invitations-are-what-stop-outsiders-triggering-work)
- **A closed issue on a public repo hides nothing.** The acceptance issue's TITLE carries the signed invitation, so the first student to accept used to publish the assignment's token to anyone who looked at the broker's issue list or searched GitHub for `pxl-accept:` - defeating §4.3.2 outright and, because the acceptance card is named `sha256(invite_token)`, making the card and its teams file public too. [Why](LESSONS.md#a-closed-issue-on-a-public-repo-hides-nothing)
- **Redaction, deletion and a sweep are all AFTER the fact - the fix was to stop publishing a credential.** The three steps above hide the browsable copy of the title; they cannot touch the `opened` event, which GitHub emits before any of them run and GH Archive mirrors permanently. Measured 2026-08-25: `curl -s https://api.github.com/repos/<org>/<broker>/events`, unauthenticated, returned a full still-valid `pxl-accept:` token on an issue that had **already been deleted**, for a live `roster_mode: open` assignment. [Why](LESSONS.md#redaction-deletion-and-a-sweep-are-all-after-the-fact-the-fi)
- **The team hint is appended AFTER signing, so the verifier has to cut it off - and for months it did not.** `verifyAcceptanceTitle` split `github.event.issue.title` on `.`, which handed the signature back as `<signature> team:alpha` - not base64url - so **every group acceptance on the signed path was rejected as `malformed`**, on every group assignment, while individual acceptance worked perfectly. [Why](LESSONS.md#the-team-hint-is-appended-after-signing-so-the-verifier-has-)
- **The acceptance payload is binary because the JSON one did not fit.** It carried the assignment id verbatim plus a full ISO-8601 `issuedAt`, and a real id - `2526-automation-scripting-practicum-exam-2` - produced a **253-character** title before any team hint was appended, so a group acceptance threw at the accept button for a reason the lecturer chose months earlier when naming the assignment. [Why](LESSONS.md#the-acceptance-payload-is-binary-because-the-json-one-did-no)
- **Who accepted is ONE field: `github.event.issue.user`.** The broker verified the signature against `issue.user.id`, validated `github.actor` and `github.event.sender.id`, and dispatched *those* to the hub - so the account we checked and the account we provision for were two different readings of the same event. [Why](LESSONS.md#who-accepted-is-one-field-github-event-issue-user)
- **`injectAuth` stored a session shape GitHub cannot produce.** It wrote `{login, name, email}` while `auth.js` persists `{login, id, name, email}`, and `getUser()` reads the stored object rather than re-fetching - so **every e2e acceptance signed with `githubId: undefined`**. [Why](LESSONS.md#injectauth-stored-a-session-shape-github-cannot-produce)
- **A leftover `pxl-accept:` title means two different things, and the advice differs.** Tier 4's exposure sweep said "still carry this assignment's invitation token... the link is effectively public... regenerate the invitation" for *any* leftover. On a **migrated** assignment that is false and the advice is actively harmful: the title is a signature naming one account, useless to anyone else, and regenerating retires every student's link to fix nothing. [Why](LESSONS.md#a-leftover-pxl-accept-title-means-two-different-things-and-t)
- **The hub CANNOT delete the trigger issue, and never could - the step is gone.** `deleteIssue` refuses an App installation token outright: measured live 2026-08-26, twice, in two organizations, `{"type":"FORBIDDEN","path":["deleteIssue"],"message":"Viewer not authorized to delete"}`. [Why](LESSONS.md#the-hub-cannot-delete-the-trigger-issue-and-never-could-the-)
- **The failed-deletion warning asserted a cause and threw the evidence away.** `acceptance-handler.yml` ran `deleteIssue` with `2>/dev/null` and, on failure, printed "deleteIssue needs Administration: write on the organization". Measured live 2026-08-26 during a full end-to-end run: **that is false**. [Why](LESSONS.md#the-failed-deletion-warning-asserted-a-cause-and-threw-the-e)
- **A pre-migration link must NOT be signed, and nothing was stopping it.** `signedAcceptanceIssueTitle` signed whatever secret the URL carried. A link handed out before the change carries a 122-character bearer token, `fromBase64Url` rejects its `.` separator, and the accept button renders **"not base64url"** to the student - so the deploy that shipped signing would have broken acceptance for **every live assignment at once**, since none had a keypair yet. [Why](LESSONS.md#a-pre-migration-link-must-not-be-signed-and-nothing-was-stop)
- **Rotation retires a link too, and only migration was covered.** `regenerate_invite` mints a fresh keypair - the answer to a leaked link, and the *recurring* case, where migration happens once. The old key is gone from the document, so the "a secret the document still carries" rule below cannot see it, and the prune deleted its card: a rotated-away link landed on the not-found page, whose only honest wording is a guess between three causes. [Why](LESSONS.md#rotation-retires-a-link-too-and-only-migration-was-covered)
- **A retired link resolves to a page that says so, and the two diagnostics for it are different checks.** Migration and rotation both take working links out of students' hands. `pages/generate.mjs` therefore writes a second card at the digest of **a secret the document still carries that is no longer the link** - phrased that way rather than as "has both fields", so it tracks `linkSecretFrom` instead of restating it: on an **unmigrated** assignment the token *is* the link, and a both-fields test would replace that cohort's only working card with a tombstone. [Why](LESSONS.md#a-retired-link-resolves-to-a-page-that-says-so-and-the-two-d)
- **Public Pages artifacts disclose only what the student portal needs.** The acceptance card lives at `data/<org>/i/<sha256(invite_token)>.json` (teams beside it as `<sha256>.teams.json`), so finding it requires the link, a leaked filename is not a working token, and the teams file stops being a public cohort list of member logins. [Why](LESSONS.md#public-pages-artifacts-disclose-only-what-the-student-portal)
- **A rejection is an outcome, not a failure.** `accept.mjs` splits `reject()` (exit **0**, `rejected:*`) from `fail()` (exit **1**, `fail:*`). A student who is not on the roster, or arrives after the deadline, is the system working - painting the hub's Actions tab red for that teaches people to ignore red runs and buries real failures beside them. [Why](LESSONS.md#a-rejection-is-an-outcome-not-a-failure)
- **A restricted GitHub account fails invisibly.** GitHub returns HTTP 201 for an issue opened by an account it has flagged, then removes the content seconds later; no webhook fires, so the broker never runs. Observed live. `AssignmentView` records the acceptance issue number and, when polling gives up, re-reads it: gone means `blocked-account` ("GitHub is blocking your request"), not `timeout` ("GitHub is under load"). [Why](LESSONS.md#a-restricted-github-account-fails-invisibly)
- **System Health must check the invitation chain, not just the broker.** Four things have to agree before a student can accept, and every mismatch fails silently: the assignment holds an `invite_token`, the hub publishes the `kid` it was signed with (`acceptance/invite-keys.json`), the broker's `INVITE_NONCE` matches the token's, and `INVITE_ENABLED` is not `false`. [Why](LESSONS.md#system-health-must-check-the-invitation-chain-not-just-the-b)
- **The Admin Panel rebuilds the whole assignment on save.** `buildDoc` constructs the YAML field by field, so anything it does not carry through is deleted - and the document still validates, because the invite fields are optional. Editing a published assignment therefore used to wipe its `invite_token` and silently retire every student's link. [Why](LESSONS.md#the-admin-panel-rebuilds-the-whole-assignment-on-save)
- **One reader for the invitation, and it is the writer's.** `INVITE_FIELDS`, `readInviteField`, `parseInviteFields` and `quoteInviteValue` live in `lib/invite-token-format.mjs` beside the wire format, and are used by `scripts/set-assignment-invite.mjs` (writer), `AdminView.verifyLiveInfrastructure` and `AssignmentDetailView.loadInviteToken` (readers). [Why](LESSONS.md#one-reader-for-the-invitation-and-it-is-the-writer-s)
- **One invitation-share surface: `InvitationShare.vue`.** The link existed as a bare `<span>` in the publish banner, a lone primary button on the detail header, and **nowhere** on either list of assignments - so a lecturer who closed the editor had no route back to it, and rotation was reachable only from the Actions tab. [Why](LESSONS.md#one-invitation-share-surface-invitationshare-vue)
- **`Republish broker` is offered on a `published` assignment and nowhere else.** `publish-assignment.yml` runs `sed -i "s/^state:.*/state: published/"` with no regard for the prior state, so the same dispatch from `closed` or `archived` **reopens acceptance**. WS5 relabelled that dispatch "Republish broker" and grouped it under *Repair*, beside copy promising "existing student repositories are untouched, and links already handed out keep working" - which is C4 exactly: the UI describing behaviour the system does not have. [Why](LESSONS.md#republish-broker-is-offered-on-a-published-assignment-and-no)
- **`max_acceptances` can overshoot, and that is a decision - do not "fix" it.** `accept.mjs` counts `acceptances/<id>/*.json`, compares, then writes, and the acceptance concurrency group is keyed on `team_hint || github_login` - so per-*team* serialization guards `max_team_size` while acceptances by **different** students run in parallel. [Why](LESSONS.md#max-acceptances-can-overshoot-and-that-is-a-decision-do-not-)
- **`is_first_member` counts acceptances, not members.** A lecturer-seeded team lists every member before anybody has accepted, so counting members told the genuinely-first student they were not. And a **team switch keeps the original `accepted_at`** - the switch falls through the idempotency check because it has work to do, and rewriting the timestamp moved the fact that decides whether a student accepted before the deadline.
- **`regenerate_invite` is reachable, and rotating clears the old link.** The input existed on `publish-assignment.yml` and nothing in the SPA or CLI ever sent it, so a leaked link could only be rotated from the Actions tab - and doing that left the panel showing and copying the retired token. [Why](LESSONS.md#regenerate-invite-is-reachable-and-rotating-clears-the-old-l)
- **Liveness is the page a student opens.** `pages/generate.mjs` writes `data/<org>/i/<sha256(token)>.json` **only** when the assignment carries an `invite_token`; without one it warns, continues, and still adds the id to `assignments.json`. So checking the index reported "Published & Verified Live" over a card that 404s for every student - the same mistake `e594f4f` fixed in diagnostics Tier 5 and not in the publish flow beside it. [Why](LESSONS.md#liveness-is-the-page-a-student-opens)
- **Publish never strands state.** "Save & publish" reverts the assignment YAML to `draft` when the `publish-assignment.yml` dispatch fails, so `state: published` never coexists with a missing broker. Cross-field rules the schema can't express (deadline > opens_at, `max_acceptances` ≥ 1) are enforced in `AdminView.validate()`.

### Roster, claims and identity

- **`roster_mode: claim` binds an account to an EMAIL ADDRESS, and `lib/claim.mjs` is the only thing that knows how.** It is "enforced, with a way in": the lecturer holds addresses, the student proves one, and it must match a roster entry. The module is isomorphic on WebCrypto so the SPA seals with the same code the hub opens with - ECDH P-256 -> HKDF -> AES-GCM, wire format `c1.<ephemeral SPKI>.<iv>.<ciphertext>`. [Why](LESSONS.md#roster-mode-claim-binds-an-account-to-an-email-address-and-l)
- **Adding a roster mode SPLIT a question that used to have one answer, and seven call sites had already conflated them.** Before `claim` there was exactly one roster-gated mode, so a hand-written `=== "enforced"` correctly answered both *"is the roster what decides who may accept?"* and *"is the student's LOGIN what gets looked up in it?"*. [Why](LESSONS.md#adding-a-roster-mode-split-a-question-that-used-to-have-one-)
- **The student confirms an address; the page must never claim more than it knows.** `ClaimAddressCard.vue` lists the student's own GitHub-**verified** addresses (`GET /user/emails`, account permission `email_addresses: read`) filtered to `claim_domains`, and typing stays open as the fallback recorded `claim_verified: false` - requiring a verified address was considered and rejected, because it blocks a real fraction of students and stops nothing determined, the page being public JavaScript either way. [Why](LESSONS.md#the-student-confirms-an-address-the-page-must-never-claim-mo)
- **`roster_mode: org_member` is GONE (2026-08-27), having never run a single cohort.** It gated on an ACTIVE org membership so a lecturer could enrol from a list of **email addresses** - the real problem, since a lecturer holds addresses and not GitHub usernames, an installation token cannot read a user's emails (`GET /user/emails` is user-to-server), and anything the SPA sends is a claim rather than a credential. [Why](LESSONS.md#roster-mode-org-member-is-gone-2026-08-27-having-never-run-a)
- **Under `open` the claim observes and never refuses, because a check anyone can skip is not a gate.** The same flow runs and the same `students/claims/<github_id>.json` is written, but nothing rejects an acceptance and **nothing counts an attempt**. That is forced, not chosen: the claim is optional under `open` (an older link, a browser without WebCrypto, a dismissed prompt must all still provision), so anyone wanting a second repository just omits it. [Why](LESSONS.md#under-open-the-claim-observes-and-never-refuses-because-a-ch)
- **A binding a lecturer cannot see is the same mistake as one they cannot undo, so the column and `unlink` shipped together.** `lib/claim-bindings.mjs` is the single join between `students/claims/<github_id>.json` and `students/roster.yml`, and the join is the **email address**, case-insensitive - the same comparison `rosterEntryForEmail` makes in the other direction when the student claims. [Why](LESSONS.md#a-binding-a-lecturer-cannot-see-is-the-same-mistake-as-one-t)
- **One reader for `roster_mode`: `lib/roster-mode.mjs`.** The rule was written by hand in five places as `roster_mode === "open" ? "open" : "enforced"`, a spelling that normalises and **silently collapses anything it does not recognise** into `enforced`. That is right for garbage - the gate must fail closed - and wrong for a value the system has since learned about: `AdminView.loadAssignmentIntoForm` used exactly that ternary, so opening an `org_member` assignment rewrote it to `enforced` on load and `buildDoc` saved the rewrite back, silently converting a membership-gated cohort into one gated on an empty roster. [Why](LESSONS.md#one-reader-for-roster-mode-lib-roster-mode-mjs)
- **`students/` was never committed, so the claim bound nothing and its rate limit could not count.** `accept.mjs` writes into a checkout the workflow commits, and the staging list was `repositories/`, `teams/`, `acceptances/` - never `students/`. Found by running a real claim: the acceptance succeeded, the log said `[ok] claim - @tomcoolpxl claimed tom.cool@pxl.be`, and `students/claims/71908551.json` was a **404** a second later. [Why](LESSONS.md#students-was-never-committed-so-the-claim-bound-nothing-and-)
- **The SPA bundles `acceptance/claim-keys.json`, and changing it deployed nothing.** `deploy-frontend.yml` is path-filtered, `frontend/src/lib/claim.js` imports that file at build time, and the path was not in the filter - so the commit that minted the hub's real claim keypair fired **no deploy**, and the live page kept telling students "claiming is not set up for this course yet" while the hub could decrypt perfectly well. [Why](LESSONS.md#the-spa-bundles-acceptance-claim-keys-json-and-changing-it-d)
- **The account permission is `emails`; the settings toggle is labelled "Email addresses".** `ACCOUNT_APP_PERMISSIONS` said `email_addresses`, so the check reported `email_addresses=missing` while `GET /apps/{slug}` plainly returned `emails: read` - a constant naming a field the API does not use is a check that can never pass, the same shape as the scanner rule that guarded `claim_token`. [Why](LESSONS.md#the-account-permission-is-emails-the-settings-toggle-is-labe)
- **Rotating the claim key was impossible, and the RUNBOOK described a remedy that does nothing.** `acceptance/claim-keys.json` has always carried a `current` kid and a `keys` map, and the SPA seals to whichever is current - so it LOOKS rotatable. It is not: the kid **never travels with the ciphertext** (`c1.<ephemeral SPKI>.<iv>.<ciphertext>`) and the hub held exactly one `PXL_CLAIM_PRIVATE_KEY`. [Why](LESSONS.md#rotating-the-claim-key-was-impossible-and-the-runbook-descri)
- **"The roster file exists" is not "somebody can accept".** Tier 3's roster check tested `rosterRes.ok` and reported **`ok`** for three rosters that let nobody accept: `students: []` (the scaffold stub - this is exactly what stranded `2526-examen-aut2-ek2` in July, every acceptance rejected `not-on-roster` with nothing saying why); a hand-edited **array-shaped** roster, which parses fine while `accept.mjs` reads `roster?.students || []` and so sees nobody; and a roster whose students have **no `github_login`**, the optional CSV column and the only field `accept.mjs` matches on. [Why](LESSONS.md#the-roster-file-exists-is-not-somebody-can-accept)
- **Student Tooltip & Identity Resolution:** Hovering over student logins in the table/cards resolves identity across 4 tiers: (1) institutional roster (`students/roster.yml`), (2) Git commit author email/name (prioritizing real email, suppressing dummy `@users.noreply.github.com` and bot names `[bot]`/`provisioner`/`web-flow`), (3) GitHub public user profile (`GET /users/{login}`, batched in background with concurrency 6), and (4) clean fallback (`null`). [Why](LESSONS.md#student-tooltip-identity-resolution)
- **`roster_mode` is per-assignment and fails closed.** `enforced` (default) requires the login in `students/roster.yml`; `open` skips the roster gate entirely for assignments whose cohort isn't known up front (exams), leaving the `opens_at..deadline_at` window and `max_acceptances` as the only guardrails. [Why](LESSONS.md#roster-mode-is-per-assignment-and-fails-closed)
- **Under `open` the system learns a GitHub login and nothing else, and that used to be the end of it.** Who accepted is recorded in `acceptances/<id>/<login>.json`; `students/roster.yml` is written **only** by a CSV import, so the next assignment started from the same blank roster and the lecturer re-collected usernames by hand. [Why](LESSONS.md#under-open-the-system-learns-a-github-login-and-nothing-else)
- **One roster identity rule: `lib/roster-entries.mjs`.** `diffRosters` existed twice - `cli/src/commands/roster.mjs` and `frontend/src/lib/csv.js` - and had **already forked**: the CLI compared entries with a stable stringify while the SPA used `JSON.stringify`, which is key-order sensitive, so a roster whose YAML serialised its keys in another order showed **every** student as "updated" in the Admin Panel and unchanged in the CLI. [Why](LESSONS.md#one-roster-identity-rule-lib-roster-entries-mjs)

### Deadlines, lockdown and preservation

- **One archive per assignment, and where a preservation lives is READ, not derived.** The archive was one repository per org and it only ever grew: measured on real PXL cohorts, student repos on the automation/systems courses run 400 KB - 58 MB each (people commit build artifacts) and git dedups the shared template but not what students add, so four assignments a year at forty students is ~800 MB per org per year in a single repository, against GitHub's ~1 GB soft warning. [Why](LESSONS.md#one-archive-per-assignment-and-where-a-preservation-lives-is)
- **Preservation pushes a complete object graph, and never with `--force`.** An org is entitled to forbid force-push with a ruleset (the same thing that made `ec896c8` stop force-pushing the broker), and a rejected push here fails preservation for every student - the safety net the whole deadline flow rests on. [Why](LESSONS.md#preservation-pushes-a-complete-object-graph-and-never-with-f)
- **Finalize is complete only when submissions are archived.** The idempotency key is not "a `lockdown-record.json` exists" - `find-finalizable.mjs` re-queues a past-deadline assignment while any student with a `snapshot_sha` lacks a verified `observations/<id>/<login>/preservation.json` (ARCHITECTURE.md §6.2.1). [Why](LESSONS.md#finalize-is-complete-only-when-submissions-are-archived)
- **`late_policy` and `lock_down_enabled` are two decisions, and both used to be dead.** `late_policy: block` said "refuse late pushes" and no code read the field; `lock_down_enabled` said "demote admin -> pull at the deadline" and no code read that either - lockdown demoted everyone on every assignment regardless. [Why](LESSONS.md#late-policy-and-lock-down-enabled-are-two-decisions-and-both)
- **The sentinel's precision was invisible in the record it exists to improve.** It writes no `lockdown-record.json` on purpose, so the nightly hours later had no prior to read and stamped `lockdown_at` with **its own clock** - for a 20:00 deadline the record said the cohort froze at 00:00 and `uncertainty_seconds` reported four hours where the sentinel had achieved seconds. [Why](LESSONS.md#the-sentinel-s-precision-was-invisible-in-the-record-it-exis)
- **The sentinel waits for the instant and stops nothing itself.** `deadline-sentinel.yml` (4-hourly cron, 4.5 h arm window, keyed on **(org, deadline instant)** so assignments sharing a deadline share a job) closes the gap between the deadline and the nightly. Load-bearing details: it **polls rather than sleeps**, and the poll is `GET /orgs/{org}/repos?sort=pushed&direction=desc&per_page=100` — one call for a hundred repos, where per-repo polling would be 7,200 requests against a 5,000/hr limit; `pushed_at` is GitHub's own timestamp, so the resulting timeline (`lockdowns/<id>/sentinel-<key>.json`) is the only thing that can answer "at 21:55 your last push was 21:12", which the committer-date fallback cannot. [Why](LESSONS.md#the-sentinel-waits-for-the-instant-and-stops-nothing-itself)
- **The `until` fallback is honest, not tamper-proof.** Phase 1 fires on the nightly, not at the deadline, so under `block` phase 2 rebuilds the submission with `commits?until=<effective deadline>` and takes `[0].sha` - `null` (a `no_submission`, not an error) when nothing was committed in time. [Why](LESSONS.md#the-until-fallback-is-honest-not-tamper-proof)
- **Lockdown stops the whole cohort first, then records it.** `lockdown.mjs` is four phases (plan / stop / record / demote), not one loop per student. The old loop read a student's `HEAD` and then demoted them, so in a 200-student cohort student 1 froze at T+0s and student 200 minutes later - the demotion is a write against an ~80/min secondary limit - which both gave the end of the list extra time and made the snapshot a smear rather than a cut. [Why](LESSONS.md#lockdown-stops-the-whole-cohort-first-then-records-it)
- **One deadline per student, and `lib/effective-deadline.mjs` is where it is decided.** Every comparison against "the deadline" must be the deadline *for that student*, or the system acts against work a lecturer allowed. `report.mjs` had the only copy and it read `override.deadline_at` - a field the Admin Panel stopped writing on 2026-06-17 in favour of the append-only `overrides[]` array that `override.schema.json` requires - while `lockdown.mjs` and `find-finalizable.mjs` never opened `overrides/` at all. [Why](LESSONS.md#one-deadline-per-student-and-lib-effective-deadline-mjs-is-w)
- **An empty population is not a failure.** Zero repository records for an assignment (nobody accepted yet) must never fail `collect`/`lockdown` - it turned every nightly finalize red and buried real failures in sibling matrix legs. `lockdown` still writes an empty `lockdown-record.json` so `preserve` reports "no students to preserve" instead of `fail:no-lockdowns`. [Why](LESSONS.md#an-empty-population-is-not-a-failure)
- **An org's base repository permission is a floor under lockdown, and nothing was watching it.** `default_repository_permission` is what every **org member** gets on every repository, private ones included. It grants students nothing today - `provision.mjs` adds them as repository **collaborators**, not members - which is exactly why nobody looks at it: six of seven readable PXL orgs are `none` and `PXL-CSMobile` sat on `read` from its 2024 creation, a year before this system existed. [Why](LESSONS.md#an-org-s-base-repository-permission-is-a-floor-under-lockdow)
- **An organization OWNER among the acceptors cannot be frozen, and only the record said so - afterwards.** `default_repository_permission` is a floor under every org *member*, and the bullet above watches it; an **owner** is not subject to a floor at all - GitHub grants owners admin on every repository - so `demote()` writes `pull`, reads the permission back, gets `admin`, and records `verified: false` / `permission_after: "admin"`. [Why](LESSONS.md#an-organization-owner-among-the-acceptors-cannot-be-frozen-a)
- **Only a published or closed assignment is finalizable.** `find-finalizable.mjs` checked the deadline and not the state, so a draft with a past deadline had no lockdown record, looked `not-finalized` forever, and queued a four-step matrix leg every night on a system whose whole point is billing zero minutes when idle.
- **The `deadline-gap` alarm was structurally guaranteed to fire, for every student, always.** It compared `uncertainty_interval_seconds` against a **one-hour** threshold, and that value is `deadline - lastOnTimeObservation` while the nightly collect observes **once a day** - so the gap is many hours by construction. [Why](LESSONS.md#the-deadline-gap-alarm-was-structurally-guaranteed-to-fire-f)
- **The preservation banner promised one number and displayed a different one.** Its copy says *"Delay between deadline and lockdown execution"*, and it read `students[].uncertainty_interval_seconds` - which `report.mjs` computes as `effectiveDeadline - lastOnTimeObservedAt`, the **other side of the deadline**: how stale the evidence was going *in*, routinely hours with a nightly collect. [Why](LESSONS.md#the-preservation-banner-promised-one-number-and-displayed-a-)
- **`preserved_sha` was null on every report ever generated, and four features hung off it.** `report.mjs` read `preservation.preserved_sha`; `preserve.mjs` writes **`source_sha`** and never had that field. Confirmed against the only real preservation in production - its `preservation.json` carries `source_sha` and `verified: true`, and the report beside it says `preservation_status: "preserved"` with `preserved_sha: null`. [Why](LESSONS.md#preserved-sha-was-null-on-every-report-ever-generated-and-fo)
- **Post-Deadline Preservation Summary Banner & Archive Links:** `AssignmentDetailView.vue` displays a post-deadline preservation summary banner with live preserved count, lockdown execution timestamp, and measured uncertainty delay (`uncertainty_seconds = lockdown_at - deadline_at`), targeted retries, and manifest download. [Why](LESSONS.md#post-deadline-preservation-summary-banner-archive-links)

### Reports, grading and document shape

- **A synthetic object handed to a shared builder loses whatever the builder learns next.** `buildDashboardEntry(assignment, students)` has two callers: `report.mjs` passes the **real** assignment YAML and so gains every new field for free, while the SPA's live refresh synthesises a `pseudoAssignment` from the stored entry **field by field** - it only wants to update one entry. [Why](LESSONS.md#a-synthetic-object-handed-to-a-shared-builder-loses-whatever)
- **A mock that accepts anything tests nothing, and the e2e fixture accepted every write.** `setupStandardMockRoutes` stored whatever the SPA `PUT` to `/contents/` and answered 200, so **no e2e ever checked that a document the app writes is one the backend could read back** - which is exactly how a member edit shipped writing a team manifest missing its required `created_by` with spec 16 green over it, and how Live Refresh shipped storing `earned_points` on report rows the schema forbids. [Why](LESSONS.md#a-mock-that-accepts-anything-tests-nothing-and-the-e2e-fixtu)
- **The report on screen is not the report on disk, and Live Refresh stored the wrong one.** Grades live in `grading/<id>/summary.json` and are **joined onto** the report's student rows at load time (`earned_points`, `total_points`, `ci_status`, `ci_run_url`, `graded_at`); a live refresh also sets `ci_status` on rows itself. [Why](LESSONS.md#the-report-on-screen-is-not-the-report-on-disk-and-live-refr)
- **Editing a team's members rebuilt the manifest from the row on screen, and deleted three fields doing it.** `TeamsTable.saveTeamMembers` constructed a whole `team.json` field by field - the `buildDoc` bug in a new place, and worse, because the source it rebuilt from is not a manifest at all: `props.teams` is the **display shape** `mergeTeamManifests` assembles, carrying `submission_status`, `commit_count`, `under_capacity` and `warnings` (none schema-legal under `additionalProperties: false`) and carrying **no `repo_id` and no `created_by`**. [Why](LESSONS.md#editing-a-team-s-members-rebuilt-the-manifest-from-the-row-o)
- **A `python` autograde test is its `script`, on every runner.** `provision.mjs` emitted `command: t.command || "pytest"` and never read `script`, while `runner-host.mjs` and `runner-docker.mjs` both write `script` to `t.py` and run it and ignore `command` - and the Admin Panel only ever writes `script`. [Why](LESSONS.md#a-python-autograde-test-is-its-script-on-every-runner)
- **Automated checks are a task, not a config language.** The assignment form showed an *Enable autograding* checkbox that opened a type dropdown and four unlabelled textareas whose meaning changed with it - no headers, no totals, no validation until the schema refused the save three commits later, and a visibility control named after its mechanism (*"Private (Hidden via reusable workflow)"*) rather than after the decision. [Why](LESSONS.md#automated-checks-are-a-task-not-a-config-language)
- **Generated YAML is serialised, never concatenated.** `buildAutogradingWorkflow` builds an object and hands it to the `yaml` library. It used to paste lecturer-authored test config into a template - `command: "${t.command}"` - so a command containing a double quote (`grep "needle" file`) closed the string early and produced a workflow that does not parse, in **every** student repository, discovered by the student when their grading run went red. [Why](LESSONS.md#generated-yaml-is-serialised-never-concatenated)
- **The Contents API returns 200 with no body above 1 MB.** `encoding: "none"`, `content: ""` - which `getRepoContent` returned as `null`, indistinguishable from a 404 to every caller, so a large `reports/dashboard.json` or roster read as absent. It now re-reads through `application/vnd.github.raw` and throws if that fails. [Why](LESSONS.md#the-contents-api-returns-200-with-no-body-above-1-mb)
- **Live Status / Refresh invariants (AssignmentDetailView):** a post-deadline commit never downgrades a student who has an on-time submission on record (it sets `first_late_sha`, not a `late` status - nightly semantics), a partial refresh is never persisted (all students refreshed, or nothing is committed to the control repo), and grading sync results with 0 check-runs are logged under failed with reason `"no CI run at preserved SHA"`. [Why](LESSONS.md#live-status-refresh-invariants-assignmentdetailview)
- **The nightly collect reported an error for every student it collected successfully, for eight days.** On 2026-08-18 the commit read moved from `/commits/{ref}` (an OBJECT) to `/commits?sha=…&per_page=1` (a LIST), so the commit count could be taken from the Link header's `rel="last"` page number.
