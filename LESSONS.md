# Lessons

Why the rules in [CLAUDE.md](CLAUDE.md) exist: what broke, how it was found, what
was measured. Nothing here is a rule of its own - every entry is the story behind
a rule, and the rule is the authority.

This file is **not** loaded into every session, which is the point: the rules are
short enough to be read every time, and the reasoning is one click away when a rule
is about to be changed. Kept because a rule whose reason is lost gets argued away.

## Working rules

### `npm run lint` is the only lint command, and CI runs exactly it.

It was `eslint .` while CI's `test` job ran `eslint . --max-warnings 0` and CI's `lint` job ran `actionlint` + `scripts/workflow-lint.mjs` with no local equivalent - so a change could be linted clean locally, repeatedly, while CI had been red since `48ed831` over a shellcheck finding no local command could produce. Nine commits shipped on top of it. `scripts/lint.mjs` now owns all three checks; `ci.yml` calls `npm run lint` and nothing else.

Both external tools are pinned because taking either from the runner image means a different version reports different findings - the same local-vs-CI drift in another coat. shellcheck was an npm devDependency until 2026-08-31, dropped because every published version from 2.x up unpacks the official release with `decompress`, which carries three unfixed critical advisories and has no patched version to move to; the only npm escape was 1.1.0, which unpins the binary to whatever "stable" meant at publish time. actionlint was worse: fetched by piping a script from a **mutable branch** into bash, with no pin on the script and no checksum on the binary it then fetched, running on every developer machine and every CI lint job. Both now go through one `fetchPinnedTool` with digests for all five platforms.

A tool that cannot be obtained **fails** the run; there is deliberately no skip flag, since a check that quietly does not run is the whole bug this file exists for.

### A `run:` block over 4 KB hangs the linter on Windows, and CI stays green while it does.

actionlint copies each script to shellcheck's **stdin**; a Windows anonymous pipe holds **4096 bytes**, so once the script exceeds that the copy blocks on a full pipe and `Wait()` never returns - no output, no exit, for ever. Linux pipes hold 64 KB, which is why `lint: success` appeared on every CI run throughout.

Measured 2026-08-26: `publish-assignment.yml`'s single 92-line *Publish broker* step reached **4106 bytes** and deadlocked; every other block in the repo was under 3 KB, which puts the cliff at 4096 exactly rather than near it. Bumping actionlint does not help (1.7.1 and 1.7.12 both hang).

It went unnoticed because a hang looks like work in progress: `91114af` added **seven lines** to that step and shipped with *"local actionlint could not be run to completion"* in its commit message instead of a lint result, and the next session lost an hour to it.

Three things now hold. The step is **split in two** (1707 + 2438 bytes) - splitting is platform-neutral, and a Windows-only workaround would reintroduce the exact local-vs-CI drift `scripts/lint.mjs` exists to end. `scripts/lint.mjs` gives every step a **120 s timeout** that names this cause, because a two-minute failure is a diagnosis where an infinite hang is not. And `tests/workflow-hardening.test.mjs` caps every `run:` block at **3500 bytes** in milliseconds, on every platform, covering composite `action.yml` files too. The timeout is the diagnosis, the test is the guard - do not rely on the timeout, and do not raise the cap to fit a block that has outgrown it.

### A second copy of a reference table is a copy that goes stale, and nothing was checking.

Every documentation defect found in the 2026-08-31 audit pass was the same shape: a fact written down twice, one copy updated, the other left. None of them would fail a test, a build or a lint run, and all of them were being read.

The App permission list was the worst of it. ARCHITECTURE §3.2.1 holds the real table, next to `MANIFEST_APP_PERMISSIONS`; §10.2 held a second copy for the SPA's sake, and that copy listed `issues: write` **twice**, omitted `checks: read`, `actions_variables: write` and `members: write` entirely, declared `organization_administration` at `read` where the App holds `write`, and called the account `emails` permission "optional" where the other table calls it required. A lecturer reading §10.2 to find out what a leaked token grants would have been reading fiction. The same section, nineteen lines below the paragraph recording that the CORS proxy order **had been reversed**, still advised a higher-security deployment to "make the PXL-owned Worker the primary rather than the fallback".

The rest of the family, all found in one pass: §10.6 spelled the design tokens as dark-only literals (`--bg-canvas: #0d1117`) after light mode shipped, when the real declaration is `light-dark(#eaeef2, #0d1117)` - a doc that hardcodes one theme's half is a doc that cannot survive the second theme. §2 and §14 both said "one GitHub App" after the broker App split, and README said it twice more. INSTALL.md §2 instructed every new deployment to grant the App account **Starring**, a permission deliberately removed - the only one of these that would actively widen a credential, because somebody following the runbook would have ticked the box.

**So a reference table lives in exactly one section, and every other place links to it.** ARCHITECTURE §10.2 now names §3.2.1 and stops; §10.6 names DESIGN.md and stops. The test is not "is this true today" but "if this changes, is there a second place that has to change with it" - and if there is, delete the second place.

Structure drifts the same way and is even quieter. ARCHITECTURE §4.3 opened a four-item bullet list, ran five subsections, and the last three bullets ended up below §4.3.4's closing paragraph, where they read as belonging to it. §5 skipped from 5.5 to 5.8. RUNBOOK declared `#### 1.3.2` **twice** - "Claim keypair" and "Migrating an assignment to signed acceptance" - while fifteen references across code, tests and both documents pointed at the number, splitting roughly two to one between them; the migration one was given its own number and both later moved to INSTALL.md. A renumber is cheap to get wrong and impossible to see: `§4.3.2` alone has 62 references, `§10.1.1` has 27, `§15` has 21, and a reference to a section that no longer exists renders as ordinary text.

**Before renumbering anything, count the references.** The section numbers are this documentation's public API - code comments, tests and workflow YAML all cite them - so the numbering is held stable on purpose, and a tidier scheme is not worth a silent dangling reference. Sweep with an exact string, and check first that the string is unambiguous: a high subsection number belongs to ARCHITECTURE alone and is safe to replace everywhere, while a low one such as `6.2` is claimed by RUNBOOK too and a blind sweep rewrites both. Verify afterwards with something that re-derives the heading set from the documents rather than trusting the sweep.

## Shape of the system

### Hub-and-spoke

All workflows live in the central public `pxl-classroom` hub. Per-org control repos hold data only and contain no workflow files.

### Minimal-minutes (Wave 8)

Synchronous provisioning (no queue), one nightly `daily-activity.yml` cron that disables itself when no assignment is active, event-driven dashboard regen. The system bills zero minutes when idle.

### Admin Panel is the source of truth for lecturer actions

Assignment YAML and override JSON are generated and committed via the SPA + Contents API. The public Page assignments index is stored in the control repo as `assignments.json` keyed by assignment ID (object format), gathered dynamically by the hub build pipeline using `scripts/fetch-pages-data.mjs` to form the global Page data index. `regenerate-dashboard.yml` runs the interim report generator script (`generate-interim-reports.mjs`) to update `reports/dashboard.json` for active assignments in real-time. Roster CSV imports map schema validation (AJV) errors from mechanical formats (e.g. `/students/3/email`) to friendly, line-and-student-specific warnings using `formatRosterValidationError`.

### `pxl-classroom` CLI is the parallel lecturer surface

(in `cli/`) - same App, same device-flow auth, same schemas as the SPA. Owns the workflows that scale poorly through clicks: CSV roster import, install audits, feedback-PR orchestration, bulk submission download (merging `_manifest.json` conforming to `download-manifest.schema.json` with fields `{login, archive_sha, archive_branch, archive_branch_url, downloaded_at}` by student login instead of overwriting, resetting remote origin to a tokenless URL). The SPA links to it via "Copy CLI command" affordances. For **autograding**, the system supports two paths: lecturer-local (via CLI) or student-side (`github_actions`, synced via SPA).

### Central GitHub App

Is created via the App Manifest form at the SPA's `/setup` route. Frontend deploys automatically via `deploy-frontend.yml` (which aggregates public JSONs from orgs). The manifest includes organization-level `organization_administration` for Enhanced Billing - **`read` is what the code needs, `write` is what it declares**, held deliberately for org-scoped lockdown (see the permission-drift bullet). Note it is distinct from repository `administration`, which is what creates student repositories: the two share the label *Administration* in the App's UI and sit in different sections, so downgrading the wrong one breaks provisioning for every cohort. Account `starring` was removed on 2026-08-31 - nothing stars anything - so no account permission is set by hand any more. Setup verification and System Health validate permission metadata and probe the live billing endpoint. `setup-org.yml` performs the same preflight before creating organization state.

### Scripting Note

Do not use inline `node -e` scripts in workflow YAML. Extract to `scripts/`.

### Everything specific to one institution is in `deployment.yml`, and it is DATA.

Claim domains, timezone, hub owner/repo, App slug, control-repo name, archive prefix - a fork edits that file and nothing else; the product name *PXL Classroom* is the software, not the deployment, and stays. YAML rather than JSON or a module, because it is a file people are meant to open: every key carries a comment saying what it does and what breaks if it is wrong, which JSON cannot hold, and it matches how the repo already configures itself (`limits.yml`, `participating-orgs.yml`). A first pass shipped it as an ES module exporting constants, which is software wearing a config file's name. Two readers because the runtimes really differ: `lib/deployment.mjs` (`node:fs` + `yaml`, throws at import on a missing required key) and `frontend/src/lib/deployment.js` (the same file inlined by Vite with `?raw`, parsed with the `yaml` package the bundle already ships for the roster import) - one source file, no generated copy to drift. **An isomorphic module takes configuration as a PARAMETER and never imports it**: `lib/claim.mjs` is shared byte-for-byte with the browser, so a `node:fs` reader inside it breaks the bundle - `resolveClaimDomains(assignment, defaults)` requires its defaults and throws naming both readers when they are missing. And `deploy-frontend.yml`'s path filter names `deployment.yml`, because the SPA bakes these in at build time and a config the build reads but the filter does not name is a change that ships to `main` and reaches nobody - the claim-keys bug, one file over. `tests/deploy-paths.test.mjs` strips Vite query suffixes so `?raw` still resolves to the file the filter has to cover. ARCHITECTURE §2.1.

### One source of truth per cross-surface concern.

`lib/audit.mjs` exports `EXPECTED_APP_PERMISSIONS` and `MANIFEST_APP_PERMISSIONS` consumed by both CLI and `SetupView.vue`; `lib/gittree.mjs` is HTTP-stack-agnostic and shared by CLI, scripts, and SPA; `lib/control-layout.mjs` exports `CONTROL_SCAFFOLD_DIRS` (the ARCHITECTURE.md §5.1 control-repo layout), consumed by `lib/audit.mjs`'s scaffold check, `scripts/scaffold-control-repo.mjs` (called by `setup-org.yml`), and `control-repo-template/`. Don't fork these. `control-layout.mjs` must stay dependency-free - `setup-org.yml` runs the scaffold script without `npm ci`. `tests/scaffold.test.mjs` fails if any consumer drifts. Four more joined the list on 2026-08-25, each after the fork it prevents had already shipped a bug - see their own bullets below: **`lib/check-run-score.mjs`** + **`lib/check-run-annotations.mjs`** (reading a grade out of a check run; two byte-identical private parsers, both looking in the wrong place), **`lib/starter-sync.mjs`** (which files land directly and which raise a PR; the modal previewed one thing and the workflow did another), and **`lib/feedback-pr.mjs`** (classifying `POST /pulls`' 422s; three surfaces, three different answers). All four are dependency-free and isomorphic, re-exported into the SPA through `frontend/src/lib/*.js` the way `deadline.js` re-exports `effective-deadline.mjs`.

## Credentials, secrets and workflow safety

### Sign-in rests on a CORS proxy, and there is no substitute to switch to.

`github.com/login/device/code` and `/login/oauth/access_token` send **no** CORS headers - measured 2026-08-28, a **200** carries zero `access-control-*`, and GitHub's docs say "CORS pre-flight requests (OPTIONS) are not supported at this time" - so a browser can never call them directly and the proxy is structural. When corsproxy.io withdrew its free tier and 401'd everything, the recovery everyone assumes exists was measured and **does not**: allorigins, thingproxy and codetabs each silently issue a **GET** and hand back GitHub's HTML sign-in page (HTTP 200, wrong method, unparseable body - no error path fires anywhere). So the fallback had to be one nobody can withdraw, and it is `cors-worker/worker.js`, a PXL-owned Cloudflare Worker speaking the same `?url=` interface, which makes it a **secret change rather than a code change**. Rules that are load-bearing: the pair is **ordered, ours first** - `device_flow_proxy` in `deployment.yml` (the PXL Worker), then `VITE_CORS_PROXY_URL` (the third party) - because whichever answers sees the access token, and getting that backwards is not a style question (see the fallback-that-never-fires bullet below); an unusable entry is **skipped, not fatal**, because a typo in the fallback taking working sign-in down is the opposite of the point, and it is only a config error when nothing usable is left; nothing **throws at module scope** (that file is imported by the whole SPA, so a throw is a blank page - the `localToUtc` mistake in the worst place); and "the proxy worked" is decided by an **allowlist of GitHub's own device-flow error codes**, never by "did JSON come back", since corsproxy's withdrawal reply was well-formed JSON with an `error` field and accepting it would both skip the failover and show a student a billing notice as an authorization failure. `preferredProxy` keeps polling on whichever answered, or a dead primary is re-paid on every tick. The Worker's **target allowlist is the real control** (two exact URLs) - its `Origin` check is defence in depth only, since anything that is not a browser sets its own `Origin`. Both values are **baked in at build time**, so `deploy-frontend.yml` must pass every `VITE_*` name `auth.js` reads or the fallback ships to `main` and reaches nobody - the claim-keys bug, one setting over, and `tests/cors-proxy-config.test.mjs` now derives that list from the source rather than hardcoding it. Diagnosing note: **`curl` gets 403 from both** (corsproxy sits behind Cloudflare bot protection, the Worker enforces its Origin allowlist) - that is them working, and it will look exactly like an outage. INSTALL.md §9, ARCHITECTURE §10.2.1.

### Two entry points run with NO `npm ci`, and a bare import in either graph is a total outage.

`acceptance/broker-workflow.yml` runs `scripts/verify-invite-token.mjs` on a **public** repository holding `PXL_APP_PRIVATE_KEY` - installing dependencies there is supply-chain surface on a credential-bearing public repo, which is why it does not - and `setup-org.yml` runs `scripts/scaffold-control-repo.mjs` before any dependency exists (the reason `lib/control-layout.mjs` is dependency-free). So a bare specifier anywhere in either import graph is not a slow start, it is **`ERR_MODULE_NOT_FOUND` at the top of the script**: on the broker that is the signature check that authorizes acceptance, so **every student on every broker is refused**, and nothing local notices - both files import fine under Node here and `npm test` passes. The live trap is `#deployment`, which looks like a plain subpath import and resolves to a module importing `yaml`. `tests/dependency-free-entrypoints.test.mjs` walks both graphs, fails on any non-`node:` import naming the file that introduced it, and also asserts the two workflows still install nothing - so relaxing the rule has to be deliberate rather than a stale test. Same shape as the SPA outage above, pointed the other way: **a module that is fine in one runtime must not drag a loader into another that cannot have it.**

### `git add <dir>/` is FATAL when the directory is absent, and CONTROL_SCAFFOLD_DIRS keeps growing.

It exits **128** and stages **nothing** - not even the pathspecs that did match - so under `set -e` the step dies and everything the job already wrote to the checkout is discarded, with a script that succeeded and a red step nobody reads as data loss. `teams/` joined `acceptance-handler.yml`'s staging list on 2026-08-19 with group assignments, and git cannot store an empty directory, so **every control repo scaffolded before that date has no `teams/`** - surveyed live 2026-08-27, `PXL-Systems-Expert` and `PXL-2TIN-DevOps-2627` were both missing it with a published assignment still accepting, and `PXL-Automation-II`'s six exam acceptances predated the change so the next one would have been the first to hit it. Seven sites had the shape; `retry-acceptance.yml` was the one that mattered, because it is what a lecturer reaches for when a student is **already** in trouble. **The fix is `mkdir -p` before the add, not a `[ -d ]` guard around it**: `git add` on an existing-but-EMPTY directory exits 0 and stages nothing, so creating it first is a no-op when there was nothing to commit and correct when there was, where a conditional would silently skip a directory that did have content. It also needs no shell function - and a helper defined in one `run:` block **does not exist in the next one**, which is a mistake this repo has now actually shipped. `tests/workflow-hardening.test.mjs` requires the `mkdir -p` **within four lines** of the add: the first version checked the whole file and passed against the very bug it was written for.

### A single-org dispatch disabled the nightly for EVERY org, and left nothing red behind.

The minimal-minutes design lets `daily-activity.yml` switch **itself** off when no assignment is active, and only a publish switches it back on - which makes `gh workflow disable` a statement about the whole hub, so only a run that looked at the whole hub may reach it. Neither disable job checked. `active_count` is summed over **the orgs that run covered**, and `workflow_dispatch` takes an `org` input that narrows the matrix to one: on 2026-08-26 a drill dispatched `-f org=PXLAutomation`, whose single published assignment had just passed its deadline, reported `active_count == 0` and disabled the nightly everywhere - **four days before a live exam in `PXL-Automation-II` that the run never opened**, which would therefore never have been finalized. `disable-when-empty` had the same shape one step earlier (a typo'd or non-participating org name yields `orgs == '[]'`, a fact about the *input*), and `deadline-sentinel.yml` carried the same job and the same gap. All three are now gated on `github.event_name != 'workflow_dispatch' || inputs.org == ''`: a scoped run may collect, finalize and report, but may not make a statement about the hub. **The reason this one nearly escaped is worth more than the bug**: every other finding this session announced itself as a red run, and a workflow that disables itself produces no failure at all - it was found only by listing the workflows afterwards. `tests/workflow-hardening.test.mjs` pins the class: any job running `gh workflow disable` in a workflow that takes an `org` input must prove the run was not scoped.

### The sentinel's `Finalize now` had never run, and 403'd the first time a deadline reached it.

It dispatches `daily-activity.yml` with the job's own `GITHUB_TOKEN`, and the `watch` job declared no `permissions:` - so it inherited the workflow's `contents: read` and could not dispatch anything (`Resource not accessible by integration`, `x-accepted-github-permissions: actions=write`, run 33013299689). The step is gated on `fired == true`, so **only a sentinel that actually reaches a deadline gets there**: same shape as `sync-starter-code.yml` and `open-feedback-prs.yml`, which had never run either. A `workflow_dispatch`-only path that nothing exercises is untested code, and a green Actions tab says nothing about it. Nothing was at risk - writes still stopped at the instant and the nightly still finalized, the documented degradation - but the job went **red at every deadline**, and a workflow that is red whenever it does its job is one nobody reads. A **job-level `permissions:` block REPLACES the workflow-level one** rather than merging, so `contents: read` has to be restated or the checkout loses it. `tests/workflow-hardening.test.mjs` pins the class, not the instance: any step dispatching a workflow with `GITHUB_TOKEN` needs `actions: write` in effect, whether through `github-script` or `gh`; a step passing a foreign token is exempt, because an App token's permissions are its own.

### Declaring a permission is not being granted it, and nothing could tell you which orgs had granted it.

Widening the App leaves every existing installation on the **old** set until that org's owner clicks *Review request*, so `check-app-declaration.mjs` passes, `GET /apps/{slug}` shows the new permission, and the feature is dead on the orgs nobody chased - with nothing red anywhere. `GET /orgs/{org}/installations` answers only for an owner **of that org**, so verification by hand stalls exactly where it matters: on the 2026-08-25 `members` + `organization_administration: write` rollout, 7 of 11 orgs could be confirmed and **4 could not be seen at all**. `scripts/check-installation-approvals.mjs` walks `GET /app/installations` - every org in one call, App JWT only, hence `environment: provisioning` on the `installation-approvals` job in `weekly-usage-report.yml`. Load-bearing details: it compares against the **App's own live declaration** (`GET /app`, read as the App so no slug can name a different one) rather than `MANIFEST_APP_PERMISSIONS`, because the question is "has this org accepted what the App asks for *today*" and a constant bumped first would paint every org amber for a permission nobody had been asked to approve yet; the comparison is `permissionMeetsRequirement`, not equality, or a **downgrade** (`read` where `write` is declared - the actual 2026-08-25 case) reads as approved; it **walks past page 1**, because "every org has approved" off the first 100 installations is a confident all-clear from a truncated read; and a missing credential, an unreadable API or a non-array body prints **`DID NOT RUN`** and exits 0 rather than a false all-clear - a check that quietly does not run looks exactly like a passing one. `lib/app-jwt.mjs` holds the one JWT minter, extracted from `scripts/fetch-pages-data.mjs` the moment a second caller needed it: two copies of a signing routine drift into an intermittently invalid credential rather than a visible error. **Not every installation is ours.** The App is publicly *listed* - hub-and-spoke requires it, because each course org is a separate organization and a private App installs only on the account that owns it, so making it private would uninstall it everywhere - which means any GitHub account can install it, and an unrelated org did on 2026-08-22. The check therefore sorts installations three ways against `participating-orgs.yml`: a participating org that has not approved **fails**, a participating org with **no installation** fails (nothing else in the system notices, and ADMIN.md §7 carried it as a manual checklist item), and a third-party installation is **named as a notice but never fails** - a permanent false positive beside the real ones is how a weekly check stops being read. Two distinctions it must keep: an **empty** `orgs:` list is an answer, not an unreadable file (the branch really does start `orgs: []`, and conflating them makes every installation third-party and silences every real gap), and an **unreadable** list treats everything as participating - over-reporting, never silencing. Matching is case-insensitive but reporting uses the file's own spelling, or a lecturer is sent looking for an org that as spelled does not exist. `tests/installation-approvals.test.mjs`, ADMIN.md §6.6.

### No value is composed into a script, anywhere.

`${{ }}` is substituted into the script *text* before bash or the JS parser sees it, so the rule is not "is this value attacker-reachable" but "is this a literal I wrote". Everything else goes through `env:`. The old guard named only `github.event.*` and `client_payload`, and sixteen sites survived it - `gh api users/${{ inputs.github_login }}` in `retry-acceptance.yml` (a job holding the App key that provisions for an arbitrary login with the deadline bypassed) and `setup-org.yml` putting an **installation token and a dispatch input into the same line**, with the org validated in the *next* step. `tests/broker-injection.test.mjs`'s `isConstant` now allowlists only run-scoped facts GitHub sets itself (`github.repository`, `github.run_id`, `runner.*`, `env.*`, literals) and covers composite `action.yml` files too. `retry-acceptance.yml` and `setup-org.yml` validate their inputs as their first use, and `setup-org.yml` passes credentials via `http.https://github.com/.extraheader` rather than embedding them in a remote URL.

### A concurrency group serializes only against the SAME STRING, so two workflows that touch one thing must build it identically.

`acceptance-handler.yml` keys on `team_hint || github_login` and `retry-acceptance.yml` keyed on `github_login` alone. Those coincide for an individual assignment and diverge for a **group** one - so a lecturer's retry and a student's join on the same team ran under different groups, neither waited for the other, and both could read the manifest at n-1 members and `members.push()` past `max_team_size`. Same bug as the team-hint mismatch, reached from the other workflow. The retry **cannot discover the team itself** (a concurrency group is evaluated before any step runs), so it takes an optional `team_slug` the lecturer supplies from the tracking page; it is used **only** for the key and deliberately not passed to the acceptance, so it cannot move a student. `tests/workflow-hardening.test.mjs` asserts the shape - both must prefer a team key and both must fall back to the login - rather than the literal.

### The master App key was on ELEVEN PUBLIC REPOSITORIES, and scoping the token never touched it.

`publish-assignment.yml` wrote `PXL_APP_PRIVATE_KEY` as a repo secret onto every `broker-<id>`, and brokers are created `--public` - counted live 2026-08-31, **11 across 8 orgs**. What that key mints, read straight from `GET /apps/pxl-classroom-provisioner`: `administration: write`, `organization_administration: write`, `members: write`, `secrets: write`, `workflows: write`, `contents: write`, on **every org the App is installed on**. `workflows` + `contents` is arbitrary code execution in every repository in every course org; `administration` deletes every student repo and every archive. The path was not exotic - anyone with admin on **one** course org pushes a workflow to that org's broker and reads the secret out, so a lecturer scoped to one course held the keys to all twelve. **The broker workflow's careful `owner:`/`repositories:` scoping was never relevant**: that narrows the minted *token*, and the *secret* is what is stored. The brokers now have their **own App** - installed on the hub repository alone, holding `contents: write` alone, which is exactly what `POST /dispatches` requires and no more (verified against GitHub's permissions reference); it deliberately has no `actions: write`, so a leaked broker key cannot dispatch a hub workflow either. Four things hold it: publish **fails closed** when `PXL_BROKER_*` is unset rather than falling back to the App key (a fallback makes the whole change cosmetic); publish **mints a token with it first**, so a broken broker App is a red publish run rather than a silent failure at the first student's acceptance; publish **deletes** the legacy secrets from the broker **after** pushing the new workflow, never before (the old workflow still reads them, and republishing *is* the migration - ceasing to write a secret does not delete it); and `tests/workflow-hardening.test.mjs` fails if either file names the provisioning credential again or the removal moves above the push. INSTALL.md §10, ARCHITECTURE §4.3.0.

### A fallback that is never reached protects nobody, and the CORS proxy pair was in the wrong order.

The PXL-owned Worker shipped as `VITE_CORS_PROXY_FALLBACK_URL` with corsproxy.io primary - and a fallback only fires when the primary *fails*, so once corsproxy.io was working again on a paid key the third party was back on the path of every sign-in. Measured 2026-08-31 by loading the deployed SPA and reading its **own resource timing**: the device-code request and all three `access_token` polls went to `corsproxy.io` and the Worker was **not contacted once**. Whichever proxy answers sees the `device_code` and the **access token**, and a lecturer token reads the private control repo - roster names, student numbers, institutional addresses. The Worker is primary now and lives in **`deployment.yml` as `device_flow_proxy`**, not a secret: it is baked into a public bundle and readable by anyone who opens the page, so calling it secret bought nothing while hiding the ordering behind "which of two similarly-named secrets holds which value" - which is exactly how it stayed wrong. `VITE_CORS_PROXY_URL` remains as the **second** entry with **no hardcoded default**, because a default meant deleting the secret silently reinstated corsproxy.io. Verified end to end against the real Worker: a device code minted through it, corsproxy.io absent from the timing entries. Nothing else changed - unusable entries are still skipped rather than fatal, nothing throws at module scope, and the GitHub-error allowlist still decides "the proxy worked". `tests/cors-proxy-config.test.mjs` pins the order against auth.js's source; `tests/cors.test.mjs` stubs `deployment.js` because what it tests is the failover, not the reader. INSTALL.md §9, ARCHITECTURE §10.2.1.

### The App-permission drift check only ever looked one way.

`missingManifestPermissions` walks `MANIFEST_APP_PERMISSIONS` and reports what the App **lacks** - a feature that cannot work. Nothing walked the other direction, so a permission the App holds and no code needs was invisible for as long as it existed. Five looked excess on 2026-08-31; **checking each against the code rather than the changelog cut it to three**, and the two survivors are the interesting part. `starring: write`, `plan` and `organization_plan` were genuinely dead and are gone (nothing stars anything; the other two gate only the `plan` object on `GET /user` and `GET /orgs/{org}`, and nothing reads it). `members` was called dead on the strength of `roster_mode: org_member` being deleted - **wrong**: that removed the enrolment use, not the diagnostic one, and `unfreezableAcceptorsFinding` still lists `GET /orgs/{org}/members?role=admin`. Dropping it would not even have gone red, since an unreadable owner list yields *no* check rather than a failing one. `organization_administration: write` was called excess against a manifest asking for `read` - also wrong in effect: ARCHITECTURE §11.2.1's org-scoped lockdown needs write and named this permission as its blocker, and the App already had it, so the feature was unblocked and the doc was stale. Both are now declared at the level the App holds, deliberately, with the reason in `lib/audit.mjs` - because a reduction reaches twelve installations instantly while restoring one needs twelve owners to approve. That asymmetry is the whole reason to check before removing. What remains true is the shape of the finding - it is the blast radius of the bullet above, and `members: write` alone adds and removes org members. `excessDeclaredPermissions` is the reverse comparison, it counts an excess **LEVEL** as excess (a name-only check reports `organization_administration` as clean), and it **tags** account-level names rather than skipping them, because `starring: write` is precisely what hides in that exemption. The remedy is deliberately two-sided - narrow the App, **or** add the permission to the constant with a comment naming the caller - and the second is not a cop-out: `actions_variables: write` turned out to be genuinely required by publish's five `gh variable set` calls and simply never written down. It **fails** rather than warns, because both directions are actionable. ADMIN.md §3.2.

### The privacy scanner never ran at the moment of publication.

`pages/scan.mjs` is a good gate and it was invoked from exactly one place - `pages/action.yml`, which runs when an ORG's control repo regenerates its own `public/`. `deploy-frontend.yml`, the workflow that actually puts bytes on a world-readable site, had **zero** references to it, while `scripts/fetch-pages-data.mjs` copies `public/i/*.json` and `public/teams/*.json` **verbatim** out of twelve control repos into the bundle. Anything that reached a control repo's `public/` by another route - hand-edited, left by an older generator, or from a run where the gate was skipped - published unchecked. The scan now runs over `frontend/dist/data` before `upload-pages-artifact`. **Scoped to `dist/data`, not all of `dist`, deliberately**: that is the aggregated externally-sourced half and the only part of the artifact this repo does not author, while the rest is the SPA bundle and `schemas/*.schema.json`, which legitimately contain `"student_number":` - scanning them would fail every deploy on the field-name rules and the gate would be off within a week. Verified both ways before shipping: clean against all 13 live published files, and blocking on a planted roster record.

### A guard written as a LIST of files covers what somebody remembered.

`tests/workflow-hardening.test.mjs` named three workflows by hand as needing the `[bot]` dispatch guard, and the list was wrong four times over: `sync-starter-code.yml`, `open-feedback-prs.yml`, `reconcile-registry.yml` and `weekly-usage-report.yml` all hold `PXL_APP_PRIVATE_KEY`, all reach `workflow_dispatch`, and none had it - the first two also mint a token for an **arbitrary org taken from their own input**. The rule is derived now: dispatchable + reads a hub credential ⇒ guarded, **unless** another workflow genuinely dispatches it (a legitimate machine caller the guard would break). Two subtleties that took a run each to find - the exemption must be computed from **real dispatch calls** (`gh workflow run <file>`, the REST `workflows/<file>/dispatches` path, a `workflow_id:`) and never from the filename merely appearing, since half these files name each other in comments and matching those exempted almost everything; and a guard **upstream in the `needs:` graph** is real protection, which is how `deadline-sentinel`'s `watch` job is covered through `arm`. The same sweep generalised action pinning from per-action tests to **every `uses:`**, which is what had let `actions/setup-node@v4` survive in those same two files - after the App token is minted, with the key in scope.

### `shellcheck` came from npm, and every version of that package unpacks with unfixed-critical `decompress`.

Zip Slip, arbitrary file write and hardlink creation on extraction, advisory range `*`, package unmaintained - there is no patched version to move to, and the only npm escape is `shellcheck@1.1.0`, which unpins the binary to whatever "stable" meant at publish time and trades a supply-chain hole for exactly the version drift `scripts/lint.mjs` exists to prevent. It is fetched directly now, the same way actionlint already was, and pins **harder** than before: `^4.1.0` pinned the *wrapper*, `SHELLCHECK_VERSION` pins the *tool*. The version chosen is `0.11.0`, which is what the wrapper was already resolving to, so no finding changed. It is **checksum-verified** against `SHELLCHECK_SHA256`, a mismatch is fatal with no retry and no fallback, and a platform with no pinned digest **fails** rather than downloading unverified. Two platform traps, both found by running it: Git Bash's `tar` is **GNU tar**, which cannot read a zip at all and reads `-C C:\...` as a *remote host* (`Cannot connect to C:`), so Windows extracts with PowerShell's `Expand-Archive` and both paths run with `cwd: TOOLS` and a bare filename; and `.tar.gz` is used rather than the `.tar.xz` the project also publishes, because xz needs liblzma and bsdtar is not guaranteed to have it. `npm audit` is **0 vulnerabilities** in both trees. **actionlint went the same way in the same pass**, and it was the worse of the two: it was fetched by piping a script from `raw.githubusercontent.com/.../main` - a *mutable branch* - straight into bash, with no pin on the script and no checksum on the binary it then fetched. That is a worse mechanism than the npm package this change removed, sitting two functions away from it, running on every developer machine and every CI lint job. Both now go through one `fetchPinnedTool` with digests for all five platforms; `tests/lint-parity.test.mjs` fails on `raw.githubusercontent.com`, on anything piped into a shell, and on a digest map that does not cover every platform the resolver can select - **stripping block comments as well as line comments**, because the `/** */` explaining the rule quotes the `| bash` it forbids and a line-only strip fails against its own prose.

### GitHub's secret scanning cannot see the credentials this system mints itself.

Push protection is on and blocks `ghp_`, which is why `.env.test` is a smaller problem than it looks - but the invitation link's PKCS#8 P-256 key and the claim key have no provider prefix and nothing for GitHub to key on. `tests/tracked-secrets.test.mjs` scans **`git ls-files`**, not the filesystem: the question is not "is there a secret on this machine" (there is, deliberately) but "is one TRACKED", which is the thing that travels. It reuses `lib/public-text.mjs`'s rule rather than writing a second one, so the repo scan and the Pages publish gate cannot disagree about what a private key looks like. Writing it immediately found three shape-matches, all read before being allowlisted and all genuinely inert - and one of them, `E2E_CLAIM_KEYPAIR` in the e2e fixtures, is a **real P-256 private key**, safe only because it is not the production one. So the exemption carries its own assertion: a separate test fails if the live claim public key ever appears in that fixture, which is what would fire the day somebody pastes the production key in to make a test pass.

### Hub credentials only run from `main`.

`workflow_dispatch` runs the workflow file from whatever ref it is given, and `participating-orgs` has deliberately lighter protection (ARCHITECTURE §5.5) - together a way to run hub code at a chosen ref with the App key in scope. Every job referencing `PXL_APP_PRIVATE_KEY` or `PXL_INVITE_SIGNING_KEY` therefore declares `environment: provisioning`, whose deployment branch policy is `main` only; a job naming an environment does not start when the ref is outside the policy, so this holds regardless of where the secret lives. Every dispatchable workflow that reads a hub credential additionally rejects a `workflow_dispatch` from a `[bot]` actor as its FIRST step - lecturers dispatch as themselves, a stolen broker credential arrives as `<slug>[bot]` - unless another workflow legitimately dispatches it, or a guarded job sits upstream in its `needs:` graph (see the derived-guard bullet above; the hand-written list of three missed four workflows). Never put these secrets in workflow-level or job-level `env:`. Both keys are **environment** secrets with no repository-level copy, so a job that omits `environment: provisioning` cannot read them at all; `PXL_APP_CLIENT_ID` stays a repo secret because a client id is public by design. `tests/workflow-hardening.test.mjs` enforces all three. See ARCHITECTURE §4.3.4.

### A per-org cap is not a global cap, and the sentinel's was the only unbounded matrix.

`find-armable.mjs`'s `MAX_SENTINELS` (8) reads like a budget for one cron firing - its own comment cites the Team plan's 60 concurrent jobs - but the `arm` job is a **matrix over orgs**, so it bounds one org's list and `aggregate-armable` then flattens all of them into a single `watch` matrix. At 22 participating orgs that is a ceiling of **176** concurrent jobs, and it gets worse with every org added. Each sentinel holds its runner slot for up to **4h45m**, so saturating the budget starves `daily-activity` - the nightly this workflow exists to degrade *to*. Failing over into the thing you broke is not a fallback. The global bound is now **`max-parallel: 8` on `watch`**, which is invariant to the org count: 22 orgs or 100, at most 8 sentinels hold slots at once. Capping *concurrency* rather than slicing the list is deliberate - nothing is silently discarded, and a sentinel that starts after its instant is not wasted either, because the wait loop breaks immediately and still runs Phase 1, so writes stop, just without the precision. Every other org-fanout matrix in the repo (`daily-activity`'s three, `reconcile-registry`, `regenerate-dashboard`, `weekly-usage-report`) already carried one at 4; `watch` is 8 because it is the only time-critical one. `tests/deadline-sentinel.test.mjs`.

### Credentials never appear in a git command line.

`preserve/preserve.mjs` logs every command it runs, on the **public** hub, and built `https://x-access-token:<token>@github.com/...` into it; Actions masked it only because `create-github-app-token` registers the value. It now passes the token through `GIT_CONFIG_KEY_0`/`http.<host>/.extraheader`, as do `setup-org.yml` and `publish-assignment.yml` - a URL-embedded credential also lands in `.git/config` and in every error message git prints. `tests/sweep-correctness.test.mjs` scans for both shapes.

### Two workflows never ran once, and no cron was there to go red.

`sync-starter-code.yml` and `open-feedback-prs.yml` were the only two on the floating `actions/create-github-app-token@v1`; **v1 has no `client-id` input** - it takes `app-id` - so the *first* step of both failed with `Input required and not supplied: app-id` and neither workflow ever reached its script. Found in a live run on 2026-08-25, not by any check here: the failure is inside the action's own input validation, which sits outside every schema, lint and test in this repo, and both are `workflow_dispatch`-only, so nothing nightly ever turned red. Behind it sat a second fault in both scripts - `loadYaml(<file text>)` with no `await`, where `loadYaml` takes a **path** and is `async`, so the assignment was a `Promise` and every field read `undefined`: `sync-starter.mjs` died on "Assignment has no template repository configured", `open-feedback-prs.mjs` on "does not have feedback_pr enabled". They were also the only two still on `node-version: "20"` - the pair was written at a different time and swept by nothing since. `tests/workflow-hardening.test.mjs` now requires every App-token step to be **pinned to one SHA** across the repo and to mint with `client-id` (never `app-id`), so "these are the right inputs" is one fact rather than a per-file guess. **The lesson is not the two bugs, it is that running the thing found both in a minute and no amount of reading had**: a `workflow_dispatch`-only workflow nothing exercises is untested code, and a green Actions tab says nothing about it.

### `gh` writes API errors to STDOUT, so a captured value is non-empty on failure.

Measured 2026-08-26: `gh api users/does-not-exist --jq .id` exits 1, puts `{"message":"Not Found",…,"status":"404"}` on **stdout** and only `gh: Not Found (HTTP 404)` on stderr. So `VAR=$(gh …)` followed by `[ -z "$VAR" ]` is not a check, it is a guard that can never fire - `retry-acceptance.yml` had exactly that, and only Actions' default `bash -e` stopped a JSON error blob being written into `$GITHUB_OUTPUT` as a student's account id; what it did cost was the message, so a lecturer who misspelled a login got `gh: Not Found` instead of being told which login. The rule is **guard on the exit code** (`if ! VAR=$(gh …)`, or `|| …`) and then **validate the shape** - `--jq` prints the string `null` for a field GitHub omits, which is non-empty too. `tests/workflow-hardening.test.mjs` fails on any capture that assumes success from the text. This cost three false readings in one session, including reporting five healthy migrations as mismatched and repeating a workflow's own guess back as a diagnosis, so it is worth knowing before writing the next one-off `gh` check.

### The CI grading sync could never have worked: the App does not declare `checks`.

Reported live 2026-08-26 by a lecturer on `python-hacking-intro` - *"CI results sync failed for 1 student(s) due to API errors. Nothing was saved; try again later."* - with **4,995 of 5,000** API calls still available, which is what ruled out the rate limit the wording implied. Both endpoints the sync uses, `GET /repos/{o}/{r}/commits/{ref}/check-runs` and `GET /repos/{o}/{r}/check-runs/{id}/annotations`, are gated by the **Checks** repository permission (GitHub's "Permissions required for GitHub Apps" reference; the endpoints' own pages document only the classic `repo` scope, which is why this was missable). The Admin Panel authenticates with a **user-to-server** token from the App, and that is capped by what the App declares - so it 403s for every student, in every org, always. `checks: read` is now in `MANIFEST_APP_PERMISSIONS`, which makes `check-app-declaration.mjs` fail until the App owner adds it and each org approves (RUNBOOK.md §3.11) - the drift is real and the check is meant to see it. Two rules the fix carries: a **403/401 gets its own sentence** naming the permission, because "try again later" is advice that can never come true and a lecturer will retry for ever; and a student with **no commit on record** is no longer counted as an API failure - `targetSha` was undefined, the URL was built with `undefined` in it, and GitHub's 404 was reported as an API error rather than as "nothing to grade yet".

## Invitations and acceptance

### `rejected:cap-reached` promised a queue that Wave 8 deleted.

The message ended *"Acceptance queued for lecturer review."* and **nothing queues a rejected acceptance, nothing retries one** - the minimal-minutes redesign replaced the queue with synchronous provisioning, and no code anywhere reads a cap-reached rejection afterwards. `acceptance-handler.yml` writes `reject_reason` straight into the org's instructor tracking issue, so this is what a lecturer reads while deciding what to do: it left them waiting for a background process that does not exist instead of raising the cap. C4 exactly. Found by **running `accept.mjs` against a replica of the live exam's config** rather than reading it - the same three cases a real deadline produces (accept now, accept late, cap full) each took one command, and the other rejection strings turned out to be honest and actionable. `tests/accept.test.mjs` now fails on any rejection message promising a queue, a review or an automatic retry, and requires the cap message to name the action that unblocks the student.

### The invitation status line could never say "Cap reached".

`InvitationShare`'s status is the **student-facing truth**, gated on the same conditions `AssignmentView` uses to decide whether to show an Accept button - a lecturer must not read *"Live"* over the page telling students *"Registration cap reached"*. Its cap branch compares `accepted_count` against `max_acceptances`, and **two of its three callers never supplied `accepted_count`**: `AdminView` builds the object field by field (its own comment already warns that *"a field omitted here is invisible to the share block"* - about the invite fields, having missed this one), and `DashboardView` passes a dashboard entry, which carries `accepted` under a different name and had no cap at all. `Number(undefined) || 0` is **0**, so `accepted >= cap` was permanently false and both surfaces reported *"Live - students can accept now"* over a full cohort. Fixed on both sides, because either alone stays fragile: the callers pass the number they already hold (`AdminView` from the cohort card's dashboard read, the dashboard from its entry) and `buildDashboardEntry` now carries `max_acceptances`; **and the component treats an absent count as UNKNOWN rather than zero**, saying the link is live *"while places remain"* instead of promising room it cannot verify - so a caller that forgets again degrades to a hedge, not to a false all-clear. Nulls stay nulls: an assignment with no cap has no cap, and an unreadable cohort report is unknown rather than zero. `tests/invitation-share-status.test.mjs`.

### A green retry run is not a repository, and the panel announced one anyway.

`accept.mjs` exits **0** for every `rejected:*` outcome on purpose (a student who is not on the roster is the system working, and painting the hub red for it teaches people to ignore red) - so `retry-acceptance.yml` concludes `success` when it **refused**, and none of its follow-up steps fire either, leaving a green run that says nothing. `startRetryWatch` read that conclusion and toasted **"Retry succeeded: repository is live."** with a link to a repository that does not exist. The case that produces it is the most likely reason to retry at all: a student the roster rejects, or a misspelled login. The fix is the rule publish liveness already follows - **verify the claim, not the run that was asked to make it** (`acceptanceCardIsLive` fetches the card rather than trusting the assignments index): a `GET /repos/{org}/{repo}` decides between "live" and "the retry ran, but @login still has no repository". It deliberately **does not guess which rejection** - the outcome string is not on the run summary, and naming the wrong cause is worse than naming none (the provisioning wait screen's rule). `tests/retry-outcome-honesty.test.mjs` pins the ordering and fails if the success toast moves back above the check. Related and still true: under `roster_mode: claim` a retry carries no `claim-payload`, so a student who never bound is refused - correctly, since a lecturer dispatch must not bypass the gate - and this toast is what now tells the lecturer so.

### Two wire formats share one vocabulary at two sizes, and merging them is the trap.

`lib/acceptance-signature.mjs` and `lib/invite-token-format.mjs` sit side by side and each declare `SUBJECT_BYTES`, each define `subjectsMatch`, each carry an `encodePayload`/`decodePayload` pair - identical names, **8 bytes against 16**. Nothing pinned that, so a sweep for duplicated logic finds two byte-identical-looking `subjectsMatch` bodies and unifies them, silently destroying one format. What makes it dangerous rather than untidy: both truncate the **same sha256 of the same input**, so the 8-byte digest is an exact **prefix** of the 16-byte one (measured) - a merged comparison agrees on every byte it looks at, and **the length check is the only thing holding the two apart**, which is precisely what a value-equality test would not assert. Neither number can move: 8 is what keeps a signed acceptance title inside the 256-character budget for a real assignment id (§4.3.2 - the JSON payload it replaced hit 253 before a team hint), and 16 is baked into `PAYLOAD_BYTES = 26` and the 35-character half of `TOKEN_PATTERN`. `tests/subject-digest-sizes.test.mjs` fails on a unified constant, on either module importing the other's subject vocabulary, and on the length check being dropped. This is the inverse of the fork rule and worth knowing before the next dedupe: **identical names over different constants are not a fork, and the guard's job is to stop the merge, not to perform it.**

### The team hint is a lock, not a label.

The acceptance concurrency group is keyed on `client_payload.team_hint`, derived from the issue *title*, because that is all the hub has before it can read the body - and per-team serialization is the only thing guarding `max_team_size` (§5.6). Nothing compared the two, so a title saying `team:decoy` with a body saying `team_slug: popular-team` serialized against one team and wrote to another; two in parallel both read the target at n-1 and both appended. `lib/team-payload.mjs`'s `teamHintMatches` refuses a mismatch, `acceptance-handler.yml` passes `TEAM_HINT`, and both-empty is the individual case.

### Nonce revocation fails closed.

`verifyInviteToken` used `if (nonce && ...)`, so a broker with no `INVITE_NONCE` variable accepted **every token ever issued** for that assignment, including ones a `regenerate_invite` had just retired - and a publish that died between creating the repo and setting its variables produced exactly that. An absent nonce is now `reason: "no-nonce"`, and `scripts/verify-invite-token.mjs` names it as a deployment fault distinct from a forged token. The value is also **trimmed**: it comes from a repository variable a human can edit, and a trailing newline superseded every live link behind a deliberately generic student-facing message. `tests/invite-nonce-revocation.test.mjs`.

### A public broker accumulates whatever anyone writes into it, and nothing was looking.

Issues are the trigger mechanism, so a broker is a public repository anyone can open an issue on - that is not a flaw. What had no owner is everything that lands there and is **not** an acceptance: the job-level `if` skips those before a runner is allocated (deliberately), so nothing redacts, closes or notices them. Found live 2026-08-31 on `PXL-2TIN-CloudEssentials-2627/broker-test-groepsopdracht-2`: two issues, open, unlocked, months old, one carrying a student's GitHub login in its body. Diagnostics Tier 4 now reports them, reusing the issue list the exposure sweep **already fetched**, so it costs nothing extra. **Surfaced rather than auto-closed, on purpose**: closing them from the broker means running a job for every non-acceptance issue, which trades away the deliberate "a non-acceptance costs no runner at all" property and hands anyone a way to make runs happen on demand. Never a `fail` - a stray issue is untidy, not an outage, and a permanent red beside real findings is how a health panel stops being read.

### No attacker-controlled text may reach a shell on a broker.

A broker is public, holds the broker App's private key as a repo secret, and has issues enabled - so any GitHub account can fire its workflow. `BODY="${{ github.event.issue.body }}"` in a `run:` block there was arbitrary code execution against the App key, reachable by anyone, against every participating org (ARCHITECTURE §4.3.1). `${{ }}` is substituted into script *text*; `env:` is not. `tests/broker-injection.test.mjs` enforces three things: no workflow interpolates `github.event.*`/`client_payload` into any `run:` or `github-script` body (repo-wide, not just the broker); the broker never reads the issue *body* (it forwards the issue number, and `scripts/read-team-payload.mjs` validates it in the hub via `lib/team-payload.mjs`, with no `client_payload` fallback left in `acceptance/action.yml`); and the broker reads the issue *title* only through `env:`, only to match `^team:<slug>$`, and only as `client_payload.team_hint` - a **concurrency key**, never an authoritative value. The hint cannot be dropped: the concurrency group is evaluated at dispatch time, before the body can be read, and per-team serialization is what guards team capacity without a distributed lock.

### Signed invitations are what stop outsiders triggering work.

Acceptance fires on a public event on a public repo, so anyone can ring the doorbell - star, fork, issue, comment, wiki edit are all open to any account, and none prove authorization. The roster gate authorizes, but only *after* the broker minted an App token and the hub cloned the private control repo. `lib/invite-token.mjs` (Node) + `lib/invite-token-format.mjs` (isomorphic, crypto-free, bundled by the SPA) move the first check to the edge: the broker checks out the public hub, verifies an Ed25519 signature against `acceptance/invite-keys.json`, and only then mints. **Asymmetric because the verifier is public** - an HMAC would put the minting secret on every broker; encryption is wrong too, since the broker cannot hold a decryption key and ciphertext replays fine on a public channel. The token rides in the issue **title** (122 chars, budget 256) so the broker never reads the body. `vars.INVITE_ENABLED` and the `pxl-accept:` prefix are job-level `if` checks, evaluated before a runner is allocated. `tests/invite-token.test.mjs` pins that no step before verification references a secret, plus canonical encoding (26 and 64 bytes do not divide into 6-bit groups, so the last char of each part carries discardable bits - without the check one link had several spellings). The token is **not** secret against sharing: that risk is accepted and bounded by `max_acceptances` (ARCHITECTURE §15). It must never reach Pages output. Republish reuses the nonce so live links survive a repair; `regenerate_invite: true` rotates it and retires them. `INVITE_KID` rotates keys. See ARCHITECTURE §4.3.2, INSTALL.md §3.1.

### A closed issue on a public repo hides nothing.

The acceptance issue's TITLE carries the signed invitation, so the first student to accept used to publish the assignment's token to anyone who looked at the broker's issue list or searched GitHub for `pxl-accept:` - defeating §4.3.2 outright and, because the acceptance card is named `sha256(invite_token)`, making the card and its teams file public too. Three steps close it and none is optional: the **broker redacts the title** on *both* the accepted and the rejected path (`gh issue edit --title`, `issues: write` only, so no extra credential on a public repo - the reject path matters because `wrong-assignment` means a *live* token for another assignment landed there); and **System Health Tier 4 sweeps** the broker for surviving `pxl-accept:` titles, which is what catches an `INVITE_ENABLED=false` that skips cleanup or a dead run. The sweep runs even when the assignment's own `invite_token` is absent or malformed. **The third step - the hub deleting the issue - was removed: an installation token cannot delete an issue at all, see the bullet below.** `tests/invite-exposure.test.mjs` pins what remains.

### Redaction, deletion and a sweep are all AFTER the fact - the fix was to stop publishing a credential.

The three steps above hide the browsable copy of the title; they cannot touch the `opened` event, which GitHub emits before any of them run and GH Archive mirrors permanently. Measured 2026-08-25: `curl -s https://api.github.com/repos/<org>/<broker>/events`, unauthenticated, returned a full still-valid `pxl-accept:` token on an issue that had **already been deleted**, for a live `roster_mode: open` assignment. Hiding it is not available - every student-initiated trigger on a public repo emits a public event and there is no private transport without self-hosting - so the title had to stop being *sufficient*. The link now carries a **P-256 private key** (`invite_key`, 184 base64url chars, `lib/acceptance-signature.mjs`), the browser signs an assertion naming the student's own account, and both the broker and the hub compare the signed `github_id` to the issue's author. **P-256, not Ed25519**: Ed25519 only reached WebCrypto in Chrome in May 2026, so one student in five could not have signed at all. Load-bearing consequences: **`linkSecretFrom` is the single answer to "which field is the link"** (`invite_key` migrated, `invite_token` not) and is consumed by `pages/generate.mjs`, `AdminView`, `InvitationShare`, `lib/diagnostics.mjs` and the e2e fixture - three independent readers is the shape that forked `diffRosters`; the broker takes the signed path only when it has **both** a title and `INVITE_PUBKEY`, so republishing a broker before a keypair exists cannot reject a whole cohort; and **`PUBLIC_TEXT_RULES` gained a second rule**, because the first is keyed on the token's `<35>.<86>` shape and could not see a key at all - it anchors on the PKCS#8 P-256 header (36 chars, identical in every key ever minted, so a partial paste is caught too) and deliberately does **not** match the public half, which lives on a public broker by design and would be a permanent false positive beside the real findings. `tests/acceptance-signature.test.mjs`, `tests/public-text-token-shape.test.mjs`, ARCHITECTURE §4.3.2.

### The team hint is appended AFTER signing, so the verifier has to cut it off - and for months it did not.

`verifyAcceptanceTitle` split `github.event.issue.title` on `.`, which handed the signature back as `<signature> team:alpha` - not base64url - so **every group acceptance on the signed path was rejected as `malformed`**, on every group assignment, while individual acceptance worked perfectly. Nothing caught it: not one test had ever verified a title carrying a hint, and the e2e fixture's mocked broker returned 201 for any string at all. The fix is `split(/\s/)[0]`, the same cut the broker's own bash regex makes; trailing content is **ignored rather than refused**, because the hint is a concurrency key and never an authoritative value (§5.6). The lasting change is the fixture: **the mocked broker now runs the real verifier**, so any spec that accepts proves the SPA→broker seam, and `tests/e2e/44-signed-acceptance.spec.mjs` asserts on the verdicts. A mocked dependency that accepts everything tests nothing.

### The acceptance payload is binary because the JSON one did not fit.

It carried the assignment id verbatim plus a full ISO-8601 `issuedAt`, and a real id - `2526-automation-scripting-practicum-exam-2` - produced a **253-character** title before any team hint was appended, so a group acceptance threw at the accept button for a reason the lecturer chose months earlier when naming the assignment. It is now 19 bytes (version, 8 bytes of `sha256(id)`, a 48-bit account id, a 4-byte nonce) = 26 base64url chars, giving 127/143/197-character titles measured live. **`issuedAt` is deleted**, not shortened: `verifyAcceptanceTitle` documented it as never enforced, so it was 32 characters of dead data. Hashing the subject is what makes the title's length independent of the id, and it keeps `wrong-assignment` meaningful - a broker holding the wrong `INVITE_PUBKEY` is a real deployment fault (INSTALL.md §3.3) and must not read as `bad-signature`. **The budget is 256 and it is OURS**: measured 2026-08-26, GitHub accepts a 1024-character title and refuses 1025, while its own 422 says "maximum is 256" - building on the enforced number would mean building on what GitHub's validator calls invalid. Titles round-trip byte-identically (whitespace and tabs included), which had to be measured, because verification compares bytes.

### Who accepted is ONE field: `github.event.issue.user`.

The broker verified the signature against `issue.user.id`, validated `github.actor` and `github.event.sender.id`, and dispatched *those* to the hub - so the account we checked and the account we provision for were two different readings of the same event. They agree for a freshly opened issue, which is exactly what makes the split dangerous; an issue opened through an App on a user's behalf reports the App as `sender` and the user as `issue.user`. The verified id was also computed as a step output and thrown away. One field now decides who signed, who is validated, who is dispatched and how the run is serialised. Related: **the hub does NOT re-check the signer and cannot** - the dispatch carries a login and an id, never the title - and a comment claiming it did was worse than the gap, because it invites the broker's check to be relaxed on the strength of a second one that does not exist. `tests/acceptance-identity.test.mjs`.

### `injectAuth` stored a session shape GitHub cannot produce.

It wrote `{login, name, email}` while `auth.js` persists `{login, id, name, email}`, and `getUser()` reads the stored object rather than re-fetching - so **every e2e acceptance signed with `githubId: undefined`**. The old payload turned that into `"g": null` and the mocked broker took it, so the suite stayed green over a title production would refuse. Personas now carry distinct ids (the anti-replay property is "is this the account that signed", which a shared id makes untestable) and `personaId(login)` fills one in for the many specs that build a user inline - `'id' in user` rather than `??`, so a spec can still test the absent case deliberately. The SPA now refuses to sign without an id and says *"your GitHub account id is missing from this session"* rather than letting the crypto's "not base64url" reach a student as if their link were broken.

### A leftover `pxl-accept:` title means two different things, and the advice differs.

Tier 4's exposure sweep said "still carry this assignment's invitation token... the link is effectively public... regenerate the invitation" for *any* leftover. On a **migrated** assignment that is false and the advice is actively harmful: the title is a signature naming one account, useless to anyone else, and regenerating retires every student's link to fix nothing. It is a `warn` there, pointing at the acceptance-handler run for the actual reason and saying explicitly **not** to regenerate; it stays a `fail` on the old format, where the title *is* the credential. Same rule as everywhere else here - do not describe a risk the system does not have.

### The hub CANNOT delete the trigger issue, and never could - the step is gone.

`deleteIssue` refuses an App installation token outright: measured live 2026-08-26, twice, in two organizations, `{"type":"FORBIDDEN","path":["deleteIssue"],"message":"Viewer not authorized to delete"}`. **It is not a permission.** Both orgs grant the App `administration: write`; the same installation token had read that very issue two steps earlier; and in the publish run that created the broker the same token created the repository and wrote its secrets and variables, all admin-level. A **user** token with repository admin deletes it immediately. GitHub documents this nowhere - the mutation's schema description is "Deletes an Issue object.", and neither the permissions reference nor the GraphQL limitations page mentions it - but its community answer for the identical error on `GITHUB_TOKEN` (also an installation token) is "use a personal access token". The system holds no PAT by design, and adding a long-lived user credential to the hub to tidy a public issue trades §4.3.4 away for housekeeping. So the step had **never once succeeded** while warning on every acceptance that an org should grant a permission it already had - which is worse than the gap, because it is a control the docs claimed and the system did not have (C4). Redaction on the broker is the mitigation, and after §4.3.2 the title is a signature naming one account rather than a credential. Tier 4's sweep is unaffected: it fires on titles that were never **redacted**, which is the signal that means something. `tests/invite-exposure.test.mjs` now fails if anything calls `deleteIssue` again.

### The failed-deletion warning asserted a cause and threw the evidence away.

`acceptance-handler.yml` ran `deleteIssue` with `2>/dev/null` and, on failure, printed "deleteIssue needs Administration: write on the organization". Measured live 2026-08-26 during a full end-to-end run: **that is false**. `PXLAutomation` grants the App `administration: write` (9 of the 12 participating orgs do, and 3 are unreadable to a non-owner), the same installation token had just read the issue body two steps earlier, and the mutation succeeds against `deleteIssue` with a user token holding repository admin. So the real cause is still unknown - and was unknowable, because the one line anybody reads was a guess and the error was discarded. It now captures GitHub's own message (truncated to 300 chars; Actions masks registered secrets in annotations) and stops diagnosing. The same wording had propagated into ARCHITECTURE §4.3.2, INSTALL.md §3.1 and the Tier 4 sweep, sending a lecturer to approve a permission they already had.

### A pre-migration link must NOT be signed, and nothing was stopping it.

`signedAcceptanceIssueTitle` signed whatever secret the URL carried. A link handed out before the change carries a 122-character bearer token, `fromBase64Url` rejects its `.` separator, and the accept button renders **"not base64url"** to the student - so the deploy that shipped signing would have broken acceptance for **every live assignment at once**, since none had a keypair yet. Found by running the thing, not by reading it. Those assignments' brokers still verify the old way, so the old title is the **correct** output there, not a fallback: `signedAcceptanceIssueTitle` branches on the wire shape (`TOKEN_PATTERN`), and `acceptanceIssueTitle` stays until no live assignment is on the old form. The team hint has to survive that branch - it is the acceptance concurrency key, and dropping it lets two joins read the same count (§5.6).

### Rotation retires a link too, and only migration was covered.

`regenerate_invite` mints a fresh keypair - the answer to a leaked link, and the *recurring* case, where migration happens once. The old key is gone from the document, so the "a secret the document still carries" rule below cannot see it, and the prune deleted its card: a rotated-away link landed on the not-found page, whose only honest wording is a guess between three causes. The fix needs **no record of retired secrets** (a list of them on the assignment is one more field `buildDoc` could silently drop): the orphaned card **names its own assignment**, so `pruneStalePublicFiles` converts it into a marker rather than deleting it, whenever that assignment is still being published. Three rules it must keep: a `.teams.json` at a retired digest is **pruned, never retired**, or a superseded link could still fetch the cohort list; a marker is **pruned once its assignment is gone**, or every rotation leaves a file behind for ever; and retiring is **idempotent**, because `regenerate-dashboard` runs on every acceptance and a marker rewritten or dropped on the second pass is a link that worked once. `tests/superseded-invitation.test.mjs`.

### A retired link resolves to a page that says so, and the two diagnostics for it are different checks.

Migration and rotation both take working links out of students' hands. `pages/generate.mjs` therefore writes a second card at the digest of **a secret the document still carries that is no longer the link** - phrased that way rather than as "has both fields", so it tracks `linkSecretFrom` instead of restating it: on an **unmigrated** assignment the token *is* the link, and a both-fields test would replace that cohort's only working card with a tombstone. The marker carries `{superseded, assignment_id, title, organization}` and deliberately **no `assignment` key**, so a browser on a cached build falls through to its own not-found state rather than rendering half an assignment with an Accept button; it must also be registered in `expectedInviteFiles` or the prune deletes it on the same run that writes it. Without it the student lands on the not-found page, whose only honest wording is a guess between three causes - **a page may not guess why it is stuck**, the same rule as the provisioning wait screen. The lecturer's half is the Admin Panel warning on the one republish that cannot preserve links, because two pieces of copy promise the opposite (C4). And **System Health Tier 4 had to be split**: `linkSecretFrom` was swapped in without teaching the parse the new shape, so `parseToken` saw a 184-char key, returned null, and the engine reported "invite_token is malformed, republish to mint a valid one" over a working link *and then returned*, taking the nonce, the switch and the exposure sweep with it. A migrated assignment is checked on `invite_key`'s shape and on the broker's **`INVITE_PUBKEY` matching the assignment's own public half** - the one agreement the signed path actually rests on, previously checked nowhere, and a republished broker sends no legacy token so a missing key does not degrade, it rejects everyone in silence. Its `INVITE_NONCE` is **not** judged: the signed path never reads it, and reporting a failure the system does not have is how a health panel stops being read. `tests/superseded-invitation.test.mjs`, `tests/diagnostics-invitations.test.mjs`, `tests/e2e/43-superseded-link.spec.mjs`, INSTALL.md §3.3.

### Public Pages artifacts disclose only what the student portal needs.

The acceptance card lives at `data/<org>/i/<sha256(invite_token)>.json` (teams beside it as `<sha256>.teams.json`), so finding it requires the link, a leaked filename is not a working token, and the teams file stops being a public cohort list of member logins. `assignments.json` survives reduced to id/title/organization/opens_at/deadline_at/timezone/repository_name_pattern/assignment_type/state, for one reason: the `/` portal matches a student's own repos against assignments and **students cannot read the control repo**. Broker repo, roster mode, cap, accepted count, description and group config are on the card only. `pages/scan.mjs` fails the publish on anything matching the token wire shape; `tests/public-data-contract.test.mjs` pins both halves. `index.html` sets `referrer: no-referrer` because the token is in the URL path. Residual, accepted: titles and deadlines stay enumerable - after §4.3.2 that grants nothing. In e2e fixtures `inviteToken()` must stay **pure** - a `Date.now()`-derived expiry is encoded at minute granularity, so the spec and the route mock straddling a minute boundary mint different tokens and 404 the card (flaked ~1 run in 4).

### A rejection is an outcome, not a failure.

`accept.mjs` splits `reject()` (exit **0**, `rejected:*`) from `fail()` (exit **1**, `fail:*`). A student who is not on the roster, or arrives after the deadline, is the system working - painting the hub's Actions tab red for that teaches people to ignore red runs and buries real failures beside them. The outcome string still gates every downstream step, and `acceptance-handler.yml` routes rejections to the org's instructor tracking issue via `./notify` (`event-type: acceptance-rejected`, deduped per assignment+login+reason) - previously a rejection wrote nothing anywhere and the lecturer of that org had no way to see it. `tests/accept.test.mjs` pins both exit codes.

### A restricted GitHub account fails invisibly.

GitHub returns HTTP 201 for an issue opened by an account it has flagged, then removes the content seconds later; no webhook fires, so the broker never runs. Observed live. `AssignmentView` records the acceptance issue number and, when polling gives up, re-reads it: gone means `blocked-account` ("GitHub is blocking your request"), not `timeout` ("GitHub is under load"). Check at timeout, never right after creation - the removal is not immediate.

### System Health must check the invitation chain, not just the broker.

Four things have to agree before a student can accept, and every mismatch fails silently: the assignment holds an `invite_token`, the hub publishes the `kid` it was signed with (`acceptance/invite-keys.json`), the broker's `INVITE_NONCE` matches the token's, and `INVITE_ENABLED` is not `false`. Tier 4 checks all four; Tier 5 checks the acceptance card at `public/i/<sha256(token)>.json` - it previously only checked that the id was in `assignments.json`, which stayed true while the student's page 404'd. The checks stay silent for an unsaved Admin Panel form (`formDoc`), which never carries a token. `tests/diagnostics-invitations.test.mjs` proves each one FAILS when it should.

### The Admin Panel rebuilds the whole assignment on save.

`buildDoc` constructs the YAML field by field, so anything it does not carry through is deleted - and the document still validates, because the invite fields are optional. Editing a published assignment therefore used to wipe its `invite_token` and silently retire every student's link. `buildDoc` and the edit-load path must both carry `invite_token`, `invite_nonce` and `invite_expires_at`; `tests/admin-lifecycle-ui.test.mjs` pins both halves.

### One reader for the invitation, and it is the writer's.

`INVITE_FIELDS`, `readInviteField`, `parseInviteFields` and `quoteInviteValue` live in `lib/invite-token-format.mjs` beside the wire format, and are used by `scripts/set-assignment-invite.mjs` (writer), `AdminView.verifyLiveInfrastructure` and `AssignmentDetailView.loadInviteToken` (readers). The module stays **dependency-free** - `lib/invite-token.mjs` imports it and the broker runs that with no `npm ci` - so the parse is line-based regex, not a YAML round trip. Three consequences that are load-bearing: **`getRepoContent` resolves to decoded FILE TEXT, not a `{ok, data}` envelope** (both invitation read paths asked a string for `.ok`, so neither ever ran - and the test written to catch it grepped for the error message, which passed *because* the code always took the error branch); **`invite_nonce` is written quoted**, because ~1 nonce in 600 is all-digits-with-a-leading-zero and round-trips through a YAML parser as an integer, failing the hub's `^[0-9a-f]{8}$` check and silently retiring every live link on the next republish; and **`verifyLiveInfrastructure` re-reads unconditionally**, never gated on the form lacking a token, or a regenerated invitation never reaches the panel. `startPublishWatch` must call it on **both** terminal branches (`ready` and `timeout`) - the token is minted while the watcher polls, so without that the success banner says "verified live" over an empty link box. `tests/invitation-link-surface.test.mjs` runs the real round trip and flags any `getRepoContent` binding used as a response. **The token is read from that file and is never a workflow output.** It was one until 2026-08-26 - `setOutput("token", token)`, four lines above the comment stating that the link secret must never be an output *because outputs are readable in the run log* - written unmasked (nothing in the script calls `::add-mask::`) from a workflow on the **public** hub. Bounded on a migrated assignment, where the token is not the link; on an unmigrated one the token **is** the bearer credential, and those are still live. Nothing consumed it: the only reference was a dead `env:` entry in `publish-assignment.yml` whose step script never read it, and removing that dead line is what revealed the output had no consumer at all - the same shape as `preserved_sha` and `earned_points`, a value moving between two places with nobody at either end. `tests/invite-token.test.mjs` runs the real script and reads its real `GITHUB_OUTPUT`, so re-adding the export under any spelling fails; it also asserts the outputs the workflow *does* consume (`nonce`, `pubkey`) still appear, because a guard satisfied by exporting nothing would be worse than the bug. The round-trip test that had used the output as its observation channel now reads the assignment file through `parseInviteFields`, which is both the honest source and the sanctioned reader.

### One invitation-share surface: `InvitationShare.vue`.

The link existed as a bare `<span>` in the publish banner, a lone primary button on the detail header, and **nowhere** on either list of assignments - so a lecturer who closed the editor had no route back to it, and rotation was reachable only from the Actions tab. Three implementations of "put the link on the clipboard" existed across two views, each with its own guard against writing the string `"null"`, and one of the reads behind them was dead for months. One component now, on four surfaces (`banner` / `inline` / `compact`), with its classes in `style.css` per DESIGN.md §7. Load-bearing details: the secret is **redacted on screen and on hover**, the box showing the host, the org and `/i/…` while the link itself lives only on the clipboard and behind *Open*; the status line is the **student-facing** truth, gated on the same conditions `AssignmentView` uses to show an Accept button, so a lecturer cannot read "Live" over a page that says "Registration cap reached"; and **`:resolve="false"` marks a caller that is authoritative about the token** - rotating sets `form.invite_token = ''` precisely so the retired link stops being copyable, and the lazy control-repo read would otherwise hand it straight back (`tests/e2e/27-invitation-link-surface.spec.mjs`). `openRegenerate()` is the only entry point that opens the republish modal pre-ticked; `handlePublishClick` still resets it, because a repair must not break links. `tests/e2e/34-share-surface.spec.mjs`.

### A truncation is a claim about the value's shape, and the shape changed under it.

`InvitationShare` printed `${head}/i/${tail.slice(0, 8)}…${tail.slice(-4)}`, with the whole link on the `title` for hover. Correct as written: the secret was then a random 122-character bearer token, so eight characters genuinely told two links apart, which is what the comment beside it claimed ("enough to recognise"). Six weeks later §4.3.2 replaced the token with the acceptance **private key** and nothing revisited the display. A PKCS#8 P-256 export is a fixed DER structure, so every key on earth base64s to the same opening characters: the box rendered `…/i/MIGHAgEA…<4>` on **every assignment in every org**, eight constant characters of zero entropy, no two links distinguishable, and the start of a private key on whatever a lecturer projects. Reported by someone reading their own dashboard and asking why a key was on it.

Two things to take from it. **The truncation encoded an assumption about the secret's format at a distance from the code that decides the format** - `linkSecretFrom` moved from `invite_token` to `invite_key` and this was three files away, so nothing failed and no test noticed; `tests/e2e/27-invitation-link-surface.spec.mjs` asserted `shown` contained `token.slice(0, 8)`, which stayed true and meant nothing once those eight characters were a constant. **And there was nothing to recognise in the first place**: the URL is `/:org/i/:secret` and has never carried the assignment id, so no prefix of it could ever have said which assignment the link belonged to. The redaction costs nothing. The spec now asserts that what follows `/i/` **is** the ellipsis, rather than that some substring is absent - a `not.toContain` against base64url passes because four characters happen not to occur in a hostname, which is luck, not a redaction.

### `Republish broker` is offered on a `published` assignment and nowhere else.

`publish-assignment.yml` runs `sed -i "s/^state:.*/state: published/"` with no regard for the prior state, so the same dispatch from `closed` or `archived` **reopens acceptance**. WS5 relabelled that dispatch "Republish broker" and grouped it under *Repair*, beside copy promising "existing student repositories are untouched, and links already handed out keep working" - which is C4 exactly: the UI describing behaviour the system does not have. From those two states the button is **`Reopen for acceptance`**, it sits with the other state transitions, and it confirms first like they do. Do not widen the repair group to `closed` "because the broker is still there".

### `max_acceptances` can overshoot, and that is a decision - do not "fix" it.

`accept.mjs` counts `acceptances/<id>/*.json`, compares, then writes, and the acceptance concurrency group is keyed on `team_hint || github_login` - so per-*team* serialization guards `max_team_size` while acceptances by **different** students run in parallel. Two arriving together both read 49, both see `49 < 50`, both write. Closing it means keying the group on the assignment, which serializes every acceptance for it: a 200-student cohort accepting in the first minutes of a lecture would run one at a time at ~30s each, on a system whose whole design goal is billing zero minutes when idle. **Raised and explicitly rejected on 2026-08-24 (Tom's call): leave it.** The cap exists to stop an unbounded link being farmed, and it does that; it is not an exam-seat allocator. The only rule that follows is a documentation one - **nothing in the UI may present the number as exact** (C4), which is why the Admin Panel hint says "Cap on accepted students" and not "Hard cap". `tests/acceptance-cap-decision.test.mjs` fails if the concurrency key is changed to close the race, so a future pass cannot silently trade the throughput away. ARCHITECTURE §5.4.

### `is_first_member` counts acceptances, not members.

A lecturer-seeded team lists every member before anybody has accepted, so counting members told the genuinely-first student they were not. And a **team switch keeps the original `accepted_at`** - the switch falls through the idempotency check because it has work to do, and rewriting the timestamp moved the fact that decides whether a student accepted before the deadline.

### `regenerate_invite` is reachable, and rotating clears the old link.

The input existed on `publish-assignment.yml` and nothing in the SPA or CLI ever sent it, so a leaked link could only be rotated from the Actions tab - and doing that left the panel showing and copying the retired token. The republish modal now offers it, defaults to **off** every time it opens (a repair must not break links), states the consequence before it happens, and clears `form.invite_token` on confirm. DESIGN.md §1.2: the modal is its own view, so the confirm is its single solid button - `.btn-primary`, or `.btn-danger` when it is actually destructive.

### Liveness is the page a student opens.

`pages/generate.mjs` writes `data/<org>/i/<sha256(token)>.json` **only** when the assignment carries an `invite_token`; without one it warns, continues, and still adds the id to `assignments.json`. So checking the index reported "Published & Verified Live" over a card that 404s for every student - the same mistake `e594f4f` fixed in diagnostics Tier 5 and not in the publish flow beside it. `acceptanceCardIsLive()` fetches the card; nothing decides liveness from the index.

### Publish never strands state.

"Save & publish" reverts the assignment YAML to `draft` when the `publish-assignment.yml` dispatch fails, so `state: published` never coexists with a missing broker. Cross-field rules the schema can't express (deadline > opens_at, `max_acceptances` ≥ 1) are enforced in `AdminView.validate()`.

## Roster, claims and identity

### `roster_mode: claim` binds an account to an EMAIL ADDRESS, and `lib/claim.mjs` is the only thing that knows how.

It is "enforced, with a way in": the lecturer holds addresses, the student proves one, and it must match a roster entry. The module is isomorphic on WebCrypto so the SPA seals with the same code the hub opens with - ECDH P-256 -> HKDF -> AES-GCM, wire format `c1.<ephemeral SPKI>.<iv>.<ciphertext>`. **Encrypted, not hashed**: an HMAC never lets the hub learn the address, which is stronger on paper and useless to the lecturer who needs to contact the student; the invite-token rule ("the broker cannot hold a decryption key") does not transfer, because decryption happens at the hub. Rules that are load-bearing, each mutation-checked: `domainAllowed` matches the **whole label, never a suffix** (`notstudent.pxl.be` ends with `student.pxl.be` and anyone can register it); **absent and empty `claim_domains` are different answers** (no key = deployment default, `[]` = deliberate opt-out, and a truthy check silently re-imposes a rule the lecturer removed); a **fresh ephemeral key per claim**, or the public archive becomes a ciphertext->address lookup table; the counter **keeps `first_at`**; and a **missing or corrupt counter reads as ZERO, never blocked** - a student must not be locked out because a file failed to parse. The payload carries `github_id` and the hub refuses a mismatch with the issue author, which is the anti-replay check; **every kind of tampering is ONE indistinguishable failure**, because naming them describes the crypto to whoever is probing it. `MAX_CLAIM_ATTEMPTS` is 5 and ships **with** the gate - an unbounded guessing oracle over enumerable addresses is not a follow-up, and the bill from a bored student with a loop bites before the identity risk does. The gate is ordered cheapest-refusal-first (bound -> counter -> payload -> decrypt -> author -> domain -> roster -> taken) and **a missing payload or a missing `PXL_CLAIM_PRIVATE_KEY` never counts** - both are deployment faults, and spending a student's attempts on one is the `no-nonce` mistake in a new place. The key itself is an **environment** secret on `provisioning` with no repository-level copy; the public half is committed to `acceptance/claim-keys.json`, where `tests/claim-keys.test.mjs` fails if anything **184 characters** (a private key) lands beside the **122** a public one is. `tests/claim.test.mjs`, `tests/claim-mode.test.mjs`, `tests/claim-payload.test.mjs`, `tests/e2e/46-claim-address.spec.mjs`. ARCHITECTURE §15, INSTALL.md §3.2 and RUNBOOK §6.4.

### Adding a roster mode SPLIT a question that used to have one answer, and seven call sites had already conflated them.

Before `claim` there was exactly one roster-gated mode, so a hand-written `=== "enforced"` correctly answered both *"is the roster what decides who may accept?"* and *"is the student's LOGIN what gets looked up in it?"*. `lib/roster-mode.mjs` now answers them separately: **`rosterGatesAcceptance`** (enforced **and** claim - the roster must exist and be readable) and **`rosterMatchesLogin`** (enforced **only** - `github_login` is precisely the column a claim assignment does not expect the lecturer to have). Applied per site, never uniformly: `accept.mjs`'s unreadable-roster failure, `seed-teams`' two roster-relative predictions, `promote-roster`'s "everyone who accepted passed the gate" and AdminView's "is roster.yml load-bearing" take the first; StudentDiagnosticsModal's roster status, AssignmentView's *"you are not on the roster"* cause line and AdminView's missing-`github_login` warning take the second - otherwise a student listed by address is told they are missing, and a lecturer is warned about an empty column their cohort deliberately does not use (C4). `tests/claim-mode.test.mjs` fails if a bare `=== "enforced"` returns to any of the seven files, scanning with comments stripped because several of them quote the old spelling while explaining why it changed. **Removing a mode is safe in a way adding one is not** - `normalizeRosterMode` fails closed, so a withdrawn value reads as `enforced`, while a new value has to be taught to every reader.

### The student confirms an address; the page must never claim more than it knows.

`ClaimAddressCard.vue` lists the student's own GitHub-**verified** addresses (`GET /user/emails`, account permission `email_addresses: read`) filtered to `claim_domains`, and typing stays open as the fallback recorded `claim_verified: false` - requiring a verified address was considered and rejected, because it blocks a real fraction of students and stops nothing determined, the page being public JavaScript either way. **A 403 and an empty list are different sentences**: a 403 is exactly what a missing permission approval looks like and is *not* evidence the student has no institutional address, so the card says "we could not check" rather than "none of yours matches" - the `/apps/{slug}` rule, applied to a student-facing page. `buildAcceptanceBody` is **one builder for both acceptance flows** (individual and group each open their own issue, and the hub reads one body with two readers); `hubClaimKey` is the one reader for the key, **bundled at build time** rather than fetched, because fetching would put a network dependency on the one control that matters plus a failure mode the page then has to explain - and it returns **null rather than throwing**, since it runs in computeds (the `localToUtc` bug). `tests/e2e/46` drives the real browser through the real crypto and opens the result with the real hub-side parser and decrypt, which is the seam Phase A's team-hint bug lived in; it also asserts the plaintext address appears **nowhere** in the posted body.

### `roster_mode: org_member` is GONE (2026-08-27), having never run a single cohort.

It gated on an ACTIVE org membership so a lecturer could enrol from a list of **email addresses** - the real problem, since a lecturer holds addresses and not GitHub usernames, an installation token cannot read a user's emails (`GET /user/emails` is user-to-server), and anything the SPA sends is a claim rather than a credential. The mechanism worked and was measured live: `GET /orgs/{org}/memberships/{login}`, **never `/members/`**, because an invited-but-unaccepted account reports `state: "pending"` on the former and **404** on the latter, identical to never-invited. What killed it is that it made enrolment depend on org **membership**, which is heavy and permanent for one semester's assignment: a member is subject to `default_repository_permission` (the floor bullet below), shows up in the org's People list indefinitely, and - as the unfreezable-owner bullet records - org roles interact with lock-down in ways collaborators do not. The claim flow binds the address directly and puts nobody in the organization. **Removing a value from `ROSTER_MODES` is safe in a way adding one is not**: `normalizeRosterMode` fails **closed**, so a control repo still holding `org_member` now reads as `enforced`, the most restrictive mode, rather than admitting anyone. Verified rather than assumed before deleting: across the twelve participating orgs, every assignment ever written is `enforced` (12) or `open` (10). Two things deliberately **kept**: the App's `members` permission (approved on eleven orgs, free to hold, and re-acquiring an org-approved permission is a slow round - see the `checks: read` bullet), and the base-permission diagnostic, whose lock-down-floor argument weakens once students are never members but which still catches `read` exposing the private control repo to every member. `accept.mjs` now makes **zero** API calls, so the `github-token` input threaded through `acceptance/action.yml` and `acceptance-handler.yml` for the membership check went with it. ARCHITECTURE §15, RUNBOOK.md §6.4.

### Under `open` the claim observes and never refuses, because a check anyone can skip is not a gate.

The same flow runs and the same `students/claims/<github_id>.json` is written, but nothing rejects an acceptance and **nothing counts an attempt**. That is forced, not chosen: the claim is optional under `open` (an older link, a browser without WebCrypto, a dismissed prompt must all still provision), so anyone wanting a second repository just omits it. An address outside `claim_domains` is recorded `domain_allowed: false` rather than refused; a second account confirming the same address writes a second binding that `lib/claim-bindings.mjs` surfaces as a duplicate; acceptances with no address are a count. All three are review signals, and **the copy may never present them as prevention** - ARCHITECTURE §16 said the uniqueness check "would stop one person quietly taking several exam repositories" while this was still a plan, building it showed it cannot, and the claim was corrected rather than the code bent to match (the same correction §11.2.2 records for `until` being called proof). Three things the observation path keeps although it gates nothing: the **anti-replay check** (a payload naming another account binds nobody - the output is a record asserting who someone is, and a false record is worse than none), **org-scoped idempotence**, and **no counter** (it exists because a refusal under `claim` tells a guesser whether an address is on the roster; nothing is refused here, so nothing is revealed - and a counter that filled up would eventually lock a student out of a mode that never refuses anyone). A missing `PXL_CLAIM_PRIVATE_KEY` is `fail:config` under `claim` and merely **logged** under `open`, because losing a review aid is not worth refusing a student their repository. `claimed_email` / `claim_verified` / `claim_domain_allowed` had been written onto the acceptance record since `claim` shipped and **read by nothing** - the `preserved_sha` shape, invisible while the Roster tab answered "who is bound" and total under `open`, where there is often no roster and the report is the only surface; `report.mjs` now carries all three, and `acceptance.schema.json` (which is `additionalProperties: false`) **declares them at last** - it had forbidden `claimed_email` since the day it was first written. `tests/claim-open.test.mjs` drives the real `accept.mjs` with really-sealed payloads and asserts on **both** halves every time - what was recorded, and that the acceptance still succeeded - because the entire risk here is a review aid quietly becoming a refusal. `encryptClaim` is async, so payloads are sealed at module level with top-level await: a `CLAIM_PAYLOAD` holding a **Promise** stringifies to `[object Promise]`, decrypts as garbage, and silently turns a domain-check test into an unreadable-payload test that still passes. ARCHITECTURE §15, RUNBOOK.md §6.7.

### A binding a lecturer cannot see is the same mistake as one they cannot undo, so the column and `unlink` shipped together.

`lib/claim-bindings.mjs` is the single join between `students/claims/<github_id>.json` and `students/roster.yml`, and the join is the **email address**, case-insensitive - the same comparison `rosterEntryForEmail` makes in the other direction when the student claims. Four readers (Roster tab, `roster list`, `roster unlink`, the Tier 3 diagnostic) is the shape that forked `diffRosters` into two implementations disagreeing on key order, so `tests/claim-bindings.test.mjs` fails if any of them compares addresses itself - its guard keys on the address comparison, **not** on merely touching both things, because `cli/src/lib/control-repo.mjs` fetches claims and fetches the roster and joins neither, and allowlisting transport is how a guard becomes a list that means nothing. Five states, because the lecturer action differs for each: `claimed`, `roster` (pre-linked, still works), `unclaimed`, **`unclaimable`** (no email on the entry - it can *never* be claimed, so the fix is a re-import rather than patience) and **`conflict`** (a claim binding this address to a different account than the roster's own `github_login`, reachable because first-come wins, and counted as bound *and* as a conflict so it cannot hide inside a healthy number). Three rules the surfaces must keep: **unlink deletes the attempt counter too** (a lecturer unlinks because something is wrong, which usually means the student has been failing to claim, and an exhausted counter hands them back a door they still cannot open); **a partial read refuses the delete**, because unlinking off an incomplete list can remove the wrong binding and "no such binding" for an unreadable file reads as success; and the unbound label is **one mode-neutral string** - an earlier version chose the wording from whether the org had any claims at all, so unlinking the last student silently relabelled every other row, and RosterTab is org-scoped anyway and cannot know which mechanism a given student is waiting on. The **diagnostic** was the live instance of the bullet below: its guard was still `roster_mode !== "open"`, so a `claim` assignment got a check headed *"Enforced Roster"* telling the lecturer that students without a `github_login` "cannot accept until theirs is added" - the exact column `claim` exists to avoid needing (C4). It asks `rosterMatchesLogin` now, counts `email` under `claim`, and its binding check is **bounded**: claims are org-scoped so a file count says nothing about one cohort, the join needs the contents, and past 60 records it says it did not finish rather than reporting `ok`. `tests/e2e/47-claim-bindings.spec.mjs`; the fixture models an **absent** claims directory as a 404 exactly as GitHub does, which is what caught the SPA read falling through to an error on every spec in the suite while every test still passed. **`roster promote` takes exactly one source and the two are opposites** - `--assignment` ADDS entries for logins the roster has never heard of, `--claims` UPDATES entries it already has - so `planClaimPromotion` is a separate planner rather than a flag on `planPromotion`, and the command refuses when given both or neither rather than defaulting. It writes only into an **empty** `github_login`: a value the lecturer set is never overwritten, which is merge-never-replace in its sharper form, and an address claimed twice is left alone rather than picking a winner. An **absent roster refuses** here where promotion would create one - a claim can only exist because it matched a roster entry, so a missing roster means the roster went away underneath the bindings. `pages/scan.mjs`'s `claim-token-field` rule guarded `"claim_token"`, a name that appeared nowhere in the repository and so could never fire; it is repointed at the record that did ship (`claim_verified`/`claimed_via`/`claimed_at`), beside the `email-address` content rule that already covers the address itself. ARCHITECTURE §15, RUNBOOK.md §6.6.

### One reader for `roster_mode`: `lib/roster-mode.mjs`.

The rule was written by hand in five places as `roster_mode === "open" ? "open" : "enforced"`, a spelling that normalises and **silently collapses anything it does not recognise** into `enforced`. That is right for garbage - the gate must fail closed - and wrong for a value the system has since learned about: `AdminView.loadAssignmentIntoForm` used exactly that ternary, so opening an `org_member` assignment rewrote it to `enforced` on load and `buildDoc` saved the rewrite back, silently converting a membership-gated cohort into one gated on an empty roster. Same shape as `buildDoc` deleting invitation tokens. `normalizeRosterMode` is now shared by `accept.mjs`, `pages/generate.mjs`, `AdminView`, `AssignmentView`, `StudentDiagnosticsModal`, `lib/seed-teams.mjs` and `lib/promote-roster.mjs`, and **every `!== "open"` guard became `=== "enforced"`** - those guards all meant "the roster is the gate", which is true of exactly one mode; leaving them would have told an `org_member` student they were not on a roster that does not govern them, and warned a lecturer that seeded students "will be rejected" when they will not. The fail-closed test now asserts the **behaviour** (junk in, `enforced` out) rather than grepping `accept.mjs` for the literal ternary, which pinned a spelling and went red the moment the rule was shared.

### `students/` was never committed, so the claim bound nothing and its rate limit could not count.

`accept.mjs` writes into a checkout the workflow commits, and the staging list was `repositories/`, `teams/`, `acceptances/` - never `students/`. Found by running a real claim: the acceptance succeeded, the log said `[ok] claim - @tomcoolpxl claimed tom.cool@pxl.be`, and `students/claims/71908551.json` was a **404** a second later. Three things were inert, and the second is the serious one: the org-scoped binding did not exist so every assignment re-prompted; **`MAX_CLAIM_ATTEMPTS` was unenforceable**, because the only commit step is gated on an ACCEPTED outcome and a *failed* attempt - the one case the counter exists for - never reached a commit at all, leaving the guessing oracle unbounded; and `rejected:claim-taken` could never fire, since `findClaimForEmail` scanned a directory that was always empty. The rejected path now has its own persisting step, `continue-on-error` for the same reason the notify steps are - a rejection exits 0 on purpose and a failed push *about* one must not turn it red.

### The SPA bundles `acceptance/claim-keys.json`, and changing it deployed nothing.

`deploy-frontend.yml` is path-filtered, `frontend/src/lib/claim.js` imports that file at build time, and the path was not in the filter - so the commit that minted the hub's real claim keypair fired **no deploy**, and the live page kept telling students "claiming is not set up for this course yet" while the hub could decrypt perfectly well. A key **rotation** would fail identically, in precisely the situation where you are rotating because something already went wrong. Nothing was red, because nothing ran: a path filter is a claim about what the build depends on, and the claim had drifted from the imports. `tests/deploy-paths.test.mjs` walks every import in `frontend/src` that resolves outside `frontend/` and fails if the push paths do not cover it.

### The account permission is `emails`; the settings toggle is labelled "Email addresses".

`ACCOUNT_APP_PERMISSIONS` said `email_addresses`, so the check reported `email_addresses=missing` while `GET /apps/{slug}` plainly returned `emails: read` - a constant naming a field the API does not use is a check that can never pass, the same shape as the scanner rule that guarded `claim_token`. It hid because `ACCOUNT_LEVEL_PERMISSIONS` carries **both** spellings, and because the check had never seen a granted App to disagree with. Account permissions are a **separate constant from `MANIFEST_APP_PERMISSIONS`** for two independent reasons: the manifest's `default_permissions` does not accept account-level names (measured for `starring`, which is why that one has always been set by hand), and `EXPECTED_APP_PERMISSIONS` spreads MANIFEST and is compared against an **installation**, which never carries one - so a name in the wrong place reports every org as permanently drifting on something no owner can approve. `starring` is deliberately **not** required: ARCHITECTURE records it as legacy and nothing in the codebase stars anything.

### Rotating the claim key was impossible, and the RUNBOOK described a remedy that does nothing.

`acceptance/claim-keys.json` has always carried a `current` kid and a `keys` map, and the SPA seals to whichever is current - so it LOOKS rotatable. It is not: the kid **never travels with the ciphertext** (`c1.<ephemeral SPKI>.<iv>.<ciphertext>`) and the hub held exactly one `PXL_CLAIM_PRIVATE_KEY`. The docs said to "keep the previous entry in the file", which changes nothing - that file holds **public** halves, and the question is what the hub can *open*. So a rotation would have failed every claim sealed to the old key (acceptances already posted, plus every browser on a cached bundle) and failed them in the worst place available: the gate is ordered bound → counter → payload → **decrypt** → author → domain → roster, so a decrypt failure sits *after* the counter and would have spent real students' attempts, locking them out of the one mode whose purpose is letting them in. The hub now holds **several** private keys (`PXL_CLAIM_PRIVATE_KEYS_RETIRED`, current tried first) and tries each. **Chosen over adding a kid to the wire** deliberately: multi-key needs no format change, no SPA change and no transition window, so nothing in flight notices - where a v2 format would have needed all three on the one path that must not break. Two rules it keeps: **every student-caused failure stays ONE failure** (a "no key matched" distinct from "bad ciphertext" would leak whether a rotation had happened), and an unconfigured hub is still a *distinguishable* deployment fault in the log. Both claim paths had to move - the `claim` gate and the `open` observation are 150 lines apart, and updating one would leave open cohorts silently losing the address they exist to record. **Forward secrecy remains impossible** and the docs now say so: a static page sealing to a long-lived recipient key has nothing to derive one from, the ciphertext is permanently public in GH Archive, so rotation bounds the window a leaked key exposes and never undoes it. `tests/claim-key-rotation.test.mjs` runs the real crypto, including the without-the-retired-key case that proves the hazard was real. INSTALL.md §3.2.

### "The roster file exists" is not "somebody can accept".

Tier 3's roster check tested `rosterRes.ok` and reported **`ok`** for three rosters that let nobody accept: `students: []` (the scaffold stub - this is exactly what stranded `2526-examen-aut2-ek2` in July, every acceptance rejected `not-on-roster` with nothing saying why); a hand-edited **array-shaped** roster, which parses fine while `accept.mjs` reads `roster?.students || []` and so sees nobody; and a roster whose students have **no `github_login`**, the optional CSV column and the only field `accept.mjs` matches on. The check now parses the file and reports counts - `fail` when the assignment is **published** (students may be trying right now), `warn` on a draft, and `ok` names how many students and confirms all are linked. It also stopped naming **`rosters/<id>.csv`**, a path the data model has never had: the comment directly above the check records that being fixed *in the request*, and the success message kept it, so a lecturer was sent looking for a file that cannot exist. The check that exists to answer "can my students accept?" could not answer it. `tests/roster-diagnostic.test.mjs`.

### Student Tooltip & Identity Resolution

Hovering over student logins in the table/cards resolves identity across 4 tiers: (1) institutional roster (`students/roster.yml`), (2) Git commit author email/name (prioritizing real email, suppressing dummy `@users.noreply.github.com` and bot names `[bot]`/`provisioner`/`web-flow`), (3) GitHub public user profile (`GET /users/{login}`, batched in background with concurrency 6), and (4) clean fallback (`null`). Search filters across all resolved fields (name, email, student number, group, company).

### `roster_mode` is per-assignment and fails closed.

`enforced` (default) requires the login in `students/roster.yml`; `open` skips the roster gate entirely for assignments whose cohort isn't known up front (exams), leaving the `opens_at..deadline_at` window and `max_acceptances` as the only guardrails. **`open` therefore requires `max_acceptances`** - enforced in the schema (`allOf`/`if`/`then`), in `AdminView.fieldErrors` (so Save disables), and in `accept.mjs` (`fail:config`) for hand-edited YAML. Absent or unrecognised values - including `"Open"` - are treated as `enforced` in **both** `accept.mjs` and `pages/generate.mjs`; never loosen that to a truthy check. The flag is published to the public assignments JSON (the privacy scanner matches field *names* like `full_name`, not the substring "roster", so it does not trip). Under `open`, `AdminView.validateStudentLogin` treats any real GitHub account as valid for retries/extensions, since there is no roster to be absent from.

### Under `open` the system learns a GitHub login and nothing else, and that used to be the end of it.

Who accepted is recorded in `acceptances/<id>/<login>.json`; `students/roster.yml` is written **only** by a CSV import, so the next assignment started from the same blank roster and the lecturer re-collected usernames by hand. `lib/promote-roster.mjs` is the pure planner (no fs, no fetch, no YAML - serialisation is the caller's, which is what lets it be tested under plain Node), shared by `pxl-classroom roster promote`. Three rules it exists to hold: it **merges, never replaces** - an existing entry is returned byte-identical, because a CSV import already replaces the file wholesale and losing a `student_number` to a helper that "updated" the roster is unrecoverable; it **never invents an identity** - GitHub has no name and no student number, so a promoted entry carries `github_login`, `github_id`, `source: "accepted"` and a `promoted_from` block and nothing else (`student_number` comes **only** from the lecturer's CSV or the RosterTab quick-add, never from GitHub - traced 2026-08-25); and it writes **no team data**, because `seed-teams.mjs` deliberately refuses to and a CSV re-import would wipe it anyway. `roster.schema.json` therefore requires `student_number`/`full_name` only for entries that are not `source: accepted` (`allOf`/`if`/`then`/`else`, the same shape as `roster_mode: open` requiring a cap) - ARCHITECTURE §15 had already accepted null identity for open-mode acceptors in *reports*; the roster schema was the last thing still insisting. An **array-shaped roster is refused, not rewritten** - it already lets nobody accept and the lecturer has to know. Matching is case-insensitive because `accept.mjs`'s gate is. The SPA shares the planner through `PromoteRosterModal.vue` (tracking page → `··· More`), offered only on an `open` assignment somebody has accepted - under `enforced` every acceptor was already on the roster, so the item would be a no-op on every assignment (C4). Two things the modal must keep: a **partial read blocks the write** (`listAcceptances` returns `{records, failed}` and a non-zero `failed` refuses, because promoting anyway reports "197 added" over 200 acceptances and the three missing students surface a week later), and the roster is cloned with a **JSON round trip, not `structuredClone`** - the existing entries come out of a `ref`, so they are reactive Proxies and `structuredClone` throws on them, which failed only when the roster was non-empty. `tests/promote-roster.test.mjs`, `tests/e2e/41-promote-roster.spec.mjs`, RUNBOOK.md §6.5.

### One roster identity rule: `lib/roster-entries.mjs`.

`diffRosters` existed twice - `cli/src/commands/roster.mjs` and `frontend/src/lib/csv.js` - and had **already forked**: the CLI compared entries with a stable stringify while the SPA used `JSON.stringify`, which is key-order sensitive, so a roster whose YAML serialised its keys in another order showed **every** student as "updated" in the Admin Panel and unchanged in the CLI. Both also keyed on `student_number` alone, which a promoted entry does not have - so every promoted student mapped to the key `undefined`, fifty collapsing into one diff row, and the CSV re-import that followed would have silently removed forty-nine of them. `rosterKey` prefers `num:<student_number>` and falls back to `login:<lowercased>` (prefixed, so a login that reads like a number cannot collide), and `describeRosterEntry` is what the diff prints - `${student_number}  ${full_name}` rendered "undefined undefined" for a promoted entry in the **removed** list, the one place a lecturer is asked to confirm a destructive change. `tests/promote-roster.test.mjs` fails if either consumer grows its own copy, scanning with comments stripped because they quote the old implementation by name.

## Deadlines, lockdown and preservation

### The login rule had no guard, and there were seven of them.

CLAUDE.md has said for a long time that *"a GitHub login is compared and indexed lowercased - `lib/github-login.mjs`, never a hand-written `.toLowerCase()`"*. Nothing enforced it, and `lib/github-login.mjs` turned out to have three importers in the whole repository. A sweep for the sharp shape - a **raw `===`** on a login, with no normalisation at all - found seven live call sites, each failing in silence:

* `scripts/get-budget-owner.mjs` found no entry and printed an empty owner. `weekly-usage-report.yml` skips the notification when it is empty, so **an org over its budget was simply never told**, on a green run.
* `scripts/usage-fetch.mjs` found no org entry, so `orgOverrides` stayed empty and the org was measured against the **global** limit instead of its own. That file already carried a comment about that exact consequence arriving by another route - the repo-level overrides file - and had it open through the org-level one.
* Four CLI filters (`download`, `feedback`, `grade`) compare a **lecturer-typed `--login`** against a stored login. `--login Alice` for a stored `alice` produced *"No preserved submission for Alice"* and *"No repository records to act on"* - a confident report of nothing, for a student who has one.

**Where the guard draws its line is the point.** A raw `===` is unambiguously wrong: two real spellings of one account compare unequal. `a.toLowerCase() === b.toLowerCase()` is a different thing - nearly right, differing from the shared helper only in that the helper also trims - and `acceptance/accept.mjs` has nine of those which were reviewed and deliberately left. A sweep that flagged both would have been switched off rather than fixed, so it catches the sharp shape only. The first draft also reported `typeof claim.github_login === "string"`, which is a type check; that false positive would have been the other reason to delete it.

### One half deleted the cohort list; the other half published it.

`pages/generate.mjs` removes `public/teams/` on every regeneration, and says exactly why: *"public/teams/ predates the move behind the invitation digest. Anything still there is a public cohort list for an assignment that no longer publishes one."* `scripts/fetch-pages-data.mjs` walked that same directory and copied it into `frontend/public/data`, which is what gets uploaded to GitHub Pages. So for any org whose control repo had not regenerated since the retirement, **every frontend deploy republished the cohort list the generator exists to remove.**

`pages/scan.mjs` does not stop it, and that is the part worth remembering: the gate was added precisely because this script *"copies `public/i/*.json` and `public/teams/*.json` verbatim out of twelve control repos, and whatever is in them ships"* — but it looks for **email addresses and invitation-token shapes**, and a teams file is `members: ["alice", …]`. GitHub logins match neither rule. A gate that covers the right *files* can still be blind to the *contents* those particular files carry. Nothing in the SPA reads `data/<org>/teams` either; teams reach a student through the invitation card, behind the digest. The fetch is gone.

**And an org that could not be read simply vanished from the published index.** `index.json` is rebuilt from the orgs that succeeded on that run, `HomeView` discovers participating orgs through it, and a non-404 failure was logged as `[error]` while the run exited **0** and the deploy went ahead. A transient 500 while minting one org's token therefore published an index without it — and that org's students open the site and see none of their assignments, with nothing red anywhere.

It fails the run now, which is the useful direction: a failed deploy leaves the **previous** Pages deployment live, and yesterday's complete index serves the cohort correctly where today's partial one does not. A 404 is still an answer — an org with nothing published yet, or no control repo — and does not stop anyone else's deploy.

### The careful per-student `try` did not cover the line that read the student.

`sync-starter.mjs` writes into student repositories — a commit straight onto `main` for files they never touched, a branch and a pull request for the ones they did. Its per-student work is properly wrapped: one student's failure becomes `outcome: "failed"` with the message, and the loop carries on. The `JSON.parse` of the repository record sat one line **above** that `try`.

So one unreadable `repositories/<id>/<login>.json` threw out of `main()`, and `main().catch()` logs and exits 1. The run stopped partway — after students earlier in the list had already had a commit pushed to their `main` and a pull request opened against it — and the sync record was **never written**. The file's own comment says what that record is for: *"what a lecturer reads to see which students got the correction and which need a second look"*. It is exactly what the failure destroyed. `accept.mjs` guards the same file type with the same reasoning; this one did not.

The record is named `<login>.json`, so the filename still identifies the student when the contents do not — the failed row carries a real login rather than "unknown".

Two smaller things from the same read. A notification issue that could not be created was `if (issueRes.ok)` with **no else**: the issue IS how a student learns a pull request is waiting, and failing it silently left the row reading like a clean sync. It records `issue_error` now, which needed a schema addition because result items are `additionalProperties: false`. And the script had **no end-to-end test at all** — everything covered `lib/starter-sync.mjs`, which decides clean-vs-conflict, and nothing drove the script that does the writing. The new harness stubs the API and drives the real file.

Two things that harness taught, both worth keeping: `spawnSync` **hangs** a test that stubs an HTTP server, because the child blocks the same event loop the server runs on — `spawn` and a promise, as the sentinel test already does. And the script's own validate-before-write caught the first fixture: `sha: "head"` is not `^[0-9a-f]{40}$`. The guard rejecting a *test's* invented shape is the pleasant direction of "a fixture must be the shape the app actually writes".

### A sentinel watches a GROUP, and "the deadline moved" was only ever asked of the group.

`find-armable` puts every assignment sharing an exact deadline instant into one sentinel — efficient, and it made the sentinel's own promise false. Its header said *"a lecturer moving the assignment deadline while the sentinel waits is honoured without restarting anything"*, and `currentTarget()` reported the **earliest** across the group. Extending one assignment does not move the earliest, so the sentinel fired at the other's instant and the stop step ran `lockdown.mjs` **for the whole group**: the extended cohort demoted to `pull` before its own deadline, which is the worst outcome this system has and the one hardest to undo afterwards.

`lockdown.mjs` cannot catch it, and that is deliberate: *"Gated on `extended`, not on the deadline alone: a lecturer running a lockdown early still locks the cohort."* It trusts its caller so a lecturer can lock early on purpose — so the caller has to be right. The sentinel now reports each assignment's own deadline, emits `due_assignment_ids`, and the workflow iterates that instead of the matrix's group. An assignment whose YAML could not be re-read still counts as **due**: the armed instant is the best evidence available and it has arrived. Only one positively read as later is skipped. Its timeline records `due: false` and its **own** deadline, because a record claiming a freeze at an instant that was never this assignment's deadline is a false record.

Two more from the same read, both fail-open:

**A capped page walk reported a clean read.** `samplePushedAt` stops after `SENTINEL_MAX_PAGES` (3 = 300 repos) and returned `{ ok: true, reason: null }` with a partial map. That map is **evidence** — it is what settles "I pushed before the deadline" — and a repository missing because the walk ran out of pages was indistinguishable from one that was never pushed. The code argued everything recent is on page one, which holds for a quiet org: the sort is over **all** the org's repositories, so several cohorts pushing near a shared deadline can carry a watched repo past the cap while it is being actively worked on. Running out of pages is now `ok: false` with a count, and the sample carries the reason.

**`find-finalizable` counted an unreadable assignment as inactive.** The `activeCount` loop ended in a silent `catch(e) {}`, and `activeCount === 0` is what makes `daily-activity.yml` **disable itself** — the nightly that enforces every deadline. One unparseable YAML could therefore switch it off, from a read failure. It counts as active now and says so; being wrong that way costs one cron firing that finds nothing to do.

All three were verified by reverting the fix and watching the test fail. Everything in this area still degrades to the nightly, which is the safety net the sentinel's header claims — these were the three places where it degraded to something worse instead.

### One archive per assignment, and where a preservation lives is READ, not derived.

The archive was one repository per org and it only ever grew: measured on real PXL cohorts, student repos on the automation/systems courses run 400 KB - 58 MB each (people commit build artifacts) and git dedups the shared template but not what students add, so four assignments a year at forty students is ~800 MB per org per year in a single repository, against GitHub's ~1 GB soft warning. The one thing that would shrink it - retiring a finished cohort - was impossible without taking every other cohort with it. `pxl-classroom-archive-<id>` now dies with its cohort: retiring a three-year-old assignment is its student repos and its archive, one gesture (RUNBOOK.md §5). `lib/archive-repo.mjs` is the single source of truth, dependency-free and isomorphic (`frontend/src/lib/archive-repo.js` re-exports it as `deadline.js` does for `effective-deadline.mjs`), and it draws one line the rest of the system may not cross: **`archiveRepoName(id)` answers "where does a NEW preservation go" and `resolveArchiveRepo({org, recorded})` answers "where is THIS one"** - the second **takes no assignment id at all**, so it cannot derive by accident. That is the whole backward-compatibility story: `preserve.mjs` has always written `archive_repo` and `preserved_ref` into `preservation.json`, **nothing had ever read either** (the `preserved_sha` class of bug from the other end), and `report.mjs` now propagates them as `archive_repo` / `archive_ref`. An absent `archive_repo` on a *preserved* row is not ambiguity - it predates the change, and everything preserved then went to `<org>/pxl-classroom-archive` - so the fallback is the **legacy** name; deriving instead 404s every submission archived before the change, including the only real one in production. Four more things that must stay true: `archiveRepoName` **truncates with a digest of the whole id** (an assignment id is schema-legal to 100 chars and GitHub refuses a repo name over 100, and unhandled that lands as `fail:create-archive` for the whole cohort *at the deadline*) and hashes the **whole** id, not the truncated head, or two assignments in one course year collide; it returns **null rather than throwing** for an unusable id, because this runs in Vue computeds and a throw there takes the pane down with the control that would fix it (the `localToUtc` bug); `archive_ref` closed a second bug on the way past - the SPA reconstructed `preserved/<id>/<login>` unconditionally, so **every group submission linked to a branch that does not exist**, a team sharing one repo being preserved under its team slug; and the banner's *Archive Repo* button is **absent until something is preserved**, because before that no archive repository exists and a link to one is the page guessing. `tests/archive-repo.test.mjs` fails if anything composes an archive name or a `preserved/` URL of its own - it scans with comments stripped, since the ones this change added name the legacy repo and quote the rule. The test that had "covered" archive links defined `buildStudentArchiveBranchUrl` **inside itself** and asserted on that, so deleting the SPA's link entirely would not have turned it red. ARCHITECTURE §11.3.1, RUNBOOK.md §5.

### Preservation pushes a complete object graph, and never with `--force`.

An org is entitled to forbid force-push with a ruleset (the same thing that made `ec896c8` stop force-pushing the broker), and a rejected push here fails preservation for every student - the safety net the whole deadline flow rests on. Nothing is lost: `refs/heads/preserved/<id>/<login|team-slug>` is fresh per student and `lockdown.mjs` freezes `snapshot_sha` across retries, so a retry pushes the same SHA to the same ref and git reports it already up to date. A genuine non-fast-forward means the archive holds something the system did not put there, which is not a thing to overwrite silently. `preserve/preserve.mjs` must fetch the submission SHA with full history before pushing it to `pxl-classroom-archive`. A shallow fetch (`--depth=1`) grafts away the commit's ancestors and the archive rejects the pack with `remote unpack failed: index-pack failed` - invisible while a student repo is one template commit, fatal once they have history. `tests/preserve-archive-push.test.mjs` reproduces it over `file://`.

### Finalize is complete only when submissions are archived.

The idempotency key is not "a `lockdown-record.json` exists" - `find-finalizable.mjs` re-queues a past-deadline assignment while any student with a `snapshot_sha` lacks a verified `observations/<id>/<login>/preservation.json` (ARCHITECTURE.md §6.2.1). Three invariants keep that safe and must not be broken independently: `lockdown.mjs` **freezes** prior `snapshot_sha`/`lockdown_at` on a retry (re-reading `HEAD` would swap an on-time submission for a late commit - `tests/lockdown-retry.test.mjs`); retries are capped by `finalize_attempts` vs `MAX_FINALIZE_ATTEMPTS`; and `Commit + push` is `if: always()` so the record and counter survive a failed leg. `check-idle` must not disable the workflow when a finalize leg failed, or the retry can never run.

### `late_policy` and `lock_down_enabled` are two decisions, and both used to be dead.

`late_policy: block` said "refuse late pushes" and no code read the field; `lock_down_enabled` said "demote admin -> pull at the deadline" and no code read that either - lockdown demoted everyone on every assignment regardless. Both shipped as form defaults, which is DESIGN.md §1.5: *the UI must not describe behaviour the system does not have.* Now `block` stops the ref with a **repository ruleset** (`lib/submission-lock.mjs`: `update` + `non_fast_forward` + `deletion`, App in `bypass_actors` as `actor_type: "Integration"`) and `lock_down_enabled` is the separate Phase 4 demotion - because "cannot push" and "cannot re-run a workflow" have different costs, and demoting takes Actions, secrets, environments and runners on a course whose subject *is* those things. Confirmed live before shipping: the App pushes straight through an `active` ruleset (`remote: Bypassed rule violations`) while an **org owner** gets `current_user_can_bypass: "never"` and `GH013` - a student is repo admin, strictly weaker. Non-negotiables: **`lock_down_enabled` defaults to `true` when the field is absent** (every pre-existing assignment was demoted at the deadline; inferring "no lock" from a missing field would silently stop freezing live cohorts), **a ruleset is never created without a resolvable App id** (the system would be locked out with no way back), and **a failed ruleset degrades to a demotion, never to no lock**. **Both form defaults are the permissive one, and that is not the same statement as the absent-field rule.** `emptyForm()` writes `late_policy: 'report'` (`block` discards work) and, since 2026-08-31 on Tom's call, `lock_down_enabled: false` - the demotion was arriving on every new assignment whose lecturer never opened the checkbox, and it confiscates Actions, secrets, environments and runners, which is the subject these courses teach. Nothing about the record weakens: phases 1-3 still run and preservation still pushes the snapshot to the archive, so the evidence a dispute rests on does not depend on the field. The absent-field default stays `true` because it governs documents nobody can go back and edit; `buildDoc` writes the field explicitly, so a new assignment carries `false` rather than relying on absence. `tests/submission-lock.test.mjs`, `tests/lockdown-late-policy.test.mjs`, `tests/admin-lifecycle-ui.test.mjs`, `tests/e2e/29-late-policy-control.spec.mjs`. ARCHITECTURE §11.2.1.

### The sentinel's precision was invisible in the record it exists to improve.

It writes no `lockdown-record.json` on purpose, so the nightly hours later had no prior to read and stamped `lockdown_at` with **its own clock** - for a 20:00 deadline the record said the cohort froze at 00:00 and `uncertainty_seconds` reported four hours where the sentinel had achieved seconds. Nothing was lost (nobody could push after the stop, so the SHA is right), but that number is the evidence a lecturer cites in a dispute and it understated the system against them. `lockdown.mjs` now reads the `sentinel-<key>.json` timeline sitting beside the record and credits a **fired** one - `gave-up:runtime` is not credited, because there the nightly really is what stopped the cohort and claiming otherwise invents precision. Credited **per target, not per cohort**: a student whose extension was still running when the sentinel fired was deferred then and is only being stopped now, so their own effective deadline is the discriminator - it is later than the instant precisely when they were deferred past it. `tests/lockdown-phases.test.mjs` pins all three, and the deferred case was written first with the dead flat `deadline_at` override shape, which reads as *no extension at all* - the fixture trap this file already records, hit again.

### The sentinel waits for the instant and stops nothing itself.

`deadline-sentinel.yml` (4-hourly cron, 4.5 h arm window, keyed on **(org, deadline instant)** so assignments sharing a deadline share a job) closes the gap between the deadline and the nightly. Load-bearing details: it **polls rather than sleeps**, and the poll is `GET /orgs/{org}/repos?sort=pushed&direction=desc&per_page=100` — one call for a hundred repos, where per-repo polling would be 7,200 requests against a 5,000/hr limit; `pushed_at` is GitHub's own timestamp, so the resulting timeline (`lockdowns/<id>/sentinel-<key>.json`) is the only thing that can answer "at 21:55 your last push was 21:12", which the committer-date fallback cannot. The stop goes through `applySubmissionLock` via `STOP_ONLY=1`, so there is one implementation of "stop writes" — and **`STOP_ONLY` must never write a lockdown record**, because `find-finalizable.mjs` reads that record's existence as evidence a finalize happened and one with empty `results` strands the assignment forever. Every failure degrades to the nightly (`fired=false` triggers no stop), which is why it is safe; it **ships disabled** and `publish-assignment.yml` enables it beside `daily-activity.yml`. `tests/deadline-sentinel.test.mjs`, `tests/lockdown-phases.test.mjs`. ARCHITECTURE §11.2.3.

### The `until` fallback is honest, not tamper-proof.

Phase 1 fires on the nightly, not at the deadline, so under `block` phase 2 rebuilds the submission with `commits?until=<effective deadline>` and takes `[0].sha` - `null` (a `no_submission`, not an error) when nothing was committed in time. Confirmed live: **`until` filters on the committer date alone** - authored-before/committed-after is excluded, authored-after/committed-before is returned, matching `git log --until` - and `GIT_COMMITTER_DATE` is client-supplied, so this must never be described as proof; the form's own copy says so. It only runs when `pushed_at` (already in hand from the repo object) is after the deadline, so the ordinary case costs no extra call, and the window is the student's *effective* deadline. Under `report` it must not run at all: a late commit **is** the submission there. `preserve.mjs` gained a third bucket for `no_submission` - one slacker used to turn the whole cohort's nightly amber. ARCHITECTURE §11.2.2.

### Lockdown stops the whole cohort first, then records it.

`lockdown.mjs` is four phases (plan / stop / record / demote), not one loop per student. The old loop read a student's `HEAD` and then demoted them, so in a 200-student cohort student 1 froze at T+0s and student 200 minutes later - the demotion is a write against an ~80/min secondary limit - which both gave the end of the list extra time and made the snapshot a smear rather than a cut. `applySubmissionLock({ targets, method })` is the only thing that knows *how* writes stop (`demotion` today, one ruleset flip later); `recordCohortState` reads `pushed_at` off the repo object it already fetches, which is GitHub's own server-side timestamp and the only field in the record a student cannot set. The record carries `locked_at`, `lock_method` and per-student `pushed_at`. Two invariants the tests pin (`tests/lockdown-phases.test.mjs`): **every** stop precedes **any** read, and a phase-2 failure leaves the cohort stopped and is safely re-runnable - a repo that cannot be read still produces no result row, because `preserve` iterates results and a permanently unpreservable row turns every later night amber. Freeze-on-retry stays, but as belt and braces rather than the thing holding the design up.

### One deadline per student, and `lib/effective-deadline.mjs` is where it is decided.

Every comparison against "the deadline" must be the deadline *for that student*, or the system acts against work a lecturer allowed. `report.mjs` had the only copy and it read `override.deadline_at` - a field the Admin Panel stopped writing on 2026-06-17 in favour of the append-only `overrides[]` array that `override.schema.json` requires - while `lockdown.mjs` and `find-finalizable.mjs` never opened `overrides/` at all. So extensions worked nowhere: the student was demoted to `pull` at the assignment's own deadline and then reported as on-time and extended. The test covering it built its fixture in the same dead shape, which is exactly the failure mode this file warns about. Both shapes are read now (old control repos hold the flat one), the array wins, and an extension only ever **extends** - a value before the assignment deadline is ignored rather than shortening it. A group shares one repo, so the most generous member extension governs the team. **The SPA imports the same module** (`frontend/src/lib/deadline.js` re-exports it, as `lib/invite.js` does for the token format) because the rule had forked three ways: the backend and the two lecturer views took the **last** entry of the append-only history, while `AssignmentView` and `GroupAcceptanceCard` took the **first** - so a student granted a second extension was shown, and counted down to, a deadline that had already been superseded. `AssignmentView` also replaced the deadline unconditionally, so an earlier value would have *shortened* it on screen. `tests/effective-deadline.test.mjs` fails if any file outside the module picks the extension in force itself. **Two more things that must stay true:** a student who already has a **frozen snapshot is never deferred**, whatever their overrides say - deferring rewrites their result row with `snapshot_sha: null` and loses the recorded submission (RUNBOOK.md §3.3 covers the after-the-fact grant); and a **malformed extension locks rather than defers**, because a student left deferred on an unparseable date would never be finalized at all. Four more consequences that must stay true together: `lockdown.mjs` **defers** such a student before its first read (no repo fetch, no observation, no permission touched) and records `deferred_until`/`deferred_count`; `preserve.mjs` does not count a deferral as an error, but a missing `snapshot_sha` *without* `deferred_until` still is; `find-finalizable.mjs` re-queues the assignment when a `deferred_until` passes, outside `MAX_FINALIZE_ATTEMPTS` because it is new work, not a retry; and the assignment stays counted in `activeCount`, or `daily-activity.yml` disables itself mid-extension and never comes back. `tests/effective-deadline.test.mjs`, `tests/lockdown-extension.test.mjs`, `tests/preserve-deferred.test.mjs`, `tests/find-finalizable.test.mjs`. ARCHITECTURE §6.2.2, RUNBOOK.md §3.2.

### An empty population is not a failure.

Zero repository records for an assignment (nobody accepted yet) must never fail `collect`/`lockdown` - it turned every nightly finalize red and buried real failures in sibling matrix legs. `lockdown` still writes an empty `lockdown-record.json` so `preserve` reports "no students to preserve" instead of `fail:no-lockdowns`. Likewise a 403/404 on the billing usage endpoint skips that org instead of failing sibling matrix legs - and because requesting an ungranted permission is a **422 at token-mint time**, `weekly-usage-report.yml` re-mints without the billing scope and warns rather than failing the leg before the script's skip can run. System Health and onboarding must surface the missing `organization_administration: read` approval or Enhanced Billing access. That permission lives on the **App**, not the installation: an App created before the manifest declared it cannot have it approved by any org (ADMIN.md §3.1) - `gh api apps/pxl-classroom-provisioner --jq .permissions` is the check.

### An org's base repository permission is a floor under lockdown, and nothing was watching it.

`default_repository_permission` is what every **org member** gets on every repository, private ones included. It grants students nothing today - `provision.mjs` adds them as repository **collaborators**, not members - which is exactly why nobody looks at it: six of seven readable PXL orgs are `none` and `PXL-CSMobile` sat on `read` from its 2024 creation, a year before this system existed. Two things arm it the moment membership is used for enrolment: GitHub grants the **highest** applicable permission, so a base of `write` sits beneath `lockdown.mjs`'s demotion to `pull` as a floor the freeze cannot go below - the demotion reports success and the student keeps pushing; and it applies to **private** repos, so at `read` every member can read `pxl-classroom-control` - the roster's names, student numbers and institutional emails, plus every report. `baseRepositoryPermissionFinding` in `lib/audit.mjs` is the single judgement (`read` -> warn, `write`/`admin` -> fail), surfaced as diagnostics Tier 1. The load-bearing rule is the **absent** case: the field is returned to org admins only, so a value the caller cannot see yields **no check at all** rather than a green one - the same "unreadable is not evidence" rule Tier 1 already applies to `/apps/{slug}`. `tests/org-base-permission.test.mjs`, ADMIN.md §7.

### An organization OWNER among the acceptors cannot be frozen, and only the record said so - afterwards.

`default_repository_permission` is a floor under every org *member*, and the bullet above watches it; an **owner** is not subject to a floor at all - GitHub grants owners admin on every repository - so `demote()` writes `pull`, reads the permission back, gets `admin`, and records `verified: false` / `permission_after: "admin"`. The verify-after-write did exactly its job; **nothing warned**. Found by running it: a live finalize rehearsal on 2026-08-26 whose only student was an org owner reported `0/1 stopped`, and the same shape was then sitting in the real `PXL-Automation-II/2526-examen-aut2-ek2` cohort **four days before its deadline** (two of six acceptors were owners). The cohort is not at risk - `partial` exits 0, so preserve and report still run and everyone else freezes - which is exactly why it needed saying in advance rather than in the record. `unfreezableAcceptorsFinding` in `lib/audit.mjs` is the judgement, surfaced as diagnostics **Tier 3**; it intersects `acceptances/<id>` with **`GET /orgs/{org}/members?role=admin`** - one request for the owner list, never `GET /orgs/{org}/memberships/{login}` per acceptor, which is 200 requests on a 200-student cohort (the arithmetic that put the Feedback PR column behind a button). Four rules it must keep: an owner list that **cannot be read at all** yields *no check*, not a green one (the `/apps/{slug}` rule); a **truncated** list may report a match it found but may never report `ok` ("one page is not the list"); **no branch is ever a `fail`** - the first cut failed on any owner but the signed-in viewer, which assumed a non-self owner would be a *student*, and it cannot be: `provision.mjs` adds students as repository **collaborators**, so a student is only an owner if somebody promoted them, and in practice every owner in an acceptance list is staff (the lecturer, or a colleague testing it - `afx42` on the live exam is another lecturer). Failing put a permanent red on a real exam that nobody should act on, which is how a check stops being read - the same reason a third-party installation is a notice. The wording still separates *"that is you"* from an account the reader may not recognise, and still spells out the one actionable case; and matching is **case-insensitive** (accept.mjs's gate is) while **reporting keeps the caller's spelling**, or a lecturer is sent after an account that, as spelled, does not exist. `tests/unfreezable-acceptors.test.mjs` also pins that `demote()` still writes `pull` and still verifies - the finding asserts a mechanism, and describing behaviour the system no longer has is C4. ARCHITECTURE §11.2 and §11.6, ADMIN.md §7.

### Only a published or closed assignment is finalizable.

`find-finalizable.mjs` checked the deadline and not the state, so a draft with a past deadline had no lockdown record, looked `not-finalized` forever, and queued a four-step matrix leg every night on a system whose whole point is billing zero minutes when idle.

### The `deadline-gap` alarm was structurally guaranteed to fire, for every student, always.

It compared `uncertainty_interval_seconds` against a **one-hour** threshold, and that value is `deadline - lastOnTimeObservation` while the nightly collect observes **once a day** - so the gap is many hours by construction. Measured live 2026-08-26: `PXL-Automation-II`'s tracking issue held six comments for six students, every one a deadline-gap, all reading **"116h"**. And 116h was not staleness at all - the deadline was four days in the *future*, so the subtraction was returning the time **remaining**, a different quantity wearing the name. Two fixes: the value is now only computed **once the deadline has passed** (before it, `uncertainty_interval_seconds` is null rather than a countdown), and the alert fires **once per assignment** at a threshold tied to the observation cadence (24h + slack), so it means the thing a lecturer would act on - *a nightly did not run*. An alarm that always fires is not an alarm, and it was crowding out `late-activity`, which is per-student and real. `tests/report-preservation.test.mjs`.

### The preservation banner promised one number and displayed a different one.

Its copy says *"Delay between deadline and lockdown execution"*, and it read `students[].uncertainty_interval_seconds` - which `report.mjs` computes as `effectiveDeadline - lastOnTimeObservedAt`, the **other side of the deadline**: how stale the evidence was going *in*, routinely hours with a nightly collect. So a cohort frozen at the instant by the sentinel showed a large "lockdown delay", understating the system on the one screen a lecturer would cite in a dispute. Two instants also got confused: `lock_down_at` came from the lockdown **observation**'s `observed_at` - when the nightly *looked* - while `lockdowns/<id>/lockdown-record.json` already held `lockdown_at`, when the student actually stopped being able to push. **Nothing read the record**, so the sentinel-crediting fix above was invisible. `report.mjs` now reads it and carries `lock_down_at` plus a new `lockdown_delay_seconds`; the banner takes the **maximum** across the cohort, because one student demoted late is exactly what the number is for. `uncertainty_interval_seconds` stays - it is a real, different measure - and `tests/report-preservation.test.mjs` asserts the two are never the same value. The e2e fixture had invented **top-level** `lockdown_at` / `uncertainty_seconds`, which appear in no report the backend produces; they only worked because the view had a fallback reading them, so the test described a document that does not exist. Same fixture trap as `earned_points` and `preserved_sha`, third instance.

### `preserved_sha` was null on every report ever generated, and four features hung off it.

`report.mjs` read `preservation.preserved_sha`; `preserve.mjs` writes **`source_sha`** and never had that field. Confirmed against the only real preservation in production - its `preservation.json` carries `source_sha` and `verified: true`, and the report beside it says `preservation_status: "preserved"` with `preserved_sha: null`. Everything gated on the field being truthy was dead: the **archive link** in the student table, **`pxl-classroom download`** (filters on it before fetching anything), **`pxl-classroom grade`** (same filter), and the export manifest's `archive_sha`. The name was right and the source wrong - preserve pushes that exact commit and verifies the remote SHA equals it, so the two are the same object by construction. **Same class as `earned_points`**: a report field every consumer reads and nothing writes, surviving because the fixtures supplied it, so the tests described a document no backend emits. `tests/report-preservation.test.mjs` pins the instance *and* the class - it parses the field names `preserve.mjs` writes and fails if `report.mjs` reads one that is not among them. Two traps in writing that scanner, both of which made it lie rather than the code be wrong: `verified` is a **shorthand property** (`^\s*name\s*[,:]`, not `name:`), and the document's own filename `"preservation.json"` reads as a field access unless string literals are stripped.

## Reports, grading and document shape

### A roster login spelled in another case made one student two rows.

GitHub logins are case-insensitive, and `accept.mjs`'s roster gate has always compared them that way (`s.github_login?.toLowerCase() === login.toLowerCase()`), so a lecturer who types `Alice-PXL` into the CSV gets a student admitted under GitHub's own `alice-pxl`. `report.mjs` then built four indexes on the **raw** string - roster, acceptances, repositories, observations - and unioned their keys. One account, two rows: a phantom `not-accepted` row carrying the name and student number, and the real acceptance row carrying neither. `total_students` and `no_submission` both doubled, `buildDashboardEntry` inherited the inflated count, and the CSV export lost the identity of every student whose roster casing differed. Reproduced against a one-student fixture on 2026-09-01, which is how it was confirmed rather than argued about.

The team index in the same function *was* lowercased, ten lines above the ones that were not - the rule was known and spelled by hand in five places (`norm()` in `effective-deadline.mjs`, `lower()` in `seed-teams.mjs` and `roster-entries.mjs`, two `.toLowerCase()` comparisons in `accept.mjs`). `lib/github-login.mjs` is the one spelling now, and it separates the two jobs that were being conflated: a login is **compared and indexed** lowercased, and **displayed** as whichever spelling the most authoritative source gave - GitHub's where we have it, the roster's only for a student who has not accepted.

### A "pick ours out of the list" helper that falls back to `[0]` answers the wrong question confidently.

Two of them, found in the same sweep, both one `||` long.

`pickClassroomInstallation` ended `|| list[0] || null`. On the `/orgs/{org}/installations` path that list is **every App installed on the org**, so with the PXL App absent, System Health reported *"App installed on org — Installation ID N"* for dependabot and then read dependabot's `permissions` and `repository_selection` as ours. A **Tier 1 misattribution**, which CLAUDE.md already records as what made the 2026-08-21 onboarding failure take hours. Its own test had named the hazard verbatim since the day it was written — *"Taking [0] blindly would attribute somebody else's installation"* — and only ever covered the case where the App **is** in the list.

`pickAutogradeCheckRun` ended `|| runs[0]`, and that one decides marks. With no check run named `/grad|classroom/`, it handed an arbitrary run to `parseCheckRunScore`, which finds no annotations, reports `matched: false`, and awards the full `fallbackTotal` for `conclusion: "success"`. A student is **admin on their own repository**: delete the autograding workflow, add any workflow of your own that goes green, collect full marks from a check the lecturer never wrote. Both return `null` now, and both callers report the absence — *"no autograding run at commit abc1234"* — because "there is a green check run here" is not evidence that grading ran.

### A synthetic object handed to a shared builder loses whatever the builder learns next.

`buildDashboardEntry(assignment, students)` has two callers: `report.mjs` passes the **real** assignment YAML and so gains every new field for free, while the SPA's live refresh synthesises a `pseudoAssignment` from the stored entry **field by field** - it only wants to update one entry. So any field the builder starts reading that the pseudo object does not supply comes out `null`, and the refresh **blanks it on the entry it was refreshing**. It fired within the hour: `max_acceptances` was added to the builder so the dashboard's share block could tell *"live"* from *"cap reached"*, and the next Live Refresh would have erased it. The loaded YAML wins over the stored entry (it is authoritative and the view already has it), with the entry as fallback. `tests/dashboard-entry-inputs.test.mjs` parses the fields the builder reads off `assignment.` and fails when the pseudo object omits one - so the builder and its synthetic caller cannot drift. Same family as `DISPLAY_ONLY_ROW_FIELDS` and the team-manifest rebuild: **a document assembled field by field drops whatever nobody remembered to list.**

### A mock that accepts anything tests nothing, and the e2e fixture accepted every write.

`setupStandardMockRoutes` stored whatever the SPA `PUT` to `/contents/` and answered 200, so **no e2e ever checked that a document the app writes is one the backend could read back** - which is exactly how a member edit shipped writing a team manifest missing its required `created_by` with spec 16 green over it, and how Live Refresh shipped storing `earned_points` on report rows the schema forbids. The fixture now validates a write against the schema for its path (`teams/`, `reports/`, `acceptances/`, `repositories/`, `overrides/`, `grading/`, `students/roster.yml`, `assignments/`) and answers **422** when it fails, the same precedent as the mocked broker running the real verifier: the SPA's own error path fires and the spec's success assertion fails, with the reason in the body. **Unparseable content is deliberately not reported** - several specs write malformed files on purpose to exercise error paths, and a schema has nothing to say about bytes that are not a document. ## Groups, teams and starter code

### The Feedback PR column answers what `pxl-classroom feedback list` answers, and it is a live read.

`open-feedback-prs.mjs` records `feedback_pr_number` and `feedback_pr_url` and **nothing else** - state and review-comment count are on neither the report nor the repository record, and the count changes every time a lecturer reviews. So it sits behind an explicit *Refresh feedback PR status* control rather than firing on render: one `GET /repos/{o}/{r}/pulls/{n}` per **open** PR (which carries `state`, `draft` and `review_comments` together, unlike the CLI's page-the-comments trick), 6-way pooled, and on a 200-student cohort that is 200 requests nobody asked for otherwise. Partial results **are** shown - nothing is committed, so a half-answer is still an answer, and the count that could not be read is part of it. A 404 on a PR means it is **gone**, and is recorded as closed rather than left claiming "Open" beside a dead link.

### The hardening went onto one of the three member lists.

`accept.mjs` reads a team's `members` in three places, and only one of them had been made safe. The comment on that one says exactly why:

> a bare `JSON.parse` plus `teamData.members.some(...)`, so one corrupt or half-written manifest threw a SyntaxError or a TypeError out of `main()` and into `fail:exception` - a red run and no repository, for a student whose only mistake was accepting after somebody hand-edited a file.

`team.schema.json` declares `members: { items: { type: "string" } }`, and **nothing validates a manifest on the way in** - `accept.mjs` reads whatever is in the control repository. So a single hand-edited entry that is not a string broke the other two reads, in two different ways:

* **The oldTeam scan** (`m.toLowerCase()` inside a bare `catch {}`). It threw, the catch swallowed it, and that team file was skipped - which silently hid the team the student was *already in*. They joined another without being removed from the first, and two manifests named them.
* **The oldTeam filter** on a team switch, and this is the sharper one. `.some()` stops at the first match, so a bad entry sitting **after** the student is never evaluated in the scan; it reaches the filter, which evaluates every entry, and throws out of `main()`. Exit 1, no repository, for a student doing nothing but changing team.

Both are `String(m).toLowerCase()` now, which is what the hardened read already did ten lines below. **A defensive fix belongs on every reader of the same shape, not the one that was in the stack trace** - and the two tests for it were written by reverting the fix and watching them fail, because a guard for a case nobody can reproduce is worth exactly what it can be shown to catch.

Found reviewing `accept.mjs` end to end. Nothing else in it needed changing: the file is the most carefully reasoned in the repository, and the one defect hypothesis worth chasing - `opened.githubId !== githubId` looking like a number compared to a string, which would reject every claim as a replay - was wrong, because both call sites pass `Number(githubId)` deliberately.

### Group Assignments (M:1 Student-to-Repository mapping)

Polymorphic assignments (`assignment_type: "individual" | "group"`). Configured via `group_config` (`formation_mode: "self-service" | "pre-assigned"`, `max_team_size`, `min_team_size`, `allow_team_creation`). Teams are stored as manifests in `teams/<id>/<team-slug>.json` conforming to `team.schema.json`. Group repos use `{team_slug}` in `repository_name_pattern`. Sequential concurrency on `accept-${org}-${id}-${team_slug || login}` serializes joins and guarantees capacity limits without distributed locks. The first member provisions the repo from the template; subsequent members receive `PUT /collaborators/{login}` with admin access. Team switching revokes old repo collaborator access (`DELETE /collaborators/{login}`) and adds to new, marking 0-member teams `vacant: true`. Lecturer dashboard provides segmented Teams View and Students View, under-capacity warnings, and interactive team creation/member management modals. Lockdown demotes all team members to `pull`; preservation archives to `refs/heads/preserved/<id>/<team-slug>`; reporting aggregates top-level `teams` array and maps `team_slug`/`team_name` across CSV exports and student tables.

### Carrying groups forward (team seeding).

Group membership is per assignment, so assignment 2 would make students re-form assignment 1's teams. `lib/seed-teams.mjs` is the single pure planner (no fs, no fetch, no Node builtins - the SPA imports it) shared by `SeedTeamsModal.vue` and `pxl-classroom teams seed`; it materialises `teams/<target>/<slug>.json` from a previous assignment's manifests or the roster's `team_slug`/`team_name` columns. **The roster is never written** - copy-forward from the *latest* grouping is drift-free, while a roster record would go stale the moment a student switches teams, and a roster CSV re-import replaces the file wholesale (`RosterTab` commits the parsed CSV, `CSV_COLUMNS` has no `teams` key) and would silently wipe it. Two invariants the planner exists to protect: **a login appears in at most one team file per assignment** (`accept.mjs` takes the first directory match, so a duplicate makes membership random) and **a target team that already has members is never overwritten**. It refuses - never truncates - on over-capacity teams, and refuses when target and source share a `repository_name_pattern`, because provisioning is idempotent on repo *existence* and would hand students the previous assignment's locked-down repository. Writes go through `lib/gittree.mjs` in **one** commit (33 teams via the Contents API would be 33 commits against a ~80 writes/min secondary limit; `utf8Base64` is `Buffer`-or-`TextEncoder` so the module is isomorphic) and **must** be followed by a `regenerate-dashboard.yml` dispatch - students read the generated public teams file, never the control repo, which is why lecturer-created teams used to be invisible until the next nightly run. Seeding is not enrolment: no repo exists until a member accepts, so `TeamsTable` dims members without an acceptance record - but only on a published assignment, since acceptance is impossible on a draft and flagging every member there is noise (`hasAccepted` is the fact, `isPending` is the display question; the undo depends on the first, the dimming on the second). **A bulk write needs a bulk undo:** `planUnseed` (shared by `TeamsTable`'s `Undo seed (N)` and `pxl-classroom teams unseed`, so the rule cannot fork) deletes - in one multi-file gittree commit, `content: null` per path - only teams carrying `seeded_from` with no repo and no accepted member; per-team deletion was the only route and `deleteVacantTeam` refuses teams with members. `planSeed` also returns `unplaced` (roster-relative, omitted under `roster_mode: open`) and names the students a kept target team strands, because after a carry-forward that list is the entire remaining manual task. `group_config.unassigned_fallback` (`block` default | `self-service`) is what stops a pre-assigned assignment from dead-ending late enrollers, and `accept.mjs` now enforces pre-assignment server-side (`rejected:team-not-assigned`) instead of honouring any team the payload names.

### Starter code sync copies content, and the two calls it used to make disagreed.

Measured live on 2026-08-25 against repos created by `POST /generate` (same-owner and cross-owner): `POST /merges {head: templateSha}` **succeeds** - a generated repo stays in its template's object network, so the SHA resolves and the merge commit takes the template's root as a second parent - while `compare/{templateSha}...main` is a **404 `No common ancestor`**. *(An earlier pass through this file asserted the merge 404'd too and called the feature impossible. It compares **blob SHAs** across three trees - template at the commit, template at its parent, student's `main`, each one `GET /git/trees/{ref}?recursive=1` - because a git blob SHA is a content address and is identical in every repository holding the same bytes: matching `head` is done, matching `base` means untouched, anything else is the student's. Load-bearing: the split is **per file**, not per student (hence the `merged-and-pr` outcome - one edited file must not hold back three other corrections), the PR branch is cut from the **student's own** `main` so no foreign SHA is involved, writes go through `lib/gittree.mjs` in one commit, and **`selected_files` is now applied** - it used to be recorded in the sync record and pasted into the PR body while the merge carried the entire template HEAD regardless, so the modal said "Files to Synchronize (1/1)" over an operation syncing everything (C4). A truncated tree listing **fails** rather than reading as "the student deleted everything", and a commit touching >300 files says so rather than silently offering GitHub's first 300. **Re-running adopts rather than duplicates**: each sync PR carries `<!-- pxl-starter-sync: <templateSha> -->` and a later run of the same sync reuses it - without that, a live rehearsal's second run opened a *second* PR (`#1` then `#3`) in the same repo, and re-running is exactly what a lecturer does when a sync looks like it did nothing. The open-PR list is walked in full, because a missed marker is a duplicate rather than a visible error. The unit is **one template commit** because the use case is "I need to correct a mistake in the assignment" - which also means a lecturer who solved the exercises in the template will sync their solution; RUNBOOK.md §6.13 says so.

## The SPA: routes, controls and copy

### `.catch()` on a call that never rejects, twice, on repository access.

Swept after the copy button, because that bug has a shape — a control announcing an outcome it never verified — and it was worth asking where else it lived. Every control handler in the SPA was read. Almost all of them are honest: `SeedTeamsModal.apply` even reports the partial case where the manifests were written and the dashboard dispatch failed, which is the hard one to get right.

Two were not, both in `TeamsTable`, both wearing the same disguise:

```js
await addCollaborator(token, org, repo, m, 'admin').catch((e) =>
  console.warn(`Failed to add collaborator ${m}:`, e)
)
…
toast.success(`Team "${name}" updated successfully.`)
```

**`addCollaborator` returns `ghApi(...)`, which RESOLVES `{ ok: false, status }` on an HTTP failure.** It does not throw. So the `.catch()` could not fire for a 403 or a 404, the returned value was dropped on the floor, and the lecturer was told it worked. A student whose access could not be granted was written into the manifest with no repository; a student who could not be *removed* kept admin on a repository they are no longer part of, which on an exam is the sharper half.

`moveMember` is the instructive one. Its reporting was already correct — it collected `problems` and raised a distinct "moved, but repository access needs attention" error — so a reviewer reading it sees a handled failure. The collection just could never happen, so it took the success branch every time. **A `.catch()` on a resolving function is worse than no handler at all: it is the appearance of care, and it stops anyone looking.**

`tests/button-honesty.test.mjs` sweeps for it now, with balanced-paren matching rather than a regex — the first draft used a lazy `[^;]*?` and reported `res.json().catch(() => null)` three lines away as a dead catch, which is a promise that genuinely does reject. It also pins the premise it rests on: that `ghApi` returns a result object rather than throwing.

### The other way to throw the answer away is to not ask for it.

`.catch()` on a resolving helper was one shape. Sweeping for the generalisation — `await f(...)` as a bare statement, result discarded — found two more, and this shape reads even more like success because there is nothing on the line to look wrong.

`RosterTab.confirmUnlink` deleted the claim record and the failed-attempt counter and then said so:

```js
await deleteFile(token, org, repo, `students/claims/${id}.json`, message)
await deleteFile(token, org, repo, `students/claim-attempts/${id}.json`, message)
toast.success(`Unlinked @${login}. They can claim again.`)
```

`deleteFile` resolves `{ ok: false, status }` — its own GET-then-DELETE returns that shape for a missing file, and `ghApi` returns it for a 403. So a permission failure or a sha conflict left the binding in place, the `catch` never fired, and the lecturer read the one sentence that was certainly false. The counter delete is now 404-tolerant for the same reason the TeamsTable removal is: a student who never exhausted their attempts has no counter file, and that is the end state we wanted.

`removeCollaborator` was the sharper one, because the discard was *labelled*:

```js
try { …cancel any pending invitation… } catch { /* non-critical */ }
return res
```

Removing a collaborator does not withdraw an invitation they have not accepted yet. It stays live and they can accept it afterwards, back onto the repository they were just removed from — so the function's own docstring promised something its return value did not report. Both call sites in `TeamsTable` were already reading `.ok` correctly and were being handed the wrong `ok`. Two rules already written down cover it: **never describe behaviour the system does not have**, and **unreadable is not evidence** — a failed invitations *read* was being reported as "there was none". The cancel outcome now reaches the caller as a non-ok result and the existing `!res.ok && status !== 404` handling does the rest.

`tests/button-honesty.test.mjs` sweeps for the shape and pins both fixes. Bare `f(...)` without `await` is deliberately not flagged: that shape here is a `Promise.all` array element, where the array collects every result — six of the first draft's eight hits were those. The sweep was verified by dropping a real offender into the tree and watching it fail, not by reading it.

### The copy button said "Copied" over an empty clipboard, and nobody could sign in.

Reported from live use on 2026-09-01: *"copy code using the button does not copy code. no one can log in."* Both halves were the same bug. The device-flow card shows a user code that has to be pasted into GitHub; a student who cannot get it onto the clipboard cannot complete sign-in, and the code is the only thing standing between them and their repository.

The button did this:

```js
let ok = copySync(code)
if (!ok && navigator.clipboard?.writeText) {
  navigator.clipboard.writeText(code).then(() => {…}, () => {})
  ok = true                          // claims success, before knowing
}
copied.value = ok                    // button says "Copied"
window.open(verificationUrl, …)      // and takes focus away
```

`writeText` is **rejected on an unfocused document** — reproduced in the browser: `NotAllowedError: Document is not focused.` — and `window.open` unfocuses it microseconds later. So the write lost that race, its rejection went into `() => {}`, and the button reported success over an empty clipboard.

**The fix is the ORDER, and it took three attempts.** The first SPLIT the button in two, on the reasoning that the open had to stay synchronous inside the click or a popup blocker would eat it — reasoning that was never measured, and that threw away a deliberate UX decision (one gesture, because two clicks are easy to get half-right: open the page, then discover you never copied the code). The second made it one button again and **awaited** the write before `window.open`, so the write completes while the document still has focus and `ok` is the truth rather than an assumption. That shipped. It was also wrong, and the next section is why.

**The second fix broke Firefox, and the reasoning that justified it was Chrome-shaped.** Reported from live use 2026-09-01: *"the copy doesn't work anymore… the live production site is broken now."* The paragraph above used to end with "a resolved clipboard write takes a millisecond or two, and transient user activation lasts about five seconds, so the open is nowhere near the blocker" — measured on nothing, and true only of Chrome. An `await` does not merely spend *time*: engines stop **attributing** a clipboard call, and a `window.open`, to the click handler once one has intervened. MDN says it outright — after an await "the function call is then not anymore assigned to a click handler" — and Firefox tracks it as bug 1605928, *"writeText() does not work in asynchronous environments"*. Two consequences, both invisible in Chrome: the `execCommand` fallback inside `copyText` ran **only after an await**, so it was refused in precisely the case it existed for (a fallback that cannot run — the `.catch()`-on-a-resolving-promise shape, one level up), and Firefox's popup blocker really did get involved in the open. **The answer was in the platform's own documentation the whole time.** A claim about browser behaviour that no test in this repo can hold — "the blocker is not involved", "activation lasts five seconds" — is exactly the kind that has to be checked against the vendor's docs before it is written down as reasoning, and it was not.

**The third fix is to not yield at all.** `copyText` tries the **synchronous** path first and the async API second, and `copyAndOpen` is no longer `async`: the sync copy finishes inside the gesture, its answer is known without yielding, and `window.open` therefore runs in the same synchronous turn as the click. `execCommand` being deprecated is not the liability here — being *synchronous* is the entire point, and if an engine ever drops it this degrades to the async API rather than breaking. Only when the sync path is unavailable is the async one spent, and then the window stays **shut until the write settles**, because opening it is what makes an in-flight write reject. The button is also `btn-primary btn-lg` now: while the card is up the sign-in button is `v-if`'d out, so it is the view's one CTA (DESIGN.md §1.2, §3). Not `btn-success` — green is the student's accepted state, and a button that is green before it has done anything claims an outcome it has not reached.

Two smaller things came out of the same read. `noopener` in window.open's FEATURES string makes it return **null even on success**, so `if (!win) toast("Allow pop-ups")` fired on every single click — the opener is nulled on the returned window instead, and null now means blocked. And when the copy does fail the card *says so in the page* (a toast is gone in seconds, and this is the step the student is stuck on) and selects the code, so the manual path is Ctrl+C and nothing else.

**Why no test caught it, which is the sharper half.** There was a guard, `tests/device-flow-clipboard.test.mjs`, asserting three things — the copy is initiated before `window.open`, a synchronous path exists, and there is an `else toast…` branch for failure. All three were true. The third is the lesson: **the branch existed and could never run**, because the line above it had just forced `ok = true`. A test that greps source text cannot tell live code from dead code — the same sentence `tests/invitation-link-surface.test.mjs` opens with, learned again one component over. The e2e could not help either, and that was already written down in the guard's own header: headless Chromium with clipboard permissions granted does not enforce the focus rule, so the browser test passes with the bug present.

The fix for the fix: the behaviour moved into `frontend/src/lib/clipboard.js` with its dependencies injected, and `tests/clipboard.test.mjs` **runs** it — a rejected write with no fallback must resolve `false`, and does. That still did not catch the second regression, because the second regression was not in the module: it was the `await` in the *caller*, which no unit test can see and which headless Chromium does not punish. So `tests/device-flow-clipboard.test.mjs` was rewritten around the structural property both regressions violated — **`copyAndOpen` must not yield before it copies and opens** — and, per the rule about absence assertions passing vacuously, it was verified by putting the `await` back: 2 of 8 fail with it, 8 of 8 pass without. The unit test that asserted "the async API is used first, and awaited" was **inverted**, and its comment says why, because that sentence was the bug.

**Ten copy implementations across eight files** were found in the sweep, and a second one was lying outright: `StudentDiagnosticsModal` reported *"Diagnostic report copied to clipboard"* from its `.catch()`, from its `else` branch, and from its outer `catch` — success on every path, including the ones that copied nothing. LESSONS.md already records this shape for the invitation link ("three implementations of *put the link on the clipboard* across two views, one silently broken for months"); only that one had been consolidated, and the rest kept their copies until this.

### A Node builtin in an isomorphic module blanks the SPA, and `npm run build` says nothing.

Shipped and live on 2026-08-27: `lib/audit.mjs` and `lib/archive-repo.mjs` were pointed at `lib/deployment.mjs`, which reads `deployment.yml` with `node:fs`/`node:url`. Vite **externalizes** node builtins instead of failing, so the build was green, the value under test really was in the bundle (via the SPA's own `?raw` reader), and the landing page rendered - because those two modules only load in **lazy route chunks**. The first navigation to a dashboard route got `TypeError: (0, sr.fileURLToPath) is not a function` and a **blank page**. Every cheap check passed; only running it found it. Three things follow. **The static/dynamic split is the whole rule**: a static import of a builtin is evaluated when the chunk loads and is fatal, while a dynamic `await import("node:fs/promises")` inside a function only runs if called - which is exactly why `lib/yaml.mjs` may export `parseYaml` to the SPA while keeping `loadYaml` Node-only, and why hoisting that import would break the health modal. **`#deployment` is the escape hatch**: root `package.json`'s `imports` field resolves it to `lib/deployment.mjs` in Node, `frontend/vite.config.js`'s `resolve.alias` resolves it to `frontend/src/lib/deployment.js` in the browser - one `deployment.yml`, two loaders, identical export surfaces (pinned). Threading configuration through every call site was the alternative and is worse for a module like `archive-repo` whose functions are called everywhere. And **the baseline you compare against must be a real one**: 9 e2e failures were dismissed as pre-existing because stashing the working tree still left the *committed* breakage in place - `git stash` is not a clean checkout. `tests/spa-bundle-safety.test.mjs` walks the SPA's import graph transitively and fails on any static builtin, naming the chain.

### The one dependency that is not `api.github.com` had nothing watching it.

Sign-in cannot reach `github.com/login/*` directly, so it goes through a proxy, and since the ordering fix the primary is the PXL Worker - on the critical path of every sign-in, in a single-owner Cloudflare account. A Worker outage was invisible until somebody tried to sign in, which for a lecturer is five minutes before a lecture. Diagnostics Tier 0 now probes it with an **OPTIONS preflight** - the cheapest thing the Worker answers, needs no `client_id`, mints no device code, leaves nothing behind. It is a **warn, never a fail**: there are two proxies and the second one covers this, so "sign-in is broken" would often be false - but the warning names the cost of the fallback (a third party seeing the token) so a silently-spent failover is not mistaken for a healthy system, which is exactly what let the third party stay primary for as long as it did. It runs **only when the caller supplies a prober**, because this module is imported by Node and tests, and a check that makes an unrequested network call from a unit run is worse than no check.

### The student's waiting screen may not guess why it is waiting.

Reported live 2026-08-24: fifteen seconds after accepting, the page said GitHub might be waiting for the student to accept a repository invitation and offered a link. The link **404'd**, and there was no invitation — an org owner or member is added as a **direct collaborator** and GitHub never sends one. The repository appeared at 20–30s. ### GitHub's repository search hides forks, and a fork can be a template.

### "No templates" must mean no templates, not no answer.

`listOrgTemplates` falls back to `listOrgRepos` when the `is:template` search fails, and that helper **swallowed a failed page** - `break` out of the pagination loop, return what it had - so a 500 on both routes produced `[]` and the panel rendered "This organization has no template repositories yet", sending a lecturer to create a template they may already own. `listOrgRepos` now takes `{ failFast }` (default off, so partial-list callers are unchanged) and the fallback leg passes `true`, because it only runs once the search has already failed and an empty result there is *no evidence*, not evidence of none. ### Theming is token-only.

The SPA is dual-theme (dark default / light / system). Every colour is declared **once** in `frontend/src/style.css`'s `:root` as `light-dark(<light>, <dark>)`; the toggle flips `color-scheme` via `data-theme` on `<html>` and every token re-resolves. **`:root` is the only place in the codebase a colour literal may appear** - no hex, `rgb()`/`rgba()` or named colours in component `<style>` blocks or inline `style=`, and no `var(--token, #fallback)` fallbacks (a fallback silently pins one theme). `light-dark()` returns a `<color>`, so it cannot wrap a whole `box-shadow` - only `--shadow-color-*` is themed, geometry is shared. Undefined custom properties fail **silently** (`border-color` -> `currentColor`, `background` -> `transparent`, `box-shadow` -> `none`), which is how `--border-color`, `--accent-amber`, `--color-border`, `--shadow-glow`, `--bg-hover`, `--bg-active` and `--accent-primary` all shipped broken. `tests/theme-tokens.test.mjs` enforces all four rules; see `DESIGN.md` §2 and §5. The runtime is `lib/theme.js` (`themeMode`, `resolvedTheme`, `setThemeMode`, `toggleTheme`). **The toggle is two-state**: `system` is only the implicit state of a visitor who has never used it, and the first press leaves it permanently - following the OS after someone has stated a preference would override them. `THEME_MODES` is what the toggle emits (`dark`/`light`); `STORABLE_MODES` adds `system` for stored values and `?theme=`, stored in `localStorage` under `pxl_theme` behind `try`/`catch`; a plain visit never writes a preference, only an explicit choice or a `?theme=dark|light|system` override does. **The default follows the OS** (`:root { color-scheme: light dark }`) - a first-time visitor gets whichever theme their machine is set to, and that is also the no-JS behaviour since an absent `data-theme` resolves from `prefers-color-scheme`. An explicit `light`/`dark` pins it regardless of the OS. Every toggle persists (`setThemeMode` -> `persistMode`); a plain visit never writes a preference, or `system` could never follow a later OS change. The inline boot script in `index.html` duplicates the storage key and mode list deliberately (it must run before the module graph or light-mode users flash dark) and sits *after* the SPA shim so a `404.html`-redirected deep link has its `?theme=` back before it reads it; the test asserts the copies stay in sync.

### A field that does not exist compares as a constant, and `!==` is the dangerous half.

`AssignmentDetailView` counted acceptances with

```js
s.repo_name || s.acceptance_state === 'accepted' || s.status !== 'no-submission'
```

The field is `submission_status`. `report.schema.json`'s student items are `additionalProperties: false`, so `s.status` was **never** a row field: `undefined !== 'no-submission'` is true, the `||` chain short-circuited on every row, and the count was the whole roster. A report carries a row per roster student, `acceptance_state: 'not-accepted'` included — so on a 30-student cohort with 8 acceptances and a cap of 10, the panel showed **30 accepted and raised "cap reached" with two slots free**, and the invitation share block said students could not accept when they could.

Two things make it worth writing down rather than just fixing.

**The correct rule was already in the file.** The same view imports `lib/dashboard-aggregate.mjs` and calls `buildDashboardEntry` to WRITE `accepted: students.filter(s => s.acceptance_state !== 'not-accepted')` into `reports/dashboard.json`. One file, one cohort, two accepted counts — one persisted and one displayed, disagreeing. The predicate is `countAccepted()` now and both callers use it.

**The mis-spelling was there twice, and only one instance was fatal.** The search filter read `s.name || s.full_name || roster?.name || …` — also fields no schema declares, also always `undefined`, and completely harmless because they sit in an `||` chain. That is the discriminator `tests/report-row-fields.test.mjs` sweeps on: it flags a **comparison** against an undeclared row field, because that is a branch which can never be taken, and ignores a dead fallback, because a guard that reported both would be argued with until somebody switched it off.

Removing `s.name` then failed an e2e test, which is the third thing: the fixture had written `name: 'Alice OnTime'` onto a report row, a field the backend cannot produce, and **the test only passed because the app read the same wrong field**. Fixture and code agreed with each other and with nothing else. That is the shape already recorded two entries below as *two fixtures described a system that does not exist* — here the app was one of the two.

## CLI

### `--dry-run` had no test at all, and its P0 was real.

CLAUDE.md calls dry-run sacred because `feedback open --dry-run` once created real pull requests; swept 2026-08-27, **not one test in the suite mentioned dry-run**, across five commands that take the flag. `tests/dry-run-safety.test.mjs` is honest about being a **shape** check - the CLI talks through Octokit, so proving "no write was issued" means intercepting its request layer - and pins the property the P0 violated: the flag is consulted **before** every mutating call, not after. Writing it produced a false positive worth keeping: `feedback.mjs` declares `openDraftPr` at the top of the file and calls it after an `if (opts.dryRun) continue`, so the POST is lexically above every guard and perfectly safe. **A helper defined early is not an unguarded write**; what matters is whether it is *invoked* after a guard.

### The shape check said what it could not do, so the next step was written down for it.

`tests/dry-run-safety.test.mjs` is honest about being a lexical check and names its own successor in its comment: *"the CLI talks through Octokit, so proving 'no write was issued' means intercepting its request layer"*. `tests/dry-run-behaviour.test.mjs` does that, against the real `cli/bin/pxl-classroom.mjs` under `node --import`, for seven of the eight `--dry-run` entry points. `grade` is the eighth and is listed in `DEFERRED` with its reason - a gap with a sentence beside it, rather than a silence.

**The design is differential, because the failure mode of a behavioural test here is vacuity.** A harness that never gets far enough to reach a write proves nothing while passing, so every command runs twice against the same canned API and both halves are asserted: the WET run must issue at least one mutating request, and only then does "the dry run issued none" mean anything. Two more assertions guard the guard - the dry run must have made *some* request (a crash is not evidence), and a read-only probe must show the interceptor is actually loaded, since an unstubbed CLI that fails to authenticate would also write nothing. It was verified by breaking a real guard: `if (false && opts.dryRun)` in `teams seed` turns the test red and names the four writes it would have made.

Three things came out of building it, none of them about the CLI:

**A test harness that patches process globals can swallow the test runner.** The first version ran in-process and replaced `globalThis.fetch`, `process.exit` and `process.stdout.write`. Node's own reporter writes through `process.stdout`, so a patched stdout captured the runner's events into a string instead of emitting them: **three of eight tests vanished and the suite reported `pass 5, fail 0`.** Nothing was red. It surfaced only because running the same file directly printed `1..8` while `node --test` printed `1..5`, and the correlation that looked causal for an hour - the missing cases were exactly the ones without a `repo` property - was a coincidence of timing. Child processes now, with their own stdout and no globals to restore. **A green suite is not a suite that ran.**

**A fixture that is not the shape the app writes fails at the app, if you are lucky.** The first roster fixture was `schema_version: 1` with no `student_number`; `roster promote` refused to commit an invalid roster and said exactly why. That is the product's own validation catching the test - the pleasant direction of the rule that a mock which accepts anything tests nothing.

**A deliberate scope boundary.** `resolveOrg` calls `saveConfig({ last_org })` on every run, dry or not, so `--dry-run` does write one thing: the CLI's own memory of which org you last named, in `~/.config/pxl-classroom/config.json`. That is not what "no writes, no PRs, no commits" is about - the rule is about the system under management - and the flag's help text promises the value is remembered. Recorded here so it stays a decision rather than an oversight found twice.

### Dry-run is sacred.

Every CLI `--dry-run` must have zero side effects - no API writes, no PRs, no commits. (`feedback open --dry-run` creating real PRs was a P0; fixed in e967035.)

### CLI destructive ops confirm.

`roster import` prompts before committing removals (TTY) or requires `--force` (non-TTY); `feedback open` separates newly created vs adopted pre-existing PR counts and exits non-zero on partial failure; `--concurrency` parses to positive integers only. Local host runner (`grade --runner host`) prompts for interactive confirmation on TTYs, requiring the `--force-host` bypass flag, or exits non-zero on non-TTY.

## Talking to GitHub's API

### `/orgs/{org}/installations` returns an OBJECT, and both fallbacks behind it were dead.

`checkInstallation` reads `/user/installations` (correctly, as `{ total_count, installations }`), then falls back to `/orgs/{org}/installations` - which it read as a **bare array**, so `Array.isArray(data)` was false and the branch whose own comment says *"works for org owners with PAT"* never ran once. The step after it, `/orgs/{org}/installation` (singular), needs an **App JWT** and answers `401 A JSON web token could not be decoded` to a lecturer's user token. So an org owner whose `/user/installations` does not list the org was told *"No PXL Classroom App installation found on this org"* for an org where it plainly was - a **Tier 1 false negative**, and a Tier 1 misattribution is exactly what made the 2026-08-21 onboarding failure take hours. Both shapes verified against the live API on 2026-08-24. `lib/audit.mjs` now exports **`pickClassroomInstallation`** (and `APP_CLIENT_ID`), shared with `lib/diagnostics.mjs` - shared because the two copies had already drifted on precisely this, and because taking `list[0]` blindly would attribute another App's installation, and its `repository_selection`, to us. `tests/installation-shapes.test.mjs`.

### One page is not the list.

A GitHub list endpoint answers with a page; reading it and then making a statement about the whole collection is a confident claim off a truncated read - the call *succeeds*, so no error path fires and no fallback runs. Three shipped, all found by looking for that one shape: the Tier 4 **invitation exposure sweep** read `issues?per_page=100` and then reported `ok` - "no acceptance issue is carrying an invitation" - which is an all-clear on a security control, and a cohort of 200 opens 200 issues, with "more than a hundred" being the exact shape of a *real* finding; **`notify.mjs`'s dedup** read the first 100 comments and GitHub returns them **oldest first**, so past a hundred the marker for a recent event was never in the window and dedup stopped deduplicating *anything*; and **`getInvitations`** used the default page size of **30**, so a student with invitations across several courses could have theirs on page two - which the waiting screen then read as "there is no invitation" and told them setup had failed (it no longer draws that conclusion from any answer - see *A 200 is not permission to draw a conclusion*, below). Rules: use `ghAll`/`ghAllItems` from `lib/gh.mjs` where the transport allows (it walks Link headers *and* carries the rate-limit retry policy); walk `&page=N` until a short page where it does not; and where a walk is capped, **the capped case may not report `ok`** - say it was not finished. In tests, a Playwright route that sets a `link` header must also set **`access-control-expose-headers: link`**, or CORS hides it from JS and the pagination under test silently sees one page. `tests/list-pagination.test.mjs`.

### A 200 is not permission to draw a conclusion.

`GET /user/repository_invitations` answered **HTTP 200 with an empty list** to a student who had a pending invitation. Measured on 2026-09-03, `PXL-Automation-II/test-pe3`, both halves within the same minute:

```
$ gh api repos/PXL-Automation-II/test-pe3-tomccargo/invitations
[{ "invitee": "tomccargo", "permissions": "admin",
   "created_at": "2026-09-03T08:53:01Z" }]
```

and the page, signed in **as `tomccargo`**, polling that endpoint every three seconds for two and a half minutes, never saw it. The acceptance page's rule was a three-way split - a match means `invited`, a *failed* read means we are blind and a guessed link beats silence, and **an answer naming nothing means there is nothing to accept**. The middle case is the whole bug: it turned a successful HTTP call into knowledge nobody had. So the student was told *"GitHub has no repository for you and no invitation waiting, so setup did not finish. This is not something you can fix from here"* - beside a repository that existed, holding an invitation with their name on it, which they could have accepted in one click. The diagnostics modal read the same signal and reported **"Repository Collaboration Invitation: Clear - No blocked invitations detected"** under the banner **"All diagnostic checks look healthy"**. Three surfaces, one false premise, and every one of them confidently wrong in the direction that strands the student.

The mechanism is not settled and the fix does not rest on it. We sign in through the **App's device flow** (`startDeviceFlow` takes the App's client id; OAuth *scopes* are an OAuth-App concept and a GitHub App ignores the `scope` parameter, so the `user:email` default was never doing anything either way). GitHub documents that a user access token reaches only what **both** the user and the App can reach - and a student holding nothing but a pending invitation does not yet have access to that repository, so the intersection may be empty by construction. Plausible, unproven, and irrelevant to what the page must do.

What the page must do is stop asserting the negative: **a match is the only proof, and everything else - an error, an empty list, a truncated walk - is *unknown*.** `frontend/src/lib/invitation-evidence.js` is the one judge, imported by both student surfaces; `proven: false` is documented as "unknown, never none". The guessed `/<org>/<repo>/invitations` link is now offered whenever nothing is proven, held back to `pollCount >= 20` (~60 s, past the 20-40 s ordinary case) so it is not put in front of every student on the happy path, and the copy beside it says the page cannot tell rather than that an invitation is waiting. **The 404 is the feature**: opening that link renders the invitation if there is one and 404s if there is not, which makes it the one check a student can run themselves - so the timeout state names both possibilities, says it cannot choose between them, and explains what each outcome of the click means. The diagnostics check reports **"Cannot be checked from here"**, the summary banner claims only *"No blocking problem found in what this page can check"*, and the copyable report carries `Pending invitation: unknown`, because that report is what a lecturer reads.

**The obvious next idea does not work either, and the documentation says it should.** Org membership would settle the question by implication, because a non-member granted a private repository is *always* invited — and `tomccargo` is not a member of `PXL-Automation-II` (404 on `orgs/{org}/members/{user}`, checked with a hub token). The App declares **`members: write`** (`gh api apps/pxl-classroom-provisioner --jq .permissions`), and GitHub's *Permissions required for GitHub Apps* reference lists `GET /user/memberships/orgs/{org}` under **Organization → Members** at `read`, token type **UAT** — a user access token, which is exactly what the SPA holds. Both checks say yes. Run from the student's own session:

```
GET /user/memberships/orgs/PXL-Automation-II  -> 403
   "You do not have access to this organization membership."
GET /user/repository_invitations              -> 200 []
```

The second line is the confirmation of everything above, taken from the student's token in their own browser rather than inferred from how the page behaved. The first is a **trap**: the permission is declared, the reference lists the token type, and it still 403s — so anyone reaching for it will spend the same half hour reaching the same wrong conclusion. `GET /orgs/{org}/members/{username}` is listed for UAT *and* IAT and is untested here; it was not needed once the hub could answer.

**What answers is the hub, and it always could.** `provisioning/provision.mjs` gets **201** from `PUT /repos/{org}/{repo}/collaborators/{login}` when GitHub sends an invitation and **204** when the student is added directly, and it already logged which. `acceptance-handler.yml` now posts `provisioned:invited` to the student's own broker issue on the 201, over the channel `comment-acceptance-outcome.mjs` already uses for rejections. The page reads it from the third poll tick: **6.4 s in the e2e**, against a 60 s hold-back on the guessed link and a ~160 s timeout. Only the 201 is published — a 204 means the student is already a collaborator or an org member, this comment lands on a **public** repository, and "this account is an org member" is not ours to publish; a directly granted repository is visible immediately anyway, so silence costs nothing. The comment carries **no URL and no invitation id**: the page builds the invitation URL from the assignment's own naming pattern, so nothing out of a public comment is ever rendered or dereferenced. The broker locks the acceptance issue with `|| true`, so the lock is best effort — which is why **a rejection outranks a `provisioned:` marker wherever it sits**, rather than the last comment winning.

**Why the invitation exists at all, measured rather than argued.** The standing question behind every version of "just make the students org members" is whether a member is *invited* or *added directly*. Run on `pxl-classroom-testbed/starter-template` — private, baseline of zero direct collaborators and zero pending invitations — and reverted, with the baseline verified back to zero:

| account | org role | access to the repo *before* | `PUT …/collaborators/{login}` | invitation |
|---|---|---|---|---|
| `tomcoolpxl-student1` | not a member | `none` | **201 Created** | yes — `read`, id `331584155` |
| `tomcoolpxl-lecturer1` | **member** (plain) | `none` | **204 No Content** | **none** |

**The control arm is the point.** Without a case that produces 201, a 204 cannot be told apart from "this setup never invites anybody", and the whole measurement would have been a green tick on an unasked question — the same defect as the section above. Same repository, same call, one minute apart: the non-member got a real invitation, so the endpoint was willing, and the 204 is a genuine difference.

**And the confound was removed rather than reasoned away.** The first attempt used an org *owner*, which proves nothing — owners hold admin on every repository, so their 204 could be the "already a collaborator" clause. GitHub's *Add a repository collaborator* reference lists three separate 204 clauses (an existing collaborator, **an organization member**, an existing team member), but documentation is exactly what said `/user/memberships/orgs/{org}` works with a user token. So the owner was demoted to a plain member for the measurement — `PUT /orgs/{org}/memberships/{login}` with `role: member` on an *already active* membership changes only the role and keeps `state: active`, so nobody has to accept anything — and the pre-grant read was taken: `permission: none`, no ownership, no team, not a direct collaborator. Genuinely no access, added directly anyway, `permission: read` the instant the call returned. **Membership alone does it, independently of `default_repository_permission`** — which stays `none`, and with students as members would become the only reason membership grants no repository access. Restored to `admin` afterwards; the testbed needs it.

One limit survives, and it is the whole decision: **enrolling by org membership is itself an invitation.** This repo already knew, in the `members` note inside `MANIFEST_APP_PERMISSIONS` (`lib/audit.mjs`), where the deleted `roster_mode: org_member` is the mode that *"enrolled by org INVITATION"*. So org membership does not remove an acceptance step, it **moves it from once per assignment to once per course org**: six assignments become one acceptance instead of six, every assignment after the first provisions silently with the repository simply appearing — and the *first* one still lands in exactly the state this section is about.

This is *"unreadable is not evidence"* one level deeper than it had been applied. Every earlier instance keyed off the transport - a non-`ok` response, a thrown read, a capped walk. This one was `ok`, well-formed, and empty, and the only thing wrong with it was that it was **an answer to a question we were not entitled to ask**. Where a read's authority cannot be established, a green tick and a "none found" are the same lie. `tests/invitation-evidence.test.mjs` holds the measurement and pins the rule; `tests/student-wait-copy.test.mjs` forbids the sentence on every student surface; `tests/e2e/40-provisioning-wait.spec.mjs` now drives the empty-list case and the 403 case through the *same* expectation, which is the assertion the old file could not make.

### Publishing opened a door, and nothing ever closed it.

Raised as "a student can spam `pxl-accept:` issues on a public broker, each burning an Actions run **billed to the org**" — and that framing was wrong in the expensive word. The broker is a **public** repository and so is the hub, so the runner is **free**; this file's own broker header already said it: *"one boot on a free public runner."* Cost was never the issue, and chasing it would have produced a rate limiter nobody needed.

What the measurement found instead, on PXL-Automation-II:

| broker | `INVITE_ENABLED` | |
| :--- | :--- | :--- |
| `broker-2526-examen-aut2-ek2` | **true** | deadline passed **30 Aug** |
| `broker-test-pe-1` | true | |
| `broker-test-pe3` | true | |

`publish-assignment.yml` sets that variable to `true` and **nothing ever set it back**. So every broker an organization has ever published still boots a runner for any `pxl-accept:` title, five days or five years after the assignment finished — and the hub then refuses each one as `rejected:past-deadline`. Not expensive; **guaranteed waste**, on a surface that grows by one door per assignment for the life of the org.

The defence that already existed is worth writing down, because it is why this was never urgent: the job-level `if:` skips anything that is not a `pxl-accept:` title *before a runner is allocated*, the signature is verified before any credential is in scope, and `concurrency: accept-<login>` serialises one attacker to a single run at a time. `INVITE_ENABLED` was the kill switch all along — it was simply only ever switched on.

So the nightly closes it in the pass that finalizes the deadline (`scripts/close-acceptance.mjs`, step 5 of `finalize`), which costs no extra run, and the refusal moves into the pre-runner condition where it costs no runner either. `continue-on-error`, before the commit that can race, and the broker's name comes from `lib/broker-repo.mjs` rather than a composed `broker-<id>` — which would have closed nothing on exactly the assignments carrying a custom `broker_repo`.

**The general lesson is the shape, not the variable.** Every `publish` in this system has a matching state it turns *on*; ask what turns it off, and when. This one had an answer for eleven months and it was "nobody".

**So the question was asked of the rest, and the answer was worse.** Publishing switches on five things: two hub workflows, the broker's variables, the broker's secrets, and the broker repository itself.

| switched on by publish | switched off by |
| :--- | :--- |
| `daily-activity`, `deadline-sentinel` | themselves ✓ |
| `INVITE_ENABLED` | the nightly, as of this change |
| **`PXL_BROKER_PRIVATE_KEY` + client id** | **nothing** |
| the broker repository and its issues | nothing, by design — it is the audit trail |

The credential is the one that mattered. It is set on every broker at publish and was never removed: measured 2026-09-03, a finished exam's broker still held it five days after the deadline. The blast radius is bounded — the broker App holds `contents: write` on the hub alone, and its whole capability is submitting a dispatch the signature check bounds, which is exactly why the *provisioning* App's key was moved off these repositories in the first place — but it is still **a private key replicated to one PUBLIC repository per assignment, with no expiry**, that stops being needed the moment the door above closes. Eleven assignments is eleven copies.

The same nightly step deletes both, **after** closing acceptance and never before: delete-then-fail-to-close leaves a broker that still accepts and can no longer dispatch, so a student gets a hung acceptance instead of a closed one. This order fails to "closed, key still present", which costs nothing. `publish-assignment.yml` sets them on every publish, so reopening an assignment restores them without anyone knowing this ran — and that file already sweeps the *legacy* provisioning keys off brokers the same way, which is the precedent this follows.

**Proven in production, not only against a stub.** Everything above was verified with a fake `fetch`, which is exactly the standard that let the comment channel pass every test and 404 on every real run. So the change was rehearsed live, using a fixture that already existed for the purpose: `finalize-drill`, an assignment published with its deadline minutes away — *"Live rehearsal of the deadline chain. Safe to delete."* One was published into `pxl-classroom-testbed` at 22:44 with a 22:49 deadline, the nightly was dispatched at 22:50, and:

```
finalize (pxl-classroom-testbed, finalize-drill)   5. Close acceptance on the broker
23:09:09  [ok] acceptance closed on pxl-classroom-testbed/broker-finalize-drill (INVITE_ENABLED=false)
```

Before: `INVITE_ENABLED=true`, two secrets — read mid-run, so the change is attributable to that step and nothing else. After: `false`, zero secrets, no warning in the log. `find-finalizable` picking the drill out at all is the half no test can fake: the deadline arithmetic, the artifact hand-off between jobs and the matrix expansion all ran against an assignment published five minutes earlier. **A drill whose deadline is minutes away is the cheapest way to exercise a nightly, and it is worth keeping.**

**And the invariant is checkable, so it is checked against the world.** `tests/live/broker-hygiene.mjs` (read-only, outside `npm test`) walks every participating org and asserts that an assignment past its deadline has `INVITE_ENABLED=false` and no `PXL_BROKER_*` secret. Its first run across 13 organizations found one still open — `PXLAutomation/broker-finalize-drill`, deadline 26 August, variable still `true`, both secrets present — which no unit test could have found, because the fault is in the state of the world rather than in the code. It also refuses to be reassuring about what it cannot see: three brokers answered 403 because the token is not an owner of those orgs, and they are reported as **NOT checked** rather than clean, which is the same rule the org-owner audit applies to `/apps/{slug}`.

**One trap found while looking and deliberately not fixed yet:** `publish-assignment.yml` composes `broker-${ASSIGNMENT_ID}` in **three** places rather than using `lib/broker-repo.mjs`. It is correct today only because nothing writes a custom `broker_repo` — the module, `audit.mjs` and every reader already support one — so publish would configure one repository while the hub and the page used another. Read side guarded, write side hand-rolled: the same asymmetry as `broker-issue-target`, still open.

### A student reached the lecturer dashboard, badged "Lecturer".

Reported with a screenshot, 2026-09-03. `tomccargo` — a test **student** account, not a member of `PXL-Automation-II` — signed in and was shown the organization in the switcher, a **Lecturer** tag beside their name, and an onboarding card:

> **Almost there - PXL-Automation-II needs its control repository**
> One more step before you can create assignments.  `[ Open Setup Organization ]`

**Nothing was exposed and nothing would have worked.** Every read behind that screen is the private control repository, which answers 404 to them; every write — workflow dispatch, control-repo commit — is refused by GitHub; and no report, roster, team or student data is served from Pages (checked directly: all 404). But a surface that hands a student a staff console and an admin button is its own defect, and it teaches them they have found a hole. That reaction is the correct reaction.

**Two faults, and the second is what made the first alarming.**

*There was no authorization check anywhere.* `/dashboard/:org?` has no route guard, and the org list is `/user/installations` filtered to organizations. Accepting **one assignment** grants collaborator access to a repository inside an installation whose `repository_selection` is `all`, so GitHub lists that installation — and the page inferred *"the App is installed somewhere you can touch"* as *"you are staff here"*.

*And a 404 was read as "absent".* GitHub returns 404, not 403, for a private repository you cannot see, so **"the control repo does not exist" and "the control repo exists and is not yours" arrive identically** — and the code picked the friendlier one. The repository existed the whole time. Same rule as the invitation, three sections up, in a place nobody thought to look for it.

**The gate is demonstrated capability, and the third signal is the interesting one.** Hub write alone would have refused the very persona the onboarding screen exists for: a lecturer just made an org owner has no hub write and produces the identical 404 as the student. `GET /orgs/{org}` separates them — `default_repository_permission` is returned to an organization **owner** and `null` to everyone else. Measured: `"none"` for an org I own, `null` for one I am not a member of; and `lib/audit.mjs` already reads that field for the base-permission check. So `staff = hubWritable || orgAdmin`, both **positive** signals, and an unreadable answer refuses rather than admits.

**The fixture could not express the bug, which is why no test caught it.** "Student" meant *no installations at all*, so no spec could reach the dashboard as one — the mock modelled a student who could never have been in the reported situation. `studentHasInstallation` is what makes it reachable, and `tests/e2e/58` now drives it. A mock that cannot represent the failure is a mock that guarantees a green suite.

`tests/dashboard-authorization.test.mjs` pins the rest, and promptly caught its own author: two of its guards anchored on `dashState.value = hubWritable.value`, which stopped existing when the org signal was added, and *"every literal a test anchors on still exists in the code"* failed them rather than letting them inspect nothing.

### A comment is a notification. Metadata is not.

The hub's channel to a student is their own acceptance issue on the public broker — the one surface both halves can read. It was a **comment**, and a student forwarded what that actually looks like from the other side:

> Re: [PXL-Automation-II/broker-test-pe4] Acceptance (processed) (Issue #1)
> **Closed #1 has been completed.**

They authored that issue, so GitHub subscribes them to it, and every state change and comment mails them. The system was sending a student email about its own plumbing — a redacted title and a closed issue — which reads like a failure and explains nothing. Nobody had thought about the issue from the inbox of the person who opened it.

The same inbox settled the mechanism for free: the broker **edits the title and closes** in the same step, and only the close produced mail. **Metadata is silent; conversation and state changes are not.**

So the outcome moved from a comment to a **label**, and the broker stopped closing (it still redacts, which is what actually protects the signed invitation, and still locks). Three separate problems fell out at once:

* **No mail.** Labels notify nobody.
* **The 403 disappears.** `POST .../comments` on the locked issue was returning 403 with the cause still unidentified after two wrong inferences; `POST .../labels` on the *same* locked issue returned **200**. Measured on the testbed, along with labels being auto-created on first use, so publishing provisions nothing.
* **It cannot be forged.** Applying a label needs triage or write access, which a student does not have on a broker. Anyone can comment on a public issue — which is why the comment version needed a rule making a rejection outrank a success. The rule is kept, but only as insurance against a bug setting both.

**And the label is deliberately coarse.** `outcome:invited` and `outcome:rejected`, no more. A per-reason label is filterable in one click, so `outcome:rejected-not-on-roster` would have been a public, sortable list of which named students are not enrolled — enrolment data about people who never chose to publish it, which is not the same as their own acceptance being public. Nineteen per-slug sentences on the student's page went with it: the label says *who* was refused, the private control repo says *why*, and the page now says "your lecturer can see the reason". That is a real loss of student-facing detail, taken deliberately, and it is written down here so the trade is not quietly reversed by someone adding "just one more label".

### The read side was guarded and the write side was not.

Found in the run log of the acceptance above, while checking whether the *fix* for it could use the same channel:

```
BROKER_REPO: PXL-Automation-II/broker-test-pe3
ISSUE_NUMBER: 2
[ok] could not comment on the broker issue (HTTP 404) - the rejection stands
```

`client_payload.broker_repo` is a **full name**, because that is what `acceptance/broker-workflow.yml` puts on the wire. `comment-acceptance-outcome.mjs` composed `/repos/${ORG}/${BROKER_REPO}/issues/${N}/comments`, which resolves to `/repos/PXL-Automation-II/PXL-Automation-II/broker-test-pe3/issues/2/comments`. So the feature — telling a rejected student *why*, on the one surface both sides can read, which is the entire point of the change — **had never worked once**, on any acceptance, since it shipped. And it printed `[ok]` while failing, under a step that is `continue-on-error: true` by design, so nothing was ever red and no annotation was ever raised. *Not fatal is not the same as not broken*, again.

The other half is worse and was invisible for the same reason. `read-team-payload.mjs`, reading the very same field, had the parse right **and** carried a check beside it — *"the broker must belong to the org the dispatch claims to be for, or a forged dispatch could make the hub read an issue from anywhere"*. The comment script had neither. It runs with the hub's App token, which holds `issues: write` on **every participating org**, so a dispatch naming `broker_repo: other-org/some-repo` would have had the hub post into a repository with nothing to do with the acceptance. A `repository_dispatch` payload is attacker-shaped input; the guard existed, one file away, and only on the path that reads.

Both halves are `lib/broker-issue-target.mjs` now, imported by both scripts, and `tests/broker-issue-target.test.mjs` refuses a bare name, a three-segment path and a cross-org owner, and fails if either script splits the field or composes the path itself. Two rules the sweep is worth repeating for: **a shape guard on the read path is not a shape guard**, and **a failure printed as `[ok]` is how a feature stays dead for as long as nobody re-reads the log.** The step stays `continue-on-error` — a courtesy comment must not turn a handled rejection red — but it now emits `::warning::`, which is visible without being fatal. Those are two different requirements and the script had conflated them.

### A failed tracking-issue lookup created a second tracking issue.

`notify.mjs` did `if (search.ok && search.data.length > 0) … else create`, so a 403, a rate limit and a 5xx all went down the same branch as *"none found"* - and every transient failure minted another `[NOTICE] PXL Classroom - Instructor Notifications`. The duplicates are the visible cost; **the dedup history splitting across them is the worse one**, because the marker `notifyEvent` searches for lives on comments the new issue does not have, so every alert already posted gets posted again. It now refuses, saying so - the same *"unreadable is not evidence"* rule Tier 1 applies to `/apps/{slug}`, where a permission it cannot see yields **no check** rather than a green one. `.length` on a non-array is `undefined` and therefore falsy, which was the same create branch a second way, so the shape is now checked explicitly. Both notify steps in `acceptance-handler.yml` also gained **`continue-on-error: true`**: `accept.mjs` exits 0 for `rejected:*` precisely so a student who is not on the roster does not paint the hub red, and a rate-limited *comment about* that rejection must not undo it. `tests/list-pagination.test.mjs`.

### One retry policy for GitHub's rate limits: `lib/rate-limit.mjs`.

A *secondary* limit answers 403 **or** 429, does not necessarily zero `x-ratelimit-remaining`, and does not always send `retry-after` - it announces itself in the **message**, so a header-only test misses it and the call fails outright instead of backing off. `retryDelayMs` honours `retry-after`, waits out a primary limit's `x-ratelimit-reset` when it is near, falls back to GitHub's documented 60 s floor for a secondary limit, and still returns `null` for a permission 403, which carries neither the headers nor the wording. `lib/gittree.mjs` (large multi-file commits - seeding a cohort's teams) and `lib/gh.mjs` (provisioning, collect, lockdown, preserve, report, notify, usage, team-payload read) both import it; `gittree` had the fix and `gh` did not, which is exactly the fork the shared module exists to prevent. **`gh()` must read the response body before deciding to retry** - the signal is in `data.message`. `tests/rate-limit.test.mjs` fails if either file grows its own copy.

### `|| true` on a `git add` is not a safety net, it is the silent version of the same bug.

The guard for *"no workflow stages a control-repo directory that might not exist"* exempted `|| true` with the comment *"also safe: neither is fatal"* — and that was wrong against the guard's own premise, three paragraphs higher in the same file, which already said `git add` on a missing pathspec "stages nothing at all - not even the pathspecs that did match". Measured rather than argued:

```
$ git add missing/ present/          # present/f.txt has a real, staged-worthy change
fatal: pathspec 'missing/' did not match any files
exit=128
$ git diff --cached --name-only
(nothing)
```

So `|| true` swallows the 128, `diff --cached --quiet` is true, and the step **exits 0 reporting "No changes."** Not fatal, and therefore invisible: the version without it at least turns the step red. Two workflows had it — `daily-activity` staging `observations/ lockdowns/ reports/` after finalising a deadline, and `regenerate-dashboard` staging `public/ reports/`. On a control repo missing any one of those, both would have computed the work, committed none of it, and gone green; and `find-finalizable` decides whether to retry from exactly those records. The precedent was already written down in that comment: `teams/` joined the staging list on 2026-08-19 and two live orgs did not have it. **Not fatal is not the same as not broken** — when the remedy for a loud failure is to silence it, the guard is now enforcing the quiet one.

### A rule that lives only in CLAUDE.md is a rule with a spelling.

`node -p "require('./$JSON').state || ''"` sat in `publish-assignment.yml` under a rule that says **No inline `node -e` in workflow YAML**. Nothing enforced it, so the rule was only as good as the reviewer remembering that `-p` is `--print` is the same thing as `-e`. It broke three rules at once, in eleven characters: inline JS in YAML, a shell value composed into JS *source text*, and `2>/dev/null || true` turning an unreadable assignment file into "no prior state" — which is the one answer that makes the failure-revert strand the assignment it was written to rescue. It is `scripts/read-json-field.mjs` now, with the absent-field and unreadable-file cases pinned apart, because those two had been the same answer.

The same sweep found `publish-assignment.yml` setting `http.<host>/.extraheader` and never unsetting it, while `setup-org.yml` one file away had carried a `trap … EXIT` for months with a comment explaining exactly why. Both rules have guards now. The lesson is not about either bug: **the rules with tests behind them were all clean, and every violation found was under a rule that had none.** The credential rules with guards — SHA pinning, `environment: provisioning`, the `[bot]` dispatch refusal, `${{ }}` never reaching a script — were at zero, and the `[bot]` guard in particular is worth reading as a model: it derives the class instead of listing files, computes the "legitimately machine-dispatched" exemption from real dispatch calls, resolves `needs:` transitively, and asserts a floor so a walk that stops matching cannot look like a clean repo.

### Two places that must agree, with no mechanism making them agree.

The shape behind more incidents in this file than any other, and it is worth naming because the instances look unrelated until they are listed together:

| the two places | how it failed |
| :--- | :--- |
| `submission_status` vs the late-activity warning | one spelled `firstLateSha !== lastOnTimeSha`, the other the weaker `if (firstLateSha)` — a finished exam read `on-time` beside "late activity" on every row |
| `s.status` vs the row field `submission_status` | a field that does not exist compares as a constant, and `!==` fails **open** — a whole roster counted as having accepted |
| `client_payload.broker_repo`, read twice | one reader split `owner/repo` and checked the org, the other composed `/repos/${ORG}/${BROKER_REPO}` — 404 on every acceptance, and the write path unauthorised |
| the `pxl-acceptance-outcome:` marker | the writer emitted `provisioned:invited`, the reader matched `rejected[a-z:-]*` — the hub posting into a void looks exactly like the feature not existing |
| `setOutput("invited")` / `action.yml` / `if:` | a typo in any of three files yields `''`, so `if: '' == 'true'` is false, the run is **green**, and the step never runs |
| `tableColumnCount` vs the `<th>`s | a hand-maintained count, already fixed once for the two grading columns, still missing the Team column |
| a `deployment.yml` value re-spelled in YAML | guarded, and the reason `tests/deployment-literals.test.mjs` exists at all |

**The class cannot be guarded as a class.** There is no sweep that finds "two things that ought to agree" — agreement is semantic, and a checker general enough to find them would flag every pair of similar strings in the repo. What *can* be done is the thing every successful guard here already does: **derive one side from the other**, in a test, and assert a floor so a broken parser cannot pass as a clean repo.

So the remedy is per-contract, and the work is enumerating the contracts rather than inventing a detector. Two were added on 2026-09-03. `tests/workflow-output-contract.test.mjs` walks every `steps.<id>.outputs.<name>` in every workflow, resolves the step to its local action, and fails if `action.yml` does not declare it — then takes each declared output's `value:` back to the script behind it and fails if nothing writes that name. `tests/table-colspan.test.mjs` reads the `<th>`s out of the template, rebuilds the arithmetic `tableColumnCount` should be, and additionally requires every conditional header to have a `<td>` gated on the *same* condition, because a header and a cell disagreeing shifts every column after it and renders perfectly.

Both were written against a live defect and both were checked by re-introducing it. Two notes from doing that. The output guard **failed on its own parser first** — composite actions call scripts as `node "$GITHUB_ACTION_PATH/accept.mjs"`, and `read-team-payload.mjs` writes six outputs from one template rather than through `setOutput` — which is the good failure: a matcher that silently finds nothing is the vacuous guard this whole section warns about, and it announced itself immediately instead of passing. And the guard on the *class* is only ever as good as the floor: `assert.ok(checked >= 15)` is what stops a future refactor from turning the walk into a no-op that still reports success.

## Tests and guards

### A guard whose anchor was renamed away checks nothing, silently.

Most source-scanning tests slice a function body out by string search (`src.slice(src.indexOf("async function saveTeamMembers"))`). When the anchor stops existing, `indexOf` returns **-1**, `slice(-1)` yields the file's **last character** and `slice(0, -1)` yields all-but-one - and an absence assertion over either passes vacuously. This repo has already shipped it: a `buildDoc` sweep anchored on `const doc = {`, a string that file has never contained (it is `return {`), fell back to scanning the whole file and reported *"omits 0 fields"* while checking nothing. Swept 2026-08-27: **60** unguarded slice-anchors across the suite, but **zero dead** - every anchor still resolves, so nothing is blind today. Rather than rewrite sixty call sites, `tests/test-anchor-liveness.test.mjs` pins the invariant that makes them safe: every literal a test hands to `indexOf` must still exist somewhere in the code, so the next rename turns the dependent guard **red, naming itself**, instead of quiet. It skips punctuation anchors (under 6 chars) and lines comparing against `-1` (a deliberate must-not-appear check), asserts a **floor** on how many anchors it found, and **blanks comments before scanning** - this file and several others explain the rule by quoting an anchor, and a raw scan reads the prose as code.

### A git worktree is a full second checkout, and the repo-wide scanners walked into it.

`.claude/worktrees/` holds them, so every "nothing re-implements this rule" guard found the worktree's copy of the module and reported it as a fork, and `eslint .` linted every file twice under the wrong config (the per-directory overrides are anchored at the repo root, so `acceptance/accept.mjs` came back as `'process' is not defined`). CI never has a worktree, so this is a purely local red - which is worse, not better: `npm run lint` is the command CLAUDE.md tells you to trust, and a suite that goes red because a sibling checkout exists trains people to ignore red. `.claude` is now in `eslint.config.mjs`'s `ignores` and in the skip list of all six directory scanners (`deadline-countdown`, `effective-deadline`, `check-run-score`, `scripts-inventory`, `vue-route-safety`, `workflow-dispatch-contract`) - six copies of that list, which is its own small fork waiting to happen.

### Three readers of `overrides/` had three different levels of honesty.

`lockdown.mjs` logs a failure line for a file that will not parse, on the stated reasoning that an unreadable extension is the only trace a lecturer would have; `find-finalizable.mjs` prints one too; `report.mjs` **silently skipped it**. Report is what tells the lecturer the extension is running and lockdown is what decides the freeze, so a file readable by one and not the other reproduces exactly the divergence that made extensions worth fixing. The same reader also loads `acceptances/`, `repositories/` and `observations/`, where a silent drop is missing evidence or a student absent from their own cohort report. An **absent** directory is still "none" - git cannot store an empty one - so only a file that exists and will not parse is reported.

### Two fixtures described a system that does not exist, and both tests passed for months.

Same failure, two shapes, found in one sweep on 2026-09-01.

**`tests/lockdown-extension.test.mjs` invented the record shape.** It wrote ONE repository record per team carrying `members: ["dana", "erin"]`. Production writes one per **login** (`repositories/<id>/<login>.json`, from `scripts/write-repository-record.mjs`) with `team_slug` and no member list — nothing has ever set `members`. So `planTargets`' `rec.members` always collapsed to `[login]`, the team's most generous extension never propagated, and RUNBOOK.md §3.2's promise to a lecturer — *"an extension granted to one member applies to the whole team, because they share one repository"* — was simply false. Not cosmetic either: under `lock_method: ruleset` the lock is **repo-scoped**, so the team-mate *without* an extension locked the repository the extended student was still entitled to push to. The membership comes from `teams/<id>/<slug>.json` now (authoritative, and it changes after provisioning when a student switches team), and the fixture builds what production builds. Both new tests were checked against the pre-fix code first and both failed there — a test written after a fix that has never been seen to fail is a guess.

**`tests/contract-form-diagnostics.test.mjs` reimplemented the code under test.** A helper called `vueBuildDoc`, commented *"recreating AdminView.vue's exact buildDoc() logic"*, had drifted past `invite_key`/`invite_pubkey` (the signed-acceptance keypair — it still emitted only the withdrawn `invite_token`), `claim_domains`, `autograde`, `feedback_pr`, `description`, and defaulted `min_team_size || 1` against a shared default of 0. The diagnostics contract was being checked against a document the Admin Panel had not written for months. The fix was not to re-sync the copy: `buildDoc` moved to `lib/assignment-doc.mjs`, takes the form state as a parameter, and both the SPA and the test import it. **If the thing under test cannot be imported, that is the defect.**

### A fixture option nobody destructures is discarded in silence.

`tests/e2e/16-team-lifecycle-edge-cases.spec.mjs` passed an `acceptances` option to `setupStandardMockRoutes` for months. The fixture never named it, so JavaScript threw it away without a word - no error, no warning, and a green test that looked like it was exercising a mock which did not exist. Replacing the whole payload with garbage left it passing, which is the only way to find out; and it could never have worked, because that scenario renders the **student** surface and a student cannot read the control repo at all. `tests/fixture-options.test.mjs` is the guard. It scans three shapes, because the discard happens at each: a key handed straight to the fixture; a key handed to a spec-local wrapper that forwards its options in (`...opts` / `...extra` / a bare pass-through, followed **transitively** - 17 wrappers, 3 of them reachable only through another one, so a one-level check misses them); and the general form, any helper whose parameter is a destructuring pattern being called with a key the pattern does not name. Plus the inverse on the fixture's own side: an option it declares and never reads. Two things keep it honest - it asserts **floors on what it actually scanned** (339 call sites, 17 wrappers), since a walk that silently stops matching looks exactly like a clean repo, and it mutation-checks its own scanner against synthetic sources. Its blind spot is named rather than papered over: it proves a key *reaches* the code that reads it, not that the spec passing it exercises the route that key feeds - only a per-test mutation run shows that.

### A whole exam cohort was flagged for late activity, and nobody had touched anything.

Reported from live use on 2026-09-02, by a lecturer who was himself one of the flagged accounts: *"all of them have late activity warnings. That is not true. That's impossible because I'm one of those people, and I didn't touch anything."*

**An observation is a collector run, not a commit.** `report.mjs` walks observations and records `firstLateSha` for the first one whose `observed_at` falls after the deadline - but the nightly, the lockdown pass and preservation all re-read an *untouched* repository after the deadline and write an observation stamped "now" carrying the student's unchanged, on-time SHA. So `firstLateSha` comes back **equal to `lastOnTimeSha`** for a repo nobody pushed to.

The status logic had always known this and guarded on `firstLateSha && firstLateSha !== lastOnTimeSha`. The `warnings` array, twenty-five lines below it, used `if (firstLateSha)`. Every row therefore read `on-time` *and* carried a `late-activity-detected` warning - the two halves of the same screen contradicting each other, on the page a lecturer would cite in a plagiarism or lateness dispute.

**The lesson is the drift, not the condition.** Two expressions that must agree were written twice and only one was ever corrected. They are one `const hasLateActivity` now, consumed in both places, so there is nothing left to keep in sync. The tooltip was wrong in the same direction and got the same treatment: it said *"Commits were detected after the student's effective deadline"*, which is what the buggy condition tested rather than what the fixed one means.

Two tests, because a false positive and a false negative are different failures: a repo merely re-observed after the deadline must carry **no** warning, and a genuinely different SHA after the deadline must still carry one. Verified by reintroducing the old condition - the first fails, the second passes - since a test written against code that already works proves only that it runs.

**Why nothing caught it.** There was no test on `warnings` at all. Every rule in this repo with a guard behind it was clean; this sat under one that had none, which is the same sentence as most of the entries above it.

### "If I press Set up, I get an empty screen." The button worked.

Reported from live use on 2026-09-02. The *Automated checks* button on the Admin Console opened nothing — a dimmed page and no dialog.

The button fired, the modal mounted, its content was correct, and it was drawn at **y = −1245**: 1245 pixels above the top of the window, where nothing can scroll to it. `.admin-view` carried `fade-in`, and

```css
@keyframes fadeIn { from { transform: translateY(4px) } to { transform: translateY(0) } }
.fade-in { animation: fadeIn 0.2s ... forwards; }
```

`animation-fill-mode: forwards` retains the last keyframe, so the wrapper keeps `transform: matrix(1,0,0,1,0,0)` **for ever** — and an identity transform is still a transform. Any of `transform`, `filter`, `perspective`, `will-change` or `contain` on an ancestor makes that element the containing block for its `position: fixed` descendants, so `.modal-overlay { position: fixed; inset: 0 }` resolved against a 2000px-tall page wrapper instead of the viewport and landed exactly `scrollY` off-screen. Measured: overlay `y=-1281, height=2000`, `scrollY=1281`.

**It only fails once the page is scrolled**, which is why it survived. Every existing modal test opens its dialog near the top of a short page, where `scrollY` is 0 and the bug is invisible; this button sits far enough down the assignment form that reaching it *guarantees* the scroll. Two views used `fade-in` as their root — `AdminView` and `SetupView` — and it would have trapped the first dialog anyone added to the latter.

`tests/e2e/47-modal-in-viewport.spec.mjs` measures the rendered box against the viewport on a scrolled page, and separately walks the overlay's ancestors for *any* containing-block property, so it catches the next cause rather than only this one. Verified by putting `fade-in` back: 3 of 3 fail.

Two things fell out of it. **`.admin-view` and `.setup-view` are declared nowhere** — `fade-in` was the only rule that had ever styled those elements, so removing it left them bare and `tests/undeclared-classes.test.mjs` immediately asked why; they are structural wrappers and now say so. And the page **is** covered by the conformity spec, which checks exactly two rules — one primary button, and *uppercase* pill capsules. The admin list's `draft`/`published` pills were **lowercase**, so they walked straight past a guard written for them. They are status dots now (DESIGN.md §1.3), which is what closed that hole.

### Then two students were marked LATE on an exam for finishing on time.

Investigating the warnings above turned up something worse underneath them. `PXL-Automation-II/2526-examen-aut2-ek2`, a finished exam, read:

| student | status | last commit | vs deadline |
| :--- | :--- | :--- | :--- |
| IlkayDuranPXL | **late** | 30 Aug 13:10 | **6h50m early** |
| LowieSerneelsPXL | **late** | 30 Aug 19:05 | **0h54m early** |

Deadline `2026-08-30T20:00Z`. Verified against GitHub itself, not just the report: both authored *and* committed dates are before the deadline, and `GET /commits?since=<deadline>` returns **zero** commits for either repository. Nobody in the cohort pushed anything late.

**`observed_at` is when the collector looked, not when the student acted.** The classifier compared the *observation's* timestamp to the deadline. The nightly ran 00:33 on the deadline day and again 00:34 the next morning, so a commit made at 13:10 in between was first *seen* after the deadline and classified late. The row even carried `uncertainty_interval_seconds: 69966` — 19.4 hours of acknowledged ambiguity — and nothing consulted it.

**The systematic shape is the worst one available for grading.** It cannot mark a late student on time; it only marks *on-time students late*, and only those who worked close to the deadline. Students who finished days early were unaffected, because an earlier nightly had already seen their work. On an exam, "worked up to the deadline" is most of the cohort.

**This file already contained the lesson, one field over.** `lock_down_at` had been moved off the observation for exactly this reason — *"when the nightly happened to look, not when the student stopped being able to push"* — and the same mistake sat untouched in the deadline comparison beside it. The observation records carried `commit_date` the whole time; `report.mjs` read it only to *display*, never to decide.

The commit's own timestamp decides now, with `observed_at` kept as the fallback for observations that predate the field, and the observation window still recorded so the tamper-evidence is not lost. Three tests: a commit before the deadline first seen after it is **on-time**; a commit after the deadline is **late** however early it was seen; and an observation with no `commit_date` still falls back to when it was seen — because losing that fallback would silently reclassify every historical report.

**The column that started it is gone.** Of the three warnings a student row could carry, `accepted-not-provisioned` *was* the acceptance column restated and `late-activity-detected` fired only where the status already said `late`. Only `missing-repo-id` said anything no other column could, and it now renders on the repository cell where the fault is. A fourth entry, `deadline-gap`, had a tooltip in the SPA and could never appear — `report.mjs` emits it as a cohort notification, never as a student warning — which is DESIGN.md §1.5 in miniature.

### A job that never ran was worth zero marks.

A colleague's exam template, running live in `PXL-2TIN-CloudEssentials-2627` on the assignment `proef-pe1`, grades **one commit and no others**:

```yaml
jobs:
  run-autograding-tests:
    if: github.event.head_commit.message == 'einde examen'
```

It has to. The checks read the student's own AWS account through credentials they commit themselves, and that sandbox is gone when their lab session ends — the measurement cannot be re-taken afterwards from the archive, which is the one thing this system is otherwise built on. So the score is captured at hand-in, by the student, on their way out of the exam.

Probed live on 2026-09-04, `proef-pe1-d-ries` had two commits and two check runs:

| commit | message | check run | conclusion | annotations |
| :--- | :--- | :--- | :--- | ---: |
| `9c4e1867` | Initial commit | `run-autograding-tests` | **skipped** | 0 |
| `44fbe7f0` | einde examen | `run-autograding-tests` | success | 3 |

**A job skipped by an `if:` gate is still a check run.** Not an absence — a real check run, at a real commit, named after the job, which `pickAutogradeCheckRun` therefore picks, correctly: it *is* the grading job. It carries no annotations, so `parseCheckRunScore` fell through to its conclusion branch, and the conclusion branch had two cases — green means full marks, anything else means zero. `skipped` fell into *anything else*.

So a student who handed in and then pushed one more commit — a typo in the readme — was recorded **0**, in the grade table and in the CSV export, beside a CI badge reading `skipped` that nobody has to notice. The file's own picker refuses this two functions up: *"no autograding run at this commit is NOT a zero and NOT a pass."* The conclusion branch had never been asked what to do about a conclusion that means the run did not happen.

`failure` stays a real zero — that run ran, and the student's code broke it. `skipped`, `cancelled`, `timed_out`, `stale`, `neutral`, `action_required` and a run still in progress are now `graded: false`, and both readers list the student by name instead of scoring them. Confirmed on this repository's own workflows, where `disable-when-empty` and `watch` are `conclusion: skipped` on every nightly.

**Then the second half: the score was never lost, it was one commit back.** `submission_marker` on the assignment records the literal the workflow compares against, and when a read finds no grading run, `lib/submission-marker.mjs` walks the submission branch for the newest commit carrying it — bounded by that student's own effective deadline, so a late hand-in cannot be graded, and capped, so "not found in the last 300 commits" stays distinguishable from "never handed in". Two extra requests, and only for the students who need them. It decides **only** which commit's check run is read: preservation, lateness and what counts as a submission are untouched.

Matching is exact and case-sensitive on the whole message, because the workflow's `==` is. Being more generous would name a commit the workflow never graded and then report "the grading workflow was skipped" about the commit the lecturer believes is the hand-in.

**Then the screen said both things at once.** The first shipped version put "Hand-in commit message" in the assignment form as a field of its own, beside the grading summary. Which rendered, on a cloud exam, as:

```
Automatic grading
Off · submissions are not scored automatically          [ Set up ]

Hand-in commit message
[ einde examen                                        ]
```

Both halves were true of *something* and the pair was nonsense. "Off" is about checks configured **here**; "submissions are not scored automatically" is a claim about the student's repository that the form cannot evaluate, and is flatly false for the assignment this field exists for. DESIGN.md §1.5 names that shape — a status line asserting a condition it has no way to check — and it had been read as being about `InvitationShare` rather than as a rule.

The wording was not the bug. **Checks defined here and a workflow that came with the template are two answers to one question**, and the form had them as two unrelated features, so no wording could make them agree. The modal now asks *who defines the checks* first and the hand-in message is the template branch's only setting; the form is back to one line, which is what ARCHITECTURE §11.6 said it was for. Neither branch is stored — checks mean one, a marker means the other — so there is no third flag to disagree with either, and saving answers both halves rather than leaving a marker behind that the summary no longer mentions.

What stays unsayable is deliberate: with no checks and no marker, "the template grades every push" and "nothing grades this" are the **same document**. The line says `Off` and the note beside it is scoped to what the screen owns. Storing a `graded_by` flag would let it say more; it would also be a field whose only reader is the sentence describing it.

**And the timeout on the generated workflow was in the wrong unit the whole time.** Every `classroom-resources` grader documents `timeout` as *"Duration (in minutes)"*; the schema field is `timeout_s`, seconds, capped at 600, and both CLI runners honour it as seconds. `provision.mjs` passed the number straight through, so one test definition meant 30 seconds locally and **30 minutes** on Actions — on the side that bills an organisation's minutes, for a runaway loop nobody is watching.
